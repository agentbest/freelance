DevOpsエンジニアのフリーランス案件では、**変更を安全に届けるCI/CDの設計、IaCのモジュールとstateの扱い、パイプラインに渡す権限と秘密情報の管理、ほかの開発者が迷わず使える共通の仕組みづくり**が見られます。ツールの名前を知っていることは前提で、評価が分かれるのは、**なぜその構成にしたかを説明し、チームで使い続けられる形にできるか**です。

この記事では、案件で問われるスキルを分野ごとに整理し、経験の段階ごとに求められる水準を示します。独立までの準備は[DevOpsエンジニアがフリーランスになるには](/media/devops-how-to/)で扱っています。

## DevOpsの案件で見られるスキルの全体像

| 分野 | 中身 | 案件での見られ方 |
|---|---|---|
| CI/CD | テスト・ビルド・デプロイの流れ、環境ごとの昇格、承認 | 速さと安全さの両方を考えて組めるか |
| IaC | モジュールの設計、stateの管理、差分の確認、既存環境の取り込み | チームで安全に変更できる形にできるか |
| 権限と秘密情報 | パイプラインの権限、クラウドへの認証、外部の部品の扱い | 自動化の仕組みが攻撃の入り口にならないか |
| 実行環境 | コンテナの作成、成果物の保管、クラウドの実行基盤 | 作ったものをどこでどう動かすか説明できるか |
| 共通の仕組み | テンプレート、社内基盤、利用の手引き | 開発者を利用者として扱えるか |
| コードを書く力 | 自動化のスクリプト、小さなツール、テスト | ほかの人が保守できる形で書けるか |

監視・ログ・SLOといった信頼性の分野も関係しますが、深く問われるのはSREの案件です。詳しくは[SREの案件で求められるスキル](/media/sre-skills/)をご覧ください。コンテナ基盤そのものの運用は、Kubernetesを専門とする案件で問われることが多い分野です。

## CI/CD：速さと安全さを両立させる設計

CI/CDの案件では、パイプラインを動かせるかより、**何をどの順に確かめ、どこで止めるか**の設計が問われます。

- 変更のたびに走る軽いテストと、時間のかかるテストを分け、待ち時間を短くする
- 一度ビルドした成果物を、検証から本番まで同じものとして昇格させる
- 本番へのデプロイに承認を挟むかどうかを、変更の影響の大きさで決める
- 失敗したときに前の版へ戻す手順を、パイプラインの中に用意しておく

案件でよく聞かれるのは、「ビルドが遅い」「デプロイのたびに手作業が残る」といった課題に、どこから手を付けたかです。測ってから直した経験は、具体的に説明できる材料になります。

## IaC：チームで安全に変更できる形にする

Terraformの公式ドキュメントでは、stateは設定に書いたリソースとクラウド上の実物を結びつける記録だと説明されています。また、ロックやアクセス制御のない場所にstateを置くと、データの消失や秘密情報の漏えいにつながるおそれがあると注意しています（2026年10月時点）。

案件で差がつくのは、次のような判断です。

| 判断 | 問われること |
|---|---|
| モジュールの分け方 | どこまでを共通にし、どこからを各チームに任せるか |
| stateの分け方 | 環境やシステムごとに分け、変更の影響範囲を小さくしたか |
| 差分の確認 | 適用前の差分を、だれがどこでレビューする流れにしたか |
| 既存環境の取り込み | 管理画面で作られた環境を、止めずにコードの管理下に移したか |
| ずれへの対応 | コードと実物がずれたときに、どちらに合わせるかをどう決めたか |

Terraformの認定の位置づけと試験の範囲は[Terraform Associateの記事](/media/cert-terraform/)で解説しています。

## 権限と秘密情報：自動化を入り口にしない

CI/CDは、本番を変更できる強い権限を持つ仕組みです。そのため、セキュリティの観点から設計を問われる場面が増えています。

GitHubの公式ドキュメントでは、GitHub Actionsについて次のような使い方が勧められています（2026年10月時点）。

- 外部のアクションは、書き換えに備えてコミットのハッシュ値で固定する
- ワークフローに自動で渡されるトークンの権限は、既定を読み取りだけにし、必要なジョブだけに広げる
- 秘密情報はJSONなどにまとめず、値ごとに登録し、ログに出たら削除して入れ替える

また、OpenID Connect（OIDC）を使うと、クラウドの認証情報をGitHubに保存せず、ジョブごとに短い期間だけ有効なトークンを受け取ってクラウドに接続できると説明されています。長く有効な鍵をパイプラインに置かない構成にした経験は、多くの案件で評価されやすい内容です。

:::view
DevOpsの案件をご紹介していると、発注側が気にしている点として、パイプラインの権限の扱いがよく挙がります。面談で「本番への認証情報をどこに置いていたか」「外部の部品をどう固定していたか」を落ち着いて説明できる方は、任せる範囲を広く考えてもらいやすい傾向があります。経験がない部分は、個人の検証環境で試したことと分けて話すことをおすすめします。
:::

## 共通の仕組み：開発者を利用者として扱う

複数のチームが使う基盤を整える仕事は、プラットフォームエンジニアリングと呼ばれることがあります。CNCF（Cloud Native Computing Foundation）のTAG App Deliveryがまとめた白書では、プラットフォームを利用者の必要に合わせて提供される機能のまとまりと位置づけ、その特徴として、製品として扱うこと、文書と導入の手引き（推奨の手順をまとめた「ゴールデンパス」を含む）、手作業を減らしたセルフサービス、開発チームの負担を減らすこと、必要な部分だけ選んで使えること、最初から安全であることなどを挙げています。

案件で見られるのは、技術より次のような動き方です。

- 利用するチームに話を聞き、困りごとから優先順位を決めた
- テンプレートや手引きを用意し、新しいサービスの立ち上げを手順どおりに進められるようにした
- 共通の仕組みを使うかどうかを各チームに選ばせ、使われない理由を聞いて改善した
- 変更を知らせ、古い版から移ってもらうまでを進めた

**作ったものが使われたか**まで話せることが、この分野の経験の中心です。

## 経験の段階ごとに求められる水準

同じ分野でも、経験の段階によって任される範囲が変わります。

| 段階 | CI/CD | IaC | 権限・共通の仕組み |
|---|---|---|---|
| 担当者 | 既存のパイプラインにジョブを足し、失敗の原因を調べられる | 既存のコードの値を変え、差分を読んで適用できる | 決められた手順で秘密情報を登録できる |
| 中心メンバー | 一つのサービスの流れを一から組み、待ち時間を減らせる | モジュールを作り、stateを分けて環境を作り分けられる | パイプラインの権限を絞り、OIDCなどで鍵を置かない構成にできる |
| 設計・標準づくり | 複数チームで使う雛形を作り、移行を進められる | 既存環境の取り込みと、組織全体のモジュールの方針を決められる | 共通の仕組みを製品として運営し、利用者の声で改善できる |

フリーランスの案件で多いのは、中心メンバー以上の役割です。担当者の段階の経験が中心の場合は、どの分野を中心メンバーの水準まで伸ばすかを決め、在職中や参画中に経験を積むと、案件の選択肢が広がります。

## コードを書く力と周辺の知識

DevOpsの仕事では、シェルやPython、Goなどで小さなツールや自動化のスクリプトを書く場面が多くあります。テストを書き、レビューを通し、ほかの人が直せる形で残せることが求められます。言語ごとの案件の傾向は[Goの案件で求められるスキル](/media/go-skills/)や[Pythonの案件で求められるスキル](/media/python-skills/)が参考になります。

クラウドの知識は、権限とネットワークの基礎が特に問われます。クラウドごとの水準は[AWSエンジニアのスキルの記事](/media/aws-skills/)をご覧ください。

:::caution
「CI/CD構築経験あり」とだけ書くと、既存の設定を少し変えた経験と、流れを一から設計した経験の区別がつきません。面談では、どこまでを自分で決めたかを確かめられます。担当した範囲と、決めたことを分けて説明できるよう準備しておきましょう。
:::

## スキルの示し方

スキルシートや面談では、ツールの名前より、**何を変え、だれが楽になり、何が安全になったか**を伝えます。

- 手作業のリリースをパイプラインに置き換え、承認を挟んで本番へ出す流れにした
- 管理画面で作られた環境をTerraformに取り込み、変更をレビューしてから適用する流れにした
- パイプラインの認証をOIDCに切り替え、長く有効な鍵を廃止した
- 新しいサービス用の雛形を作り、複数のチームに使ってもらった

書き方の詳細は[DevOpsエンジニアのスキルシートの記事](/media/devops-skillsheet/)で解説しています。

:::view
当社では、契約で業務範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。DevOpsの案件は、構築のあとに利用者からの問い合わせ対応や運用が続くことがあるため、スキルに合うかどうかとあわせて、どこまでが業務範囲かを参画前に確かめておくことをおすすめします。案件票の書き方で分かりにくい点は、ご質問いただければ確認します。
:::

:::point
- DevOpsの案件では、CI/CDの設計、IaCのモジュールとstate、パイプラインの権限と秘密情報、共通の仕組みづくりが見られる
- 権限の扱いは、外部の部品の固定、トークンの権限の絞り込み、OIDCによる鍵の廃止などで示せる
- 共通の仕組みは、作ったものが使われたかまで話せると評価されやすい
- 経験の段階ごとに任される範囲が変わるため、伸ばす分野を決めて経験を積む
:::

## よくある質問

### GitHub Actions以外のCIツールの経験でも案件はありますか？

あります。CIツールは現場によってさまざまで、移行の案件では古いツールの経験が役に立つこともあります。どのツールでも、何を確かめる流れにしたか、権限をどう扱ったかは共通して問われるため、その考え方を説明できるようにしておきましょう。

### プラットフォームエンジニアリングの経験がないと応募できませんか？

共通の仕組みを作る案件ばかりではありません。一つのサービスのCI/CDやIaCの整備が中心の案件も多くあります。そのうえで、雛形を作ってほかのチームに使ってもらった経験があれば、小さな範囲でもプラットフォームに近い経験として伝えられます。

### 資格はどのくらい評価されますか？

資格は知識の裏付けになりますが、案件では実務で何を決めたかが先に見られます。手作業の構築からコード化に広げたい場合など、資格が補いになる場面もあります。IaCについては[Terraform Associateの記事](/media/cert-terraform/)で、効きやすい場面を解説しています。
