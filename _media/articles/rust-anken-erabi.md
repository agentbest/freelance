フリーランスのRustエンジニアが案件を選ぶときは、報酬や稼働日数に加えて、**Rustで書く範囲、Rustを選んだ理由と求められる成果、チームのレビュー体制、既存コードとunsafeの状態、ツールチェーンと開発環境、契約の形と責任、稼働の振れ幅と契約期間**の7点を契約前に確かめておくことが大切です。Rustの案件は、同じ「Rust開発」の募集でもこの7点の違いで負担と責任が大きく変わります。

特に見落としやすいのは、**求められる成果と、任される判断の範囲が釣り合っているか**です。性能や安全性の結果を求められているのに、設計を変える権限がない案件では、どれだけ働いても状況を動かせません。この記事では、Rust案件に固有の確認点を整理します。契約書全般の確認点は[業務委託契約書のチェックポイント](/media/contract-checkpoints/)で解説しています。

## Rust案件の選び方で差が出る理由

Rustは、発注側が理由をもって選ぶことの多い言語です。その理由によって、求められる成果も、仕事の重さも変わります。

- **速さが理由**：性能を測り、目標に届かせることが成果になる
- **メモリ安全性が理由**：境界のコードとレビューの質が問われる
- **配りやすさが理由**：対応する環境の数と、保守の続けやすさが問われる
- **既存の技術方針が理由**：範囲の決まった機能の追加や保守が中心になる

また、Rustを書ける人がチームに少ない現場では、参画した人に**設計の判断やレビュー、チームへの教え役**が集まりやすくなります。案件票に「Rustでの開発」としか書かれていなくても、実際にはチームの中で最もRustに詳しい人として扱われる、ということが起こりえます。こうした差は、契約前に聞いておかないと見えにくい部分です。

## 契約前に確かめたい7つの点

### 1. Rustで書く範囲

Rustで書くのはサービス全体か、一部の部品か。新しく作るのか、既存のRustのコードを保守するのか。ほかの言語で書かれた部分との割合も聞いておきます。Rustの経験を積みたい場合、Rustで書く割合が小さい案件では、思ったほど経験にならないことがあります。

### 2. Rustを選んだ理由と、求められる成果

性能の目標があるなら、何をどの環境で測り、どこまで届けば成果とするのかを確かめます。目標が「速くしてほしい」のような曖昧な形だと、参画後にどこで区切るかでもめやすくなります。目標がまだ決まっていない場合は、目標を決めることも仕事に含まれるのかを聞いておきます。

### 3. チームのRustの経験とレビュー体制

チームの中でRustを書ける人の数、レビューを誰が担うか、自分のコードを誰がレビューするかを確かめます。自分しかRustを書けない状態だと、レビューを受けられず、品質の責任が一人に集まります。反対に、チームへの教え役を期待されているなら、その時間を稼働の見込みに入れておく必要があります。

### 4. 既存コードの状態と、unsafe・他言語との境界

既存のRustやC/C++のコードがある場合、テストの有無、unsafeを使っている箇所の量、他言語とのつなぎ方（FFI）を聞きます。前の担当者がいなくなったコードの保守は、読むのに時間がかかる分、初月の成果が出にくくなります。

:::view
Rustの案件をご紹介していると、参画後に負担が大きくなりやすいのは、「Rustで書ける人がチームに一人だけ」という状態を、契約前に知らなかった場合です。レビューや設計の相談、ビルドの不具合の対応まで一人に集まり、本来の担当の作業が進まなくなる傾向があります。面談で、Rustを書ける人の数とレビューの担当を具体的に聞いておくことをおすすめします。
:::

### 5. ツールチェーンと開発環境

使っているRustの版、安定版か開発中の版（nightly）か、ツールチェーンの更新を誰がいつ行うかを確かめます。Rustの安定版は6週間ごとに出ます（2026年10月時点、Rustの公式ドキュメントによる）。Cargo.tomlの`rust-version`で、最低限サポートする版を宣言している現場もあります。nightlyに頼っている現場では、更新のたびに直す手間が生じやすいため、その作業が担当に含まれるかを聞いておきます。

開発環境が手元のPCか、配布された環境か、ビルドにどれくらいの時間と資源がかかるかも、稼働の見込みに関わります。リモートで働く場合の確認点は[Rustエンジニアのリモート案件の記事](/media/rust-remote/)で解説しています。

### 6. 契約の形と、負う責任の範囲

業務委託の契約が、作業を行うこと自体に報酬が払われる準委任か、完成した成果物に報酬が払われる請負かで、負う責任が変わります。性能の目標の達成を約束する形になっていないか、不具合が見つかったときにどこまで直す責任があるかを確かめます。違いは[準委任と請負の違い](/media/junin-vs-ukeoi/)で解説しています。

書いたコードの権利の扱いも、Rustの案件では大切な確認点です。自分で作って公開しているクレートを案件で使う場合、その権利がどうなるかを契約の前に確かめておきましょう。考え方は[著作権の記事](/media/copyright/)、依存するクレートのライセンスの扱いは[OSSライセンスの記事](/media/oss-license/)で解説しています。

### 7. 稼働の振れ幅と契約期間

リリースの前後や、性能の問題が表に出たときに、稼働がどれくらい増えるかを聞いておきます。月の稼働時間に幅を決めて精算する契約なら、幅と超えたときの扱いを確かめます。精算の仕組みは[精算幅の記事](/media/seisan-haba/)をご覧ください。

契約期間は、置き換えや新規開発の区切りに合わせて決まることがあります。最初の契約が検証の期間だけなのか、その後も続く前提なのかを聞いておくと、次の案件を探す時期を見通しやすくなります。

:::caution
「Rustでの開発」として参画したのに、Rustとは関係のない言語の保守や、インフラの運用の作業が多くを占めていた、ということがあります。案件票と面談で聞いた内容が、契約書の業務内容とずれていないかを確かめましょう。参画後に作業が増えたときの扱いは[作業範囲が広がったときの契約の扱い](/media/scope-change/)で解説しています。
:::

## 確かめた内容を書面と照らし合わせる

面談や問い合わせで確かめた内容は、契約の書面と照らし合わせます。

| 面談で確かめた点 | 書面で見る箇所 |
|---|---|
| Rustで書く範囲、担う作業 | 業務内容・業務の範囲 |
| 求められる成果・性能の目標 | 業務内容、成果物、検収の条件 |
| 契約の形と責任 | 契約の種類、不具合への対応、損害賠償の範囲 |
| 書いたコードの権利 | 知的財産権の扱い |
| 稼働の振れ幅 | 精算の条件、稼働時間の幅 |
| 契約期間 | 契約期間、更新の条件 |

フリーランス法では、発注事業者がフリーランスに業務を委託したとき、給付の内容、報酬の額、支払期日などの取引条件を、書面やメールなどで直ちに明示することが求められています（2026年10月時点、公正取引委員会の案内による）。明示される事項の詳しい内容は[フリーランス法の取引条件の明示の記事](/media/freelance-act-terms/)で解説しています。

面談で聞いた話が書面にない場合は、契約の前に確かめておきましょう。逆質問の組み立て方は[Rustエンジニアの面談の記事](/media/rust-interview/)と[業務委託の面談で聞いておくべき逆質問](/media/reverse-questions/)で解説しています。

:::view
当社では、取引先の会社の実態と支払条件を確かめた案件を扱い、契約では業務範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。Rustで書く範囲やレビューの体制など、案件票だけでは分からない点は、ご質問いただければ確認します。
:::

:::point
- Rust案件は、同じ「Rust開発」でも書く範囲、体制、求められる成果で負担が大きく変わる
- 契約前に、書く範囲・選んだ理由と成果・レビュー体制・既存コード・ツールチェーン・契約の形・稼働と期間の7点を確かめる
- 成果を求められる範囲と、任される判断の範囲が釣り合っているかを見る
- 面談で聞いた内容を、契約の書面と照らし合わせる
:::

## よくある質問

### 自分しかRustを書けない案件は避けたほうがよいですか？

一概に避ける必要はありません。設計の判断を任され、経験を広げられる面もあります。ただ、レビューや教え役の負担が稼働の見込みに入っているか、品質の責任をどこまで負うかを確かめてから受けることをおすすめします。

### 性能の目標がある案件では、どんな契約が向いていますか？

目標の達成そのものを約束する形だと、届かなかったときの責任が重くなります。調査と改善の作業に対して報酬が払われる形か、目標を決める作業を先に区切る形かを、契約の前に確かめておきましょう。契約の形の違いは[準委任と請負の違い](/media/junin-vs-ukeoi/)が参考になります。

### 報酬の高い案件と、Rustで書く割合の高い案件で迷ったらどうしますか？

今後どの分野のRustで経験を積みたいかで決めるのが一つの考え方です。Rustの経験を伸ばしたい時期なら、書く割合の高い案件のほうが次の案件につながりやすくなります。報酬の決まり方は[Rustエンジニアの報酬の記事](/media/rust-rate/)で解説しています。
