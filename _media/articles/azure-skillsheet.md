Azureエンジニアのスキルシートは、**テナント・管理グループ・サブスクリプション・リソースグループのどの層で作業したか**と、**Entra IDでどこまでの権限を持ち、何を任されていたか**を書くのが基本です。Azureの案件は、IDと権限、社内ネットワークとのつなぎ込みが絡むことが多く、読み手は「この人に触らせてよい範囲」をシートから判断しようとするからです。Microsoft 365やActive Directoryの経験は、Azureの経験と混ぜずに、隣の欄で示します。

全体の構成は[スキルシートの基本](/media/skillsheet-basics/)で解説しています。どんな経験が求められるかは[Azureエンジニアの案件で求められるスキル](/media/azure-skills/)、経験の棚卸しと独立の準備は[Azureエンジニアがフリーランスになるには](/media/azure-how-to/)をご覧ください。この記事では、シートへの書き方と見せ方に絞って説明します。

## 「どの層で作業したか」を書くと影響範囲が伝わる

Azureの環境は、テナントの下に管理グループ、サブスクリプション、リソースグループと階層が重なっています。同じ「Azureの構築経験」でも、1つのリソースグループの中で仮想マシンを作った人と、管理グループにポリシーを割り当てて全社の決まりを作った人では、任せられる仕事がまったく違います。

そこで、プロジェクト欄の担当内容に、作業した層を一言添えます。

| 作業した層 | 書き方の例 |
|---|---|
| テナント | Entra IDの条件付きアクセスの設計に参加。グループの命名規則を作成 |
| 管理グループ | 部門ごとの管理グループを切り、Azure Policyで利用できるリージョンを制限 |
| サブスクリプション | 本番・検証・開発のサブスクリプションを分け、予算のアラートを設定 |
| リソースグループ | 割り当てられたリソースグループの中で、Webアプリとデータベースを構築 |

これは書き方を示すための例です。上の層ほど経験が少ないのは普通のことで、隠す必要はありません。下の層だけを担当していた場合も、「上位の決まり（ポリシーや命名規則）に沿って構築した」と書くと、統制のある環境で作業できる人だと伝わります。

環境の規模は、サブスクリプションの数や利用者の数を「数十」「数千人規模の社内利用」のように桁でぼかして書けば十分です。テナント名やサブスクリプションIDは書きません。

## Entra IDの権限は「持っていた権限」と「設計した権限」を分ける

Azureの案件の読み手が特に気にするのが、IDと権限の経験です。ここは2つに分けて書くと、誤解が起きにくくなります。

- **持っていた権限**：自分が作業で使っていたロール。「サブスクリプションの共同作成者」「特定のリソースグループの所有者」など
- **設計した権限**：ほかの人のために決めたロールの割り当て。「運用担当のカスタムロールを作成」「特権ロールを申請制にする運用を設計」など

「Entra ID経験あり」とだけ書くと、ユーザーを追加していただけなのか、権限の設計を担っていたのかが読み取れません。ロールの名前は製品の用語なので書いてかまいませんが、実際のグループ名やユーザー名は参画先の情報です。

テナント全体に影響する管理者の権限を持っていた場合は、その事実と、どんな手続きで使っていたか（申請・承認のうえで期限付きで使った、など）を1行添えると、権限の扱いに慎重な人だと伝わります。

## Microsoft 365・Active Directoryの経験の並べ方

Azureの案件に応募する方には、社内のActive DirectoryやMicrosoft 365の管理から入った方が多くいます。これらはAzureの案件でも評価されやすい経験ですが、スキル一覧で「Azure」と同じ行にまとめると、Azureの基盤の経験が実際より長く見えてしまいます。

スキル一覧は、次のように行を分けます。

| 区分 | 書き方の例 |
|---|---|
| Azure基盤 | 仮想ネットワーク、App Service、Azure SQL Database（構築・運用 ○年） |
| ID・権限 | Entra ID（条件付きアクセスの設計に参加）、Azure RBAC（ロール割り当ての設計） |
| 隣接する経験 | Active Directory（ドメインの運用 ○年）、Microsoft 365の管理（ライセンスとメールの運用） |
| IaC・自動化 | Bicep（新規作成）、Terraform（既存の修正）、PowerShellでの定型作業の自動化 |

「隣接する経験」の行を作っておくと、読み手はAzureの経験とは別に、ID連携や移行の案件で生かせる経験として読めます。オンプレミスのActive DirectoryとEntra IDの同期に関わった経験は、両方の行にまたがる経験なので、プロジェクト欄で具体的に書く価値があります。

:::view
Azureの案件をご紹介していると、Microsoft 365の管理やActive Directoryの運用の経験が、スキルシートの最後に小さく書かれているだけの方を多く見かけます。移行やIDの整備の案件では、社内の管理者側の事情が分かる方が面談で評価されやすい傾向があります。Azureの経験と混ぜずに、隣接する経験として独立した行で書くことをおすすめします。
:::

## ハイブリッド接続は「誰と何を決めたか」まで書く

オンプレミスとAzureをつなぐ経験は、Azureの案件でよく求められます。ただし「VPN Gateway構築」「ExpressRoute経験あり」と製品名だけを書いても、自分がどこを担ったかは伝わりません。接続の仕事は、社内のネットワーク担当や回線の事業者と分担して進むことが多いためです。

次の3点を書くと、関わり方がはっきりします。

1. **自分の担当範囲**：Azure側の設定だけか、オンプレミス側の機器の設定も含むか
2. **決めたこと**：アドレスの割り当て、名前解決の方法、どの通信を通すか
3. **調整した相手**：社内のネットワーク担当、利用部門、回線の事業者など（社名は書かない）

ネットワークの機器側の経験が中心の方は、[ネットワークエンジニアのスキルシートの書き方](/media/network-skillsheet/)もあわせてご覧ください。

## 認定資格は試験番号と有効期限を添える

Microsoftの認定資格は、正式名称に加えて**試験番号**と**有効期限**を書くと、読み手が範囲を確かめやすくなります。

> 例：Microsoft Certified: Azure Administrator Associate（試験AZ-104）20XX年X月取得、有効期限20XX年X月

Microsoft Learnの案内では、Azure管理者アソシエイトの更新頻度は12か月とされ、Microsoft Learnのオンライン評価に合格すれば無料で更新できると案内されています（2026年10月時点）。AWSなどに比べて更新の間隔が短いため、取得した年だけを書いていると、すでに期限が切れているのに有効なように見えることがあります。提出の前に、Microsoft Learnの自分の資格情報で状態と期限を確かめてから書きましょう。

認定は廃止や名称の変更が起こります。廃止された認定（たとえばAzure セキュリティ エンジニア アソシエイト）を持っている場合の扱いは、[Azureの案件で求められるスキル](/media/azure-skills/)で触れています。期限が切れたものは「取得歴」として分けて書くと、有効な資格と混同されません。

## プロジェクト欄の記入例

ここでは、オンプレミスの業務システムの移行と、IDの整備にまたがる担当を想定しています。**以下は書き方を示すための例**で、実在の案件や実績ではありません。業界や規模はぼかしています。

> **期間**：20XX年X月〜20XX年X月（1年程度）
> **案件概要**：流通業向け 社内システムのAzureへの移行と、利用者のIDの整理
> **作業した層**：サブスクリプションとリソースグループ（管理グループのポリシー設計はレビューに参加）
> **規模・立場**：基盤チーム数名（自分はメンバー。ID関連は主担当）
> **担当工程**：構築、移行、運用の引き継ぎ
> **使用技術**：仮想ネットワーク、VPN Gateway、App Service、Azure SQL Database、Entra ID、Azure RBAC、Bicep（新規作成）
> **担当内容**：Bicepで検証と本番の環境を作成。オンプレミスとの接続ではAzure側の設定を担当し、社内のネットワーク担当とアドレスの割り当てを決めた
> **工夫・成果**：個人に直接付いていたロールを、グループ単位の割り当てに整理した。管理者の権限を常時付与から申請制に変える運用を提案し、採用された

「レビューに参加」「Azure側の設定を担当」のように、主担当でない部分は関わり方をそのまま書いています。面談では、その権限の割り当て方にした理由を聞かれることがあります。答えられる深さで書くことが、評価の安定につながります。

:::caution
構成を具体的に書こうとして、テナントのドメイン名、サブスクリプションID、リソースの実際の名前、社内のIPアドレスの範囲などがシートに残ってしまうことがあります。いずれも参画先の環境を特定できる情報です。提出の前に、固有の名前や値が残っていないか見直してください。どこまで書いてよいかの考え方は[スキルシートに書いてよいこと・いけないこと](/media/confidentiality-in-skillsheet/)をご覧ください。
:::

## ほかのクラウドの経験と並べるとき

AWSやGoogle Cloudの経験もある場合は、クラウドごとに行を分けます。Azureの案件に応募するなら、Azureの経験を上に置き、ほかのクラウドは「関連する経験」として添えます。AWSの経験が長い方は、AWSで使ったサービスの名前をAzureの名前に置き換えて書かないでください。名前を読み替えただけの経験は、面談でAzure特有のIDや権限の話になったときに食い違いが出ます。AWSの書き方は[AWSのスキルシートの書き方](/media/aws-skillsheet/)、Google Cloudは[GCPのスキルシートの書き方](/media/gcp-skillsheet/)で紹介しています。

:::view
当社では、経歴はご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。Azureの案件は、IDの整備、基盤の設計、移行、運用のどれが中心かで読み手が見る行が変わります。要約の1行目に、軸にしたい仕事の種類と、作業してきた層を書いておくことをおすすめします。どの層の経験として書けばよいか迷う場合は、ご質問いただければ確認します。
:::

:::point
- テナント・管理グループ・サブスクリプション・リソースグループのどの層で作業したかを書く
- Entra IDは「持っていた権限」と「設計した権限」を分けて書く
- Microsoft 365やActive Directoryの経験は、Azureと混ぜずに隣接する経験として行を分ける
- 認定は試験番号と有効期限を添える。更新が12か月ごとなので、状態を確かめてから書く
:::

## よくある質問

### 仮想マシンの運用が中心で、設計の経験がありません。どう書けばよいですか？

作業した層と、運用の中で自分が判断したことを書きます。バックアップの設定の見直し、監視のアラートの整理、パッチの適用手順の改善などは、運用から構築へ広げるための実績になります。決まった構成の中で作業していた場合も、その決まりに沿って作業したことを書けば、統制のある環境での経験として読まれます。

### 権限の設計に関わった経験は、守秘義務に触れませんか？

ロールの種類や割り当ての考え方（グループ単位にした、申請制にした、など）は、一般的な設計の考え方として書けることが多い部分です。実際のグループ名、利用者の名前、例外として許可した具体的な設定などは書かないようにします。判断に迷う場合は、参画先との秘密保持の取り決めを確かめてください。

### 認定資格の有効期限が切れていました。書かないほうがよいですか？

書いてかまいませんが、有効な資格とは分けて「取得歴」として、取得年月と期限が切れていることが分かる形で書きます。Azureのロールベースの認定は、オンライン評価で更新できると案内されているため、応募の前に更新できるかを確かめておくのも一つの方法です。
