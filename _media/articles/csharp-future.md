C#エンジニアの将来性は、**「C#が残るかどうか」より「どの.NETで、どんな仕事をするか」で考える**のが現実的です。.NETは毎年新しい版が出て、版ごとにサポートの期限が決まっています。そのため、運用中のシステムでは版を上げる作業が続き、古い.NET Frameworkの業務アプリを新しい.NETへ移す仕事も残ります。

一方で、移行の下調べや定型的な書き換えは、生成AIを使った支援ツールが担う場面も出てきました。これから選択肢を広げるには、移行の判断と検証、データベース、クラウド、業務の理解といった「ツールに任せきれない部分」を自分の強みにしていくことが近道です。

案件の型や独立の準備は[C#エンジニアがフリーランスになるには](/media/csharp-how-to/)、案件で見られるスキルは[C#の案件で求められるスキル](/media/csharp-skills/)で扱っています。この記事では、今後の変化と、キャリアの広げ方に絞って整理します。

## .NETの公式な周期から見える仕事の流れ

Microsoftのサポートポリシーでは、.NETは毎年1回リリースされ、偶数の版がLTS（3年サポート）、奇数の版がSTS（2年サポート）とされています。サポート期間の最後の6か月は「保守期間」で、直されるのはセキュリティの問題だけです。2026年10月時点の状況は次のとおりです。

| 版 | 種類 | サポートの期限・状況 |
|---|---|---|
| .NET 8 | LTS | 2026年11月10日まで（保守期間中） |
| .NET 9 | STS | 2026年11月10日まで（保守期間中） |
| .NET 10 | LTS | 2028年11月14日まで |
| .NET 11 | 奇数の版（STSの扱い） | 2026年10月25日にRC3が公開。11月10〜13日の.NET Conf 2026でリリース予定と案内 |

この周期が意味するのは、**「一度作れば終わり」にならない**ということです。.NET 8で動いているシステムは、2026年11月を境にサポートが切れるため、.NET 10などへ上げる判断が必要になります。こうした版上げは毎年どこかの現場で発生し、依存しているライブラリの更新やテストを含めて、まとまった作業になります。

もう一つの流れは、デスクトップの技術も更新が続いている点です。Microsoft Learnの「What's new in .NET 10」では、WinFormsとWPFにも改善が入ったことが案内されています。WinFormsやWPFの業務アプリは、新しい.NETに移したうえで使い続けるという選択肢が現実的にあり、画面を作り直すかどうかは、システムごとの判断になります。

## 生成AIで変わりつつある移行の進め方

C#の仕事で特に影響を受けやすいのが、移行の作業です。Microsoft Learnでは、GitHub Copilotのアップグレード用エージェントが、.NET Frameworkのプロジェクトを.NET 8以降へ上げる作業を支援すると案内されています。進め方は次のように整理されています。

1. **評価**：プロジェクトの構成、依存関係、コードの書き方を調べ、互換性の問題や移行の範囲を洗い出す
2. **計画**：移行の順番（下の層から上げるか、アプリから上げるかなど）や、置き換えるライブラリを決める
3. **実行**：作業を小さなタスクに分け、変更ごとにコミットを作り、ビルドとテストで確かめる

同じページでは、エージェントが解決できない問題に当たったときは人に助けを求めること、生成された計画のファイルを人が見直してから次へ進めることも説明されています。WebFormsからBlazorへの移行や、Newtonsoft.JsonからSystem.Text.Jsonへの置き換えといったシナリオも挙げられています。

ここから読み取れるのは、**移行の作業そのものより、何をどの順で移すか決める力と、移した結果が正しいか確かめる力の比重が増える**ということです。たとえば次のような判断は、業務とシステムの事情を知る人が担う部分として残りやすいと考えられます。

- 画面の技術（WinForms・WPF）を残すのか、Webに作り直すのか
- 移行の途中で、旧版と新版をどう並行して動かすか
- 帳票や外部の装置との連携など、テストで確かめにくい部分をどう検証するか

生成AIの使い方は、発注元の方針によって大きく違います。ソースコードを外部のサービスに送ってよいかは、契約やセキュリティの規程で決まっているため、参画の前に確かめておきましょう。秘密保持の考え方は[NDAで確認すること](/media/nda/)で解説しています。

:::view
C#の案件をご紹介していると、移行の経験を「◯◯を.NET 6に上げた」と一行で書かれている方が少なくありません。面談で評価されやすいのは、何を調べて移行の範囲を決めたか、どこで動きが変わり、どう確かめたかまで話せる方です。今後、ツールで書き換えを進める現場が増えても、この部分の説明はそのまま強みになります。経歴の整理では、移行の判断と検証の手順を書き出しておくことをおすすめします。
:::

## 選択肢を広げる4つの方向

C#の経験を土台にした広げ方は、主に次の4つです。どれも、今の経験と地続きで始められるものを選んでいます。

| 方向 | 身につけたいこと | 生かしやすい経験 |
|---|---|---|
| 移行・モダナイズ | 互換性の調査、段階的な移行計画、移行前後の検証 | .NET Frameworkの保守、テストの自動化 |
| クラウドと運用 | Azureでの実行環境、CI/CD、コンテナ | ASP.NET CoreでのWeb開発 |
| データベースと性能 | SQLの改善、EF Coreの使い方、実行計画の読み方 | 業務アプリでのSQL Server経験 |
| 上流工程・業務 | 要件の整理、移行方針の説明、見積もり | 業務アプリの設計書作成、利用部門とのやり取り |

### 移行・モダナイズ

前の章のとおり、移行の作業はツールの支援が進んでいます。そのぶん、ツールが出した評価や計画を読み、業務上のリスクを判断できる人の役割がはっきりしてきます。互換性の問題を洗い出した経験や、移行後に動作の違いを見つけた経験は、早めに言葉にしておきましょう。

### クラウドと運用

.NET 10では、SDKだけでコンソールアプリのコンテナイメージを作れるようになるなど、クラウドで動かす前提の機能が増えています。アプリを作るだけでなく、デプロイと監視までを担えると、関われる工程が広がります。Azure側の広げ方は[Azureエンジニアの将来性](/media/azure-future/)も参考にしてください。

### データベースと性能

業務システムでは、画面よりもデータの扱いに時間がかかる場面が多くあります。EF Core 10ではLINQの改善などが案内されていますが、どんなSQLが発行されるかを確かめて直す力は、版が変わっても求められます。

### 上流工程・業務

移行の方針を決める段階では、利用部門や発注元の情報システム部門に、費用と期間、リスクを説明する役割が生まれます。進め方は[上流工程の案件に入るために必要な経験](/media/upper-process/)で解説しています。

## 経験に応じた広げ方

### 実装が中心の時期

まず、新しい.NETとASP.NET Coreでの開発経験をしっかり積むことが土台になります。生成AIでコードを書く現場でも、async/awaitの誤った使い方や、意図しないSQLの発行を見抜けないと、レビューで指摘を受ける側にとどまります。出てきたコードを読んで直せる力を優先しましょう。

### 設計や移行を任され始めた時期

移行や版上げの案件で、範囲を決める段階から関わるのが次の一歩です。ツールが出した評価をそのまま使うのではなく、業務の都合と合わせて優先順位を付けた経験は、上流に入る材料になります。Javaの業務システムと進め方の近い部分も多いため、[Javaエンジニアの将来性](/media/java-future/)の記事も比較に使えます。

### 長く業務アプリを支えてきた人

製造業の制御系や、長年運用されてきた業務アプリの知識は、文書に残っていないことが多く、移行の場面で頼りにされます。40代・50代からの広げ方は[40代のフリーランス](/media/40s/)と[50代のフリーランス](/media/50s/)でも扱っています。業務の知識と、新しい.NETへの移行の進め方を組み合わせて説明できると、関われる案件の幅が保ちやすくなります。

:::caution
「C#の経験◯年」とまとめただけでは、新しい.NETの経験があるのか、.NET Frameworkの保守だけなのかが伝わりません。今後は、移行の経験や生成AIを使った開発の経験も問われやすくなるため、プロジェクトごとに版・領域・担当した判断を分けて書いておきましょう。書き方は[C#のスキルシートの記事](/media/csharp-skillsheet/)をご覧ください。
:::

## AIを組み込む開発との距離

.NETでは、生成AIを業務アプリに組み込むための仕組みも整えられています。Microsoft Learnのアップグレード用エージェントのページには、Semantic KernelのエージェントをMicrosoft Agent Frameworkへ移すシナリオも挙げられており、AIを使う部分も版上げの対象になっていることが分かります。

C#エンジニアがこの領域に関わる場合、求められるのはモデルそのものの知識より、既存の業務システムとAIの機能をどうつなぐか、権限やログをどう扱うかといった、業務アプリで培ってきた設計の力です。生成AIの開発を専門にする道は[生成AIエンジニアの案件で求められるスキル](/media/genai-skills/)で解説しています。

:::view
当社では、案件をご案内する前に、稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。業務の範囲・報酬・支払期日・契約期間は個別契約に書いてお渡ししています。移行の案件は、調査だけで終わるのか、実際の移行と検証まで担うのかで負担が大きく変わります。面談の前に、担当する工程と、生成AIのツールを使ってよいかを確かめておくことをおすすめします。
:::

:::point
- .NETは毎年版が出て、偶数はLTS（3年）、奇数はSTS（2年）。版上げの作業は毎年どこかで発生する
- .NET 8と.NET 9は2026年11月10日でサポートが終わり、.NET 10は2028年11月14日まで
- 移行は生成AIの支援が進み、範囲を決める判断と、結果を確かめる検証の比重が増える
- 移行・クラウド・データベース・上流工程のどれかを、今の経験と地続きで広げる
:::

## よくある質問

### WinFormsの業務アプリしか経験がありませんが、この先も仕事はありますか？

.NET 10でもWinFormsの改善は続いており、業務アプリを新しい.NETへ移して使い続ける現場もあります。そのうえで、移行の進め方や、ASP.NET CoreでのWeb開発に触れておくと、移行先を決める段階から関われるようになります。

### 生成AIで移行が自動化されると、C#エンジニアの仕事は減りますか？

一概には言えません。Microsoftの案内でも、エージェントが解決できない問題は人に助けを求め、計画を人が見直す流れになっています。作業の一部は速くなりますが、業務に合わせた判断と、結果の検証を担える人の役割は残ると考えられます。

### .NET 11が出たら、すぐに覚えるべきですか？

.NET 11は奇数の版で、サポート期間はLTSより短くなります。運用中のシステムでは、LTSの.NET 10を選ぶ現場も多いと考えられます。新しい機能は把握しつつ、まずは.NET 10への版上げや移行を着実に進められることを優先するとよいでしょう。
