Scalaエンジニアがフリーランスになるには、**Scalaで書いたサービスや処理を本番で動かした経験**と、**参画先のチームの書き方に合わせて、関数型のコードを読み書きできること**が目安になります。Scalaの案件は、すでにScalaで動いているシステムに途中から加わる形が多く、初日から既存のコードを読んで手を入れられるかが見られます。

経験年数の決まった基準はありません。目安としては、Scalaのチーム開発で、設計の相談からテスト、リリースまでを一通り担ったことがあるかどうかが分かれ目になりやすいところです。この記事では、出身ごとの準備と、独立までの進め方を整理します。

## Scalaの案件で最初に確かめられること

Scalaの案件の面談や書類選考では、次の3つがまず確かめられる傾向があります。

1. **本番で動いているScalaを触ったか**：学習や個人の開発だけでなく、利用者のいるサービスやバッチで、障害や改修を経験したか
2. **どの書き方のScalaか**：Javaに近い書き方か、型クラスやエフェクトのライブラリを中心にした書き方か
3. **どの版か**：Scala 2.12・2.13・3のどれで書いてきたか、ビルドの仕組み（sbtなど）を自分で直せるか

2つめは特に大切です。Scalaの現場は書き方の幅が広く、自分の経験と参画先の書き方が離れていると、立ち上がりに時間がかかります。自分がどの書き方の現場にいたのかを言葉にしておくと、案件を選ぶときの基準にもなります。

### 版の経験は時点とあわせて整理する

scala-lang.orgの配布ページでは、2026年10月時点で、Scala 3の現行版として3.10系、長期サポート（LTS）の版として3.3系と3.9系、Scala 2の保守版として2.13系と2.12系が並んでいます。どの版で何を作ったかを書き出しておくと、案件の条件と照らし合わせやすくなります。求められる技術の中身は[Scalaの案件で求められるスキル](/media/scala-skills/)で扱っています。

## 出身によって準備することが違う

### Javaの経験が長い人

JVMの知識、ライブラリの扱い、性能の調べ方はそのまま生かせます。一方で、面談では「Javaのように書いていないか」が見られることがあります。

- 変更できない値（val、不変のコレクション）を基本にして書けるか
- nullや例外に頼らず、OptionやEitherで失敗を表せるか
- パターンマッチとcase classで、データの形を型で表せるか

社内にScalaのプロジェクトがあれば、小さな改修からでも関わっておくと、本番での経験として話せます。Javaの側の独立の進め方は[Javaエンジニアがフリーランスになるには](/media/java-how-to/)で解説しています。

### 関数型の言語やほかの言語から来た人

HaskellやOCamlなどの関数型の言語に触れてきた人は、型や関数の考え方にはなじみやすい反面、JVMの運用やJavaのライブラリとの組み合わせで戸惑うことがあります。ScalaのコードはJavaのライブラリを呼ぶ場面も多いため、JVMの基本（メモリやスレッドの見方、ビルドと依存関係の解決）を押さえておくと、本番の問題に対応しやすくなります。

PythonやRubyなどの動的な型の言語から来た人は、型エラーを読む力を早めに身につけておくと、Scalaの現場での立ち上がりが早くなります。

### 社内でScalaを使ってきた人

Scalaの経験が一つの会社に限られる場合、その会社の独自の書き方やライブラリが「Scalaの普通」になっていることがあります。参画先が変わると、使うライブラリや規約が大きく違うことがあるため、主要なライブラリの考え方の違いを、手元で比べておくと安心です。

:::view
Scalaの案件をご紹介していると、Scalaの経験年数が長くなくても、Javaなどで本番の運用や性能の調査を担ってきた方は、参画先から前向きに検討されることがあります。一方で、関数型の用語は知っていても、自分のコードでなぜその書き方を選んだかを説明できないと、評価が分かれやすい傾向があります。面談の前に、実際に書いたコードを一つ選び、判断の理由を言葉にしておくことをおすすめします。
:::

## 独立までの進め方

### 1. Scalaで担った仕事を書き出す

プロジェクトごとに、サービスの概要、Scalaの版、使ったライブラリ、自分が担った範囲（設計、実装、テスト、運用）を書き出します。本番での障害対応や性能の改善に関わった経験があれば、原因と対策まで書いておきます。

### 2. 足りない経験を一つだけ補う

書き出した内容を見て、狙う案件の条件と比べて足りない部分を一つ選びます。全部を一度に埋める必要はありません。

| 足りない部分 | 補い方の例 |
|---|---|
| Scala 3の経験 | 手元の小さなアプリをScala 3で書き直し、2との違いを確かめる |
| エフェクトのライブラリ | 参画先で使われやすいライブラリで、小さなAPIを作ってみる |
| ビルドの知識 | sbtの設定を自分で読み、依存の衝突を直した経験をつくる |
| 運用 | 自分の書いたサービスをコンテナで動かし、ログと監視を整える |

会社員のうちに副業として業務委託を受けて経験を積む方法もありますが、勤務先の就業規則を確かめてから始めてください。注意点は[副業で業務委託を受けるときの記事](/media/fukugyo-gyomu-itaku/)で解説しています。

### 3. スキルシートを用意する

Scalaの経歴は、版とライブラリ、書き方の型、担った判断が伝わるように書きます。書き方は[Scalaのスキルシートの記事](/media/scala-skillsheet/)で解説しています。

### 4. 条件を決めてから案件を探す

稼働日数、リモートの希望、報酬の下限、開始時期を決めてから探します。Scalaの案件は数が多い言語ではないため、条件を広げすぎず、譲れない条件と譲れる条件を分けておくと判断しやすくなります。リモートの傾向は[Scalaのリモート案件の記事](/media/scala-remote/)、探し方の流れは[フリーランスエージェントの使い方](/media/agent-how-to-use/)をご覧ください。

### 5. 面談で判断の理由を話す

Scalaの面談では、言語の機能そのものより、設計の判断が問われやすくなります。よく出るのは次のような話題です。

1. エラーや失敗をどう表し、どの層で扱ったか
2. 非同期・並行の処理をどう書き、どう止めたか
3. ライブラリやバージョンをどう選び、どう更新したか
4. Scalaに慣れていないメンバーとどう書き方をそろえたか

正解を言おうとするより、当時の状況と理由を具体的に話すほうが伝わります。面談全般の準備は[面談でよく聞かれる質問の記事](/media/interview-questions/)にまとめています。

:::caution
Scalaの案件には、少人数のチームで書き方の決まりが文書になっていない現場もあります。参画後に「思っていた書き方と違う」となると、レビューで手戻りが続くことがあります。面談の段階で、使っているライブラリ、コードの規約の有無、レビューの進め方を確かめておきましょう。
:::

## 独立前後の手続きとお金の準備

会社を辞めて独立するときは、年金・健康保険の切り替え、開業届、青色申告の申請などの手続きがあります。開業届の提出期限は、国税庁の案内で「事業を始めた年分の確定申告期限まで」とされています（2026年10月時点）。手続きの全体は[会社員からフリーランスになる手順](/media/quit-company-steps/)、開業届は[開業届の出し方](/media/kaigyo-todoke/)、青色申告は[青色申告の記事](/media/aoiro-shinkoku/)で解説しています。個別の判断は税理士・専門家にご相談ください。

最初の報酬が入るまでには、稼働を始めてから時間がかかります。案件の切れ目に備えて、生活費の数か月分を手元に残しておくと、案件を焦って選ばずに済みます。

契約では、業務の内容、報酬の額、支払期日などが書面またはメールで示されているかを確かめます。フリーランス法で、発注する事業者に明示が求められている事項です。確かめ方は[フリーランス法の取引条件の記事](/media/freelance-act-terms/)で解説しています。

:::view
当社では、ご経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。業務の範囲・報酬・支払期日・契約期間は個別契約に書いてお渡ししています。取り扱う案件は、取引先の会社の実態と支払条件を確かめたものです。独立の時期が決まっていなくても、どの書き方のScalaの案件が多いかなど、気になる点は早めにご相談ください。
:::

:::point
- Scalaの独立では、本番で動かした経験と、チームの書き方に合わせて関数型のコードを読み書きできることが目安
- Java出身はJVMの知識を生かしつつ「Javaのように書かない」こと、他言語出身はJVMの基本を押さえる
- 足りない経験は一つずつ補い、面談では判断の理由を話せるようにする
:::

## よくある質問

### Scalaの実務経験は何年あれば独立できますか？

決まった年数の基準はありません。案件によっては年数を条件にすることもありますが、Scalaで設計からリリースまでを一通り担ったか、本番の問題に対応したかがあわせて見られます。Scalaの経験が短い場合は、Javaなどでのバックエンドの経験と合わせて説明できるようにしておきましょう。

### 個人の学習だけでScalaの案件に入れますか？

学習や個人の開発だけで参画できる案件は多くありません。Scalaの案件は既存のコードに途中から加わる形が多く、本番での経験が重視されやすいためです。社内のScalaのプロジェクトに関わる、Javaの経験を軸にしてScalaも使う案件を選ぶなど、実務での経験を少しずつ積むことをおすすめします。

### Scala 2と3のどちらを学べばよいですか？

これから学ぶなら、Scala 3を中心にしつつ、Scala 2.13との違いを押さえておくのが実用的です。既存の案件にはScala 2で動いているシステムもあるため、2の書き方を読めると参画できる範囲が広がります。版ごとの動きは[Scalaエンジニアの将来性](/media/scala-future/)で整理しています。
