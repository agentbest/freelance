テスト自動化エンジニアは、**テストコードの作成、CIへの組み込み、不安定なテストの改善などで、リモートで働けるフリーランス案件があります**。成果がコードとして残り、変更の確認もプルリクエストで進められるため、QAの仕事の中でも場所に縛られにくい分野です。

ただし、テストを流す相手である検証環境や、テストを動かすCIの実行環境が社内のネットワークの中にある案件では、接続の方法が限られ、自宅から同じ条件でテストを動かせないことがあります。テスト自動化のリモートを左右するのは「**テストを、どこから、どこに向けて動かすか**」です。この記事では、その事情と、離れた場所で失敗を調べる進め方を整理します。

## リモートで進めやすい案件の型

| 案件の型 | 主な仕事 | リモートとの相性 |
|---|---|---|
| E2Eテストの新規の構築 | ツールの選定、共通の部品づくり、主要な画面の流れの自動化 | 進めやすい。検証環境に社外から入れるかで決まる |
| 既存のテストの安定化 | 不安定なテストの原因の調査、待ち方やデータの見直し | 進めやすい。CIの記録をもとに調べられる |
| CI/CDへの組み込み | 実行のタイミングの設計、並列化、結果の通知 | 進めやすい。CIの設定はコードで管理できる |
| APIのテスト | 仕様にもとづく確認、契約のテスト | 進めやすい。画面を介さず、環境の差が出にくい |
| モバイルアプリの自動化 | 実機やエミュレーターでの自動実行 | 場面による。実機を拠点で管理している場合は接続の工夫が要る |
| 性能のテスト | 負荷をかけて応答の時間や限界を測る | 場面による。負荷を出す場所の申請や、時間帯の調整が要る |

求められる技術は[テスト自動化エンジニアの案件で求められるスキル](/media/test-automation-skills/)で、独立の進め方は[テスト自動化エンジニアがフリーランスになるには](/media/test-automation-how-to/)で解説しています。

## 接続や現地が条件になりやすい場面

テスト自動化の案件で出社や指定の環境が条件になるのは、多くの場合、ネットワークの都合です。

- **検証環境が社内のネットワークの中にある**：社外から検証環境に入れず、自宅の端末からテストを流せない
- **CIの実行環境を社内に置いている**：GitHub Actionsでは、自分たちで用意して管理する実行環境（セルフホステッドランナー）を使えます。ハードウェアやOS、ソフトウェアを自由に選べ、社内で使っている機械も使えるため、社内のネットワークの中でテストを動かす構成にしている会社があります。この場合、CIの上では通るのに手元では再現できない失敗が起きやすくなります
- **外部のサービスのテスト環境が接続元を制限している**：決済や認証などの外部のサービスのテスト環境に、許可された接続元からしか入れない
- **実機を拠点で管理している**：モバイルの実機をつないだ機械が拠点にあり、そこからしか動かせない
- **性能のテストの負荷**：負荷をかける場所と時間帯を、取引先やクラウドの事業者に申請する必要がある

同じ案件でも、テストコードを書くのは自宅、実行の確認は取引先の接続の経路を使う、という形はよくあります。手元の端末から、検証環境とCIの両方にどう入るのかを確かめておきましょう。

:::view
テスト自動化の案件をご紹介していると、リモートの可否は使うツールの種類より、検証環境とCIの実行環境がどこにあるかで決まっている傾向があります。これまでどんな環境に向けてテストを動かしてきたか、社内のネットワークの中の環境を扱った経験があるかを伝えていただくと、合う案件を選びやすくなります。当社では、先に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをご案内しています。
:::

## 離れた場所で失敗を調べる進め方

リモートの自動化で時間を取られやすいのが、「CIの上で落ちたテストの原因を、自分の手元で再現できない」問題です。失敗の手がかりをCIの上で残す仕組みを、最初に用意しておくと効率が上がります。

### 失敗の記録をCIで残す

E2Eテストのツールの多くは、失敗したときの記録を残す機能を持っています。たとえばPlaywrightのトレースビューアーは、操作ごとの前後の画面の状態、コンソールの出力、ネットワークの要求と応答（ヘッダーや本文を含む）などを記録し、CIで再実行したテストの記録をダウンロードして開けます。記録を開く公式のWebページは、ブラウザの中だけで読み込み、外部にデータを送らないと説明されています（2026年10月時点の公式ドキュメント）。

### 記録の中身に気をつける

ただし、ネットワークの本文や画面の状態がそのまま残るということは、テスト用のアカウントの情報や、検証環境のデータが記録に入りうるということです。CIに残す記録の保存期間と、見られる人の範囲を決めておくこと、記録をチャットに気軽に貼らないことが大切です。

### 不安定なテストの扱いを決めて共有する

離れた場所にいると、落ちたテストを開発のチームが「また自動テストが落ちている」と無視するようになりがちです。不安定なテストは一覧にして原因の見立てを書き、一時的に外す基準と戻す基準を決めて共有すると、自動テストへの信頼を保てます。

### 実行の時間と成功の割合を見せる

自動化の効果は、離れた相手には見えにくいものです。テストの件数、実行にかかる時間、成功の割合の推移を、ダッシュボードや週ごとの短い報告で示すと、どこまで進んだかを同じ前提で話せます。

## 手動のテストとの分担を文章にする

テスト自動化の案件では、QAのチームや開発のチームと分担して進めることが多くなります。対面なら雑談で済む「どの確認を自動化し、どれを人が見るか」も、リモートでは文章にしておかないとずれが生じます。自動化の対象と対象外、自動テストが落ちたときに誰が最初に見るか、テストの追加は誰が書くかを、短い文書にまとめて共有しておきましょう。手動のテストの側の事情は[QAエンジニアのリモート案件](/media/qa-engineer-remote/)の記事で解説しています。

## 端末・接続・情報管理で確かめること

1. **テストを書く端末**：私物のパソコンを使えるか、貸与の端末や仮想デスクトップに限るか
2. **検証環境とCIへの入り方**：社外からの接続の方法、接続元の制限、手元から実行してよい範囲
3. **テスト用のアカウントの情報**：CIのシークレットなどの仕組みで保管し、コードや手元のファイルに書かないか
4. **失敗の記録**：画面の動画や通信の記録の保存先、保存期間、共有の範囲
5. **テストデータ**：個人情報を含まない作られたデータを使えるか、本番から複製したデータに触れるか
6. **手元のブラウザの状態**：テストで使ったブラウザの保存情報や、ダウンロードしたファイルを作業の後にどう消すか

総務省の「テレワークセキュリティガイドライン」（第5版、2021年5月公表）も、テレワークでの認証の情報や端末の管理の考え方を整理しています。テスト用のアカウントは本物の権限を持つことも多いため、本番のアカウントと同じように扱うつもりでいると安心です。

:::caution
CIの実行時間や、クラウドの実機のサービス、負荷をかけるための計算機の利用料は、テストを増やすほどかさみます。自分の契約で立て替えるのか、取引先の契約で使うのかを、参画前に決めておきましょう。また、作った共通の部品やテストコードの権利が誰に属するかも、契約で確かめておくと安心です。考え方は[著作権の記事](/media/copyright/)で解説しています。
:::

## リモート案件の探し方

### 環境の経験をスキルシートに書く

リモートの案件では、ツールの名前に加えて、どんなCIの上で、どんな環境に向けてテストを動かし、失敗をどう調べてきたかが見られます。実行時間を短くした、不安定なテストを減らした、といった改善は、取り組んだ内容とあわせて書いておくと伝わります。書き方は[テスト自動化エンジニアのスキルシートの書き方](/media/test-automation-skillsheet/)をご覧ください。

### 隣の分野の案件も見る

CIや実行の基盤の整備は、SREや開発の案件と重なることがあります。[SREのリモート案件](/media/sre-remote/)や[TypeScriptエンジニアのリモート案件](/media/typescript-remote/)の記事もあわせて読むと、探せる範囲が広がります。

:::view
テスト自動化の案件の面談では、不安定なテストにどう向き合ったか、落ちたテストを開発のチームにどう信頼してもらったかを聞かれることがよくあります。原因の調べ方と、チームとの決めごとを話せる方は、離れていても任せやすいと受け取られる傾向があります。経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。CIの利用料の負担など気になる点は、ご質問いただければ確認します。
:::

:::point
- テストコードの作成、CIへの組み込み、不安定なテストの改善はリモートで進めやすい
- 検証環境やCIの実行環境が社内のネットワークにある、外部のサービスが接続元を制限している、実機を拠点で管理している案件では接続の条件が付く
- 失敗の記録の残し方と中身の扱い、テスト用のアカウントの保管、利用料の負担を参画前に確かめる
:::

## よくある質問

### 手元でテストが通るのに、CIの上だけで落ちるときはどうすればよいですか？

実行環境の違い（ブラウザの版、画面の大きさ、ネットワークの速さ、データの状態）が原因のことが多くあります。CIの上で失敗の記録を残す設定にし、手元とCIの環境の差を一つずつ確かめるのが近道です。CIの実行環境が社内にある場合は、その環境に入る方法を取引先と決めておきましょう。

### 自宅から検証環境に入れない案件は、リモートでは無理ですか？

取引先が用意した接続の経路や仮想デスクトップを使えば、自宅から作業できることがあります。テストコードを書く作業と、実行の確認の作業で条件が違うこともあるため、作業ごとに確かめておくことをおすすめします。

### テスト自動化の案件は、週に数日の稼働でも受けられますか？

受けられる案件はあります。ただし、CIで落ちたテストへの対応が遅れると開発の妨げになるため、稼働しない日の扱いや、急ぎの対応の連絡の取り方を決めておく必要があります。
