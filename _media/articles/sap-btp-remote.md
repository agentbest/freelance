SAP BTPエンジニアのフリーランスは、**アプリの開発、連携フローの作成、APIの設定、テストなど、クラウドの上で完結する仕事が多く、リモートと相性のよい職種です**。開発の道具も実行の環境もクラウドにあるため、決められた端末と接続の手段があれば、手元から作業を進められる場面が多くあります。

一方で、**オンプレミスのシステムとの接続の設定、本番の環境での強い権限を使う作業、業務部門との要件定義や受け入れのテスト**では、出社や決まった端末での作業を求められることがあります。この記事では、BTPの仕事をリモートとの相性で分け、信頼を得る進め方と、案件の探し方・確認点を整理します。

## リモートで進めやすい仕事・進めにくい仕事

| 仕事 | リモートとの相性 | 理由 |
|---|---|---|
| CAPでのサービス開発、Fioriの画面の開発 | 進めやすい | 開発の環境と実行の環境がクラウドにある |
| 連携フローの作成と単体のテスト | 進めやすい | 設定の画面とテストの道具がクラウドにある |
| APIの公開・監視の設定 | 進めやすい | 管理の画面から設定できる |
| SAP Buildでの試作 | 進めやすい | 画面を共有しながら利用部門と確かめられる |
| オンプレミスとの接続の設定 | 進めにくいことがある | 社内のネットワークに置く機器や設定に触れる |
| 本番の環境での作業 | 条件付き | 強い権限を使うため、場所や端末が決められることがある |
| 業務部門との要件定義・受け入れのテスト | 案件次第 | 対面での説明や操作の立ち会いを求められることがある |

### オンプレミスとの接続がリモートの可否を分ける

BTPの上のアプリや連携は、多くの場合、社内のS/4HANAや旧来のSAP ERPとつながります。SAP Learningでは、Cloud Connectorや宛先（destination）の設定を使ってクラウドとオンプレミスの接続を構成することが示されています。Cloud Connectorは社内のネットワークの側に置くため、その設定や障害の調査では、社内の環境に入れる端末や、インフラ・Basisの担当との作業が必要になります。

接続の部分を誰が担うかで、リモートで進められる範囲は変わります。接続はBasisやインフラの担当が持ち、自分はBTPの上の開発と連携に専念する案件なら、リモートの比率は高くなりやすい傾向があります。Basisの側のリモートの傾向は[SAP Basisエンジニアのリモート案件の記事](/media/sap-basis-remote/)で解説しています。

### 本番の権限と業務データの扱い

本番の環境では、取引先や従業員の情報など、業務のデータに触れることがあります。そのため、作業は貸与された端末に限る、作業の記録を残す、特定の場所からだけ接続できる、といった条件が付くことがあります。総務省のテレワークセキュリティガイドライン（第5版、2021年5月）でも、端末やネットワーク、ルールの面から安全に在宅で働くための対策が整理されています。案件ごとのルールに従うことが前提になります。

:::view
BTPの案件紹介の現場では、「フルリモート可」とあっても、立ち上げの時期や受け入れのテストの時期だけは出社が求められる案件をよく見ます。リモートで評価されやすいのは、設計の判断や作業の結果を文章で残し、つなぐ先の担当者とのやり取りを自分から進められる方です。当社では、先に稼働日数・リモートの希望・ご希望の金額を伺い、その条件に合う案件だけをご案内しています。出社できる頻度の上限も、早めにお知らせいただくことをおすすめします。
:::

## リモートで信頼を得る進め方

### 判断の理由を文章で残す

BTPの仕事では、「標準で済ませるか作り込むか」「同期でつなぐかイベントでつなぐか」といった判断が続きます。対面なら会話で済む説明も、リモートでは残らないと伝わりません。判断の理由と、選ばなかった案を短く書き残しておくと、後から参加した人や業務部門にも説明しやすくなります。

### つなぐ先の担当者との段取りを自分から組む

連携のテストは、相手先のシステムの担当者と時間を合わせて進めることが多くなります。誰が、いつ、どのデータで試すかを先に決めておかないと、リモートでは待ち時間が増えます。テストの計画を自分から出せる人は、リモートでも進行を任されやすくなります。

### 時差のあるチームとの働き方

BTPの案件では、海外の開発チームやSAPの側の窓口とやり取りすることがあります。会議の時間帯が早朝や夜にかかることもあるため、稼働の時間帯をどこまで動かせるかを先に決めておきましょう。英語を使う場面の考え方は[英語を使うプロジェクトの記事](/media/eigo-project/)が参考になります。

## 案件の局面によってリモートの比率は変わる

同じBTPの案件でも、プロジェクトのどの局面かで、出社の求められ方は変わります。

| 局面 | リモートの比率の傾向 | 出社が求められやすい場面 |
|---|---|---|
| 立ち上げ・要件定義 | 低めになりやすい | 業務部門への聞き取り、現行の業務の見学 |
| 設計・開発 | 高めになりやすい | 設計のレビューを対面で行う方針の場合 |
| 結合・受け入れのテスト | 案件次第 | 利用部門の操作の立ち会い、不具合のその場での確認 |
| 本番の切り替え | 案件次第 | 夜間・休日の作業、関係者が集まる切り替えの当日 |
| 保守・改善 | 高めになりやすい | 障害の調査で社内の環境に入る必要がある場合 |

参画の時期がどの局面にあたるかで、最初の数か月の働き方は大きく変わります。たとえば、要件定義から入る案件では、最初の1〜2か月だけ出社が多く、開発に入るとリモートが中心になる、といった形もあります。面談では、今の局面と、今後の予定の局面をあわせて聞いておくと、働き方の見通しが立てやすくなります。

保守・改善の案件は、作業がクラウドの上で完結しやすく、リモートの比率が高くなりやすい一方、障害の対応で稼働の時間外に連絡が来ることがあります。連絡を受ける時間帯と、その時間の精算の扱いを先に決めておきましょう。

## 案件の探し方と確認点

BTPの案件は、案件票の「リモート可」の一言だけでは中身が分かりません。面談や事前のやり取りで、次の点を確かめておきましょう。

1. **担当の範囲**：開発・連携だけか、オンプレミスとの接続や本番の作業も含むか
2. **出社の条件**：頻度、どの時期に出社が増えるか、出社先の場所
3. **端末と接続**：貸与の端末か、私物の端末を使えるか、接続の手段は何か
4. **稼働の時間帯**：海外のチームとの会議、本番の切り替えの時間帯
5. **テストの進め方**：受け入れのテストに立ち会いが必要か

案件票の読み方は[案件票の読み方の記事](/media/project-info-read/)、常駐が前提の案件の考え方は[常駐の記事](/media/jochu/)、フルリモートの案件の全体的な傾向は[フルリモートの記事](/media/full-remote/)で解説しています。

:::caution
「リモート中心」と書かれた案件でも、本番の切り替えや障害の対応で、急に出社や夜間の作業を求められることがあります。急な出社の交通費や、夜間の作業の時間の扱いが契約にどう書かれているかを、参画前に確かめておきましょう。
:::

## 契約の書面で確かめること

リモートの条件は、口頭の説明だけで済ませず、契約の書面で確かめることが大切です。フリーランス法では、発注側は業務を委託したときに、業務の内容、報酬の額、支払期日に加え、役務の提供を受ける場所などを、書面またはメールなどで明示する必要があります（公正取引委員会の案内による）。取引条件の明示の考え方は[取引条件の明示の記事](/media/freelance-act-terms/)で解説しています。

:::view
当社がご案内する案件では、業務の範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。また、取引先の会社の実態と支払条件を確かめた案件を扱っています。出社の頻度や貸与の端末の扱いなど、リモートの条件で気になる点は、ご質問いただければ確認します。
:::

:::point
- BTPの開発・連携・API・ローコードの仕事はクラウドの上で完結しやすく、リモートと相性がよい
- オンプレミスとの接続、本番の権限、業務部門との要件定義では出社や決まった端末が求められることがある
- 担当の範囲、出社の条件、端末、時間帯、テストの進め方を参画前に確かめる
:::

## よくある質問

### SAP BTPの案件はフルリモートで受けられますか？

開発や連携が中心の案件では、フルリモートで進むものもあります。ただ、立ち上げや受け入れのテスト、本番の切り替えの時期に出社が求められることがあるため、出社の条件を時期ごとに確かめておくことをおすすめします。

### 自宅のパソコンで作業できますか？

案件によります。業務のデータに触れる案件では、貸与の端末に限るとされることが多くなります。私物の端末を使える場合も、ウイルス対策やOSの更新、画面の覗き見の対策など、案件のルールに沿った準備が必要です。

### 週2〜3日のリモート案件はありますか？

連携の保守や小さな拡張の開発など、稼働日数を抑えた案件が出ることもあります。ただ、相手先との連携のテストや障害の対応で、決まった日に稼働を求められることがあります。稼働日数を抑える場合は、稼働日以外に障害の連絡が来たときの扱いを先に決めておきましょう。
