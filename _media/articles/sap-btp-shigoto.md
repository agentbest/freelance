SAP BTPエンジニアのフリーランス案件の仕事は、**S/4HANAなどのSAPのシステムの外側で、アプリを作り、システムどうしをつなぎ、動き続けるように面倒を見ること**です。ただし、拡張アプリの開発なのか、連携の構築なのか、旧環境からの移行なのかで、1日の時間の使い方も、話す相手も、手元に残る成果物も大きく変わります。

この記事では、BTPの案件を5つの種類に分け、それぞれの1日と1か月の流れ、関わる相手、成果物を整理します。求められるスキルの中身は[SAP BTPエンジニアのスキルの記事](/media/sap-btp-skills/)、報酬の決まり方は[SAP BTPエンジニアの報酬の記事](/media/sap-btp-rate/)で扱っているので、ここでは「参画したら実際に何をしているか」に絞ります。

## 仕事の中身は「領域」と「局面」で決まる

案件票に「SAP BTP」と書かれていても、担う仕事は案件ごとに違います。違いを生むのは主に次の2つです。

- **領域**：拡張アプリの開発、システム連携、ローコード・自動化、AIの組み込み、アカウントや権限の管理のどれを担うか
- **局面**：新しく作るのか、古い仕組みを移すのか、動いているものを保守・改善するのか

この2つを掛け合わせると、フリーランスのBTP案件はおおむね次の5種類に分けられます。

| 案件の種類 | 主な相手 | 時間を多く使う仕事 |
|---|---|---|
| 拡張アプリの開発 | 業務コンサル、利用部門、開発チーム | データのモデルとサービスの実装、画面、テスト |
| システム連携の構築 | つなぐ先のシステムの担当、Basis、業務コンサル | 連携フローの設計と作成、相手先との結合テスト |
| 旧環境からの移行 | 情報システム部門、既存の連携の担当、運用の担当 | 現状の棚卸し、方式の見直し、作り直しと切り替え |
| ローコード・自動化の支援 | 利用部門、情報システム部門 | アプリやワークフローの作成、作り方の基準づくり |
| 保守・改善 | 運用の担当、問い合わせの窓口、利用部門 | エラーの調査と再処理、小さな改修、運用の改善 |

以下では、それぞれの1日と1か月の流れを典型的な例として紹介します。時間の配分は案件ごとに違うため、目安として読んでください。

## 拡張アプリの開発の仕事

### 1日の流れ（例）

朝は開発チームの短い打ち合わせで、前日の進み具合と詰まっている点を共有します。午前は、SAPのCloud Application Programming Model（CAP）でデータのモデルやサービスを実装する時間に充てることが多くなります。午後は業務コンサルや利用部門と、画面の項目や承認の流れを確かめる打ち合わせが入ります。夕方は、S/4HANAの標準のAPIから想定どおりのデータが取れるかを試したり、レビューで受けた指摘を直したりします。

CAPの公式の手引きでは、最小の準備はNode.jsで、Javaは追加の準備として案内されています。デプロイの先としてはCloud FoundryやKymaへの手順が示されています（2026年10月時点）。案件ではこのどちらかの言語と環境に合わせて開発します。

### 1か月の流れ（例）

- **月初**：その月に作る機能を決め、要件の不明点を業務コンサルに上げる
- **毎週**：開発チームの定例で進み具合をそろえ、利用部門に画面を見せて確かめてもらう
- **月の半ば**：検証の環境にデプロイし、つなぐ先のデータで結合のテストを行う
- **月末**：テストの結果と残っている課題をまとめ、次の月の計画に反映する

### 成果物

データのモデルとAPIの設計書、サービスと画面のソースコード、テストの仕様と結果、デプロイの手順書、利用者向けの操作の説明などです。画面をFiori elementsの標準の型で済ませたのか、作り込んだのかは、後の保守の負担を左右するため、判断の理由を設計書に残すことが求められます。

## システム連携の構築の仕事

### 1日の流れ（例）

午前は、Integration Suiteで連携フローを作ったり、データの変換のルールを実装したりします。午後は、つなぐ先のシステムの担当者と、受け渡すデータの項目やタイミング、エラーが起きたときの扱いを詰めます。結合テストの時期には、相手先と時間を合わせてデータを流し、どちらの側で止まったのかを切り分ける作業で1日が終わることもあります。

SAP Learningでは、Integration Suiteの機能として、Cloud Integration、API Management、Event Mesh、Integration Advisor、Migration Assessmentなどが挙げられています（2026年10月時点）。連携の案件では、これらのうちどれを使うかが、仕事の中身を決めます。

### 1か月の流れ（例）

- **月初**：担当する連携の一覧と優先順位を確かめ、相手先とテストの日程を決める
- **毎週**：連携ごとの進み具合と、相手先の準備の状況をそろえる
- **月の半ば**：結合テストを行い、変換の誤りやエラー時の動きを直す
- **月末**：本番に出す連携の判定と、運用の担当への引き継ぎの準備

### 成果物

連携の一覧、連携ごとのインターフェースの仕様書、データの変換の定義、エラー時の再処理の手順、APIを公開する場合は認証と利用の制限の設定の記録などです。**正常に流れるフローより、止まったときの手順書**のほうが、運用の担当にとっては大切な成果物になります。

:::view
BTPの案件をご紹介していると、同じ「BTPエンジニア」の募集でも、開発の案件と連携の案件で1日の過ごし方がまったく違うことに、参画してから気づく方がいます。開発の経験が長い方は、連携の案件で相手先との日程の調整やテストの立ち会いに想像以上に時間がかかることに戸惑いやすい傾向があります。応募の段階で、つなぐ先の数と、相手先の担当とのやり取りを誰が担うかを聞いておくことをおすすめします。
:::

## 旧環境からの移行の仕事

旧来の連携基盤や、BTPの古い実行環境で動いている仕組みを、新しい環境に作り直す案件です。期限のある移行が背景にあることが多く、その動きは[SAP BTPエンジニアの将来性の記事](/media/sap-btp-future/)で整理しています。

### 前半の数か月

最初は**作るより読む**のが仕事です。動いている連携やアプリを一覧にし、設定や処理の中身を読み解き、使われていないものを見つけます。そのうえで、そのまま移すもの、作り直すもの、廃止するものに分けます。資料が残っていない仕組みでは、昔の担当者への聞き取りに時間を使うこともあります。

### 後半の数か月

方式を決めた後は、新しい環境での作り直しと検証、段階的な切り替えに移ります。切り替えの当日は業務を止めない時間帯に作業することが多く、夜間や休日にかかる場合もあります。問題が起きたときに元に戻す手順も、切り替えの前に用意します。

### 成果物

現状の棚卸しの一覧、移行の方式の判断の記録、新旧の対応表、切り替えの計画と手順、戻し方の手順、移行後の確認の結果などです。

## ローコード・自動化の支援の仕事

SAP Buildのツールを使い、利用部門の業務アプリやワークフロー、業務のポータルを作る案件です。仕事の中身は、**自分が作る立場か、利用部門が作るのを支える立場か**で大きく分かれます。

自分が作る立場なら、利用部門の担当と画面を見ながら試作し、直していく時間が中心になります。支える立場なら、作り方の基準、使ってよいデータと権限のルール、作ったものを誰が保守するかの決まりを整え、利用部門からの相談に応じる時間が増えます。1か月の単位では、新しく作られたアプリの確認や、ルールの見直しが定期的な仕事になります。

成果物は、作成したアプリやワークフロー、作り方の基準、権限とデータのルール、利用部門向けの手引きなどです。

## 保守・改善の仕事

本番で動いている拡張アプリや連携を預かる案件です。毎朝、失敗したメッセージやエラーの記録を確かめ、原因を切り分けて再処理するところから1日が始まります。その後は、利用部門からの問い合わせへの回答や、小さな改修の対応に時間を使います。

1か月の単位では、エラーの件数や問い合わせの傾向をまとめ、再発を防ぐ改善の案を出すことが求められます。SAPやBTPのサービスの更新の情報を追い、影響があるものを洗い出すのも保守の仕事に含まれることがあります。新規の開発と保守の働き方の違いは[新規開発と保守の案件の違い](/media/shinki-vs-hoshu/)も参考になります。

## どの案件にも共通する仕事

種類が違っても、次の仕事はほぼすべてのBTP案件にあります。

1. **権限と接続の確認**：利用者のロール、つなぐ先への宛先の設定、オンプレミスとの接続が想定どおりかを確かめる
2. **つなぐ先のデータの理解**：S/4HANAなどのどのデータを読み書きし、業務のどこに影響するかを押さえる
3. **判断の記録**：標準で済ませたのか作り込んだのか、なぜその方式にしたのかを残す
4. **環境ごとの配布**：開発・検証・本番の環境に、決まった手順で載せる

オンプレミスとの接続の設定は、Basisやインフラの担当と分担することが多い部分です。分担の考え方は[SAP Basisエンジニアの仕事内容](/media/sap-basis-shigoto/)、S/4HANAの中の拡張を担うABAPの側の仕事は[SAP ABAPエンジニアの仕事内容](/media/sap-abap-shigoto/)で解説しています。

:::caution
BTPの案件は、開発・連携・運用の境目があいまいなまま始まることがあります。作ったアプリの問い合わせ対応や、利用部門が作ったアプリの手直しが、少しずつ自分の仕事に加わることもあります。引き受ける前に契約の業務範囲に入るかを確かめ、外れる場合は条件の見直しを相談しましょう。考え方は[作業範囲が広がったときの契約の扱い](/media/scope-change/)で解説しています。
:::

## 関わる相手と、その相手に出すもの

BTPエンジニアの1日は、技術の側と業務の側の両方とのやり取りで組み立てられています。

| 相手 | BTPエンジニアが出すもの | 頻度の目安 |
|---|---|---|
| 業務コンサル・利用部門 | 画面や連携の動きの確認、仕様の確認事項 | 週次、随時 |
| つなぐ先のシステムの担当 | インターフェースの仕様、テストの段取り | 週次、テストの時期は毎日 |
| Basis・インフラの担当 | 接続や権限の設定の依頼 | 随時 |
| 開発チームのリーダー・PM | 進み具合、課題、見積もり | 毎日〜週次 |
| 運用の担当 | 手順書、エラー時の対応の引き継ぎ | 本番の前、改修のたび |

働く場所については、開発や連携の作成はリモートで進めやすい一方、要件定義や受け入れのテスト、本番の切り替えでは出社を求められることがあります。詳しくは[SAP BTPエンジニアのリモート案件の記事](/media/sap-btp-remote/)をご覧ください。

:::view
当社では、案件をご案内する前に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。BTPの案件は、領域と局面によって毎日の仕事が変わるため、「これまで多く時間を使ってきた仕事」と「避けたい働き方」をあわせてお伝えいただくと、案件を照らし合わせやすくなります。つなぐ先の数や本番の切り替えの時間帯など、案件票に書かれていない働き方の点は、ご質問いただければ確認します。
:::

:::point
- BTPの仕事は、拡張開発・連携・移行・ローコードの支援・保守改善の5種類で中身が変わる
- 開発はデータのモデルと画面、連携は相手先とのテスト、移行は棚卸しと切り替えに時間を使う
- どの案件でも、権限と接続の確認、つなぐ先のデータの理解、判断の記録が共通の仕事になる
:::

## よくある質問

### BTPエンジニアは、コードを書く時間が長い仕事ですか？

拡張アプリの開発の案件では、実装の時間が長くなります。一方、連携や移行の案件では、仕様の確認や相手先とのテスト、既存の仕組みの読み解きに多くの時間を使います。どの種類の案件かで、手を動かす時間の割合は大きく変わります。

### AIの組み込みの案件では、どんな仕事をしますか？

AIの機能を業務アプリや連携に組み込む案件では、どの業務データをAIに渡してよいか、AIの結果を誰が確かめるかを決める仕事の比重が大きくなります。開発の流れは拡張アプリの開発に近く、検証から始まることが多い点が特徴です。動向は[SAP BTPエンジニアの将来性の記事](/media/sap-btp-future/)にまとめています。

### 参画して最初の1か月は何をすることが多いですか？

環境の構成と権限の確認、つなぐ先のシステムと担当者の把握、既存の設計書や連携の一覧の読み込みから始めるのが一般的です。初月の進め方は[SAP BTPエンジニアの参画初月にやること](/media/sap-btp-first-month/)で解説します。
