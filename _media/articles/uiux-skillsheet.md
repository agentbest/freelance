UI/UXデザイナーのスキルシートは、作った画面やサービスを並べるよりも、**「誰のどんな課題を、どう調べ、設計で何を変え、どう確かめたか」**を書くと伝わります。読み手は、見た目の質と同じくらい、使いやすさの判断を任せられるかを見ているからです。

この記事では、UI/UXデザイナーならではの書き方のポイントを、架空の記入例とあわせて紹介します。全体の構成は[スキルシートの書き方の基本](/media/skillsheet-basics/)、求められるスキルは[UI/UXデザイナーのスキルの記事](/media/uiux-skills/)をご覧ください。

## UI/UXデザイナーのシートが伝わりにくくなる理由

UI/UXデザイナーの経歴は、ツールや手法の名前が並びやすい傾向があります。「ユーザーインタビュー」「ペルソナ」「カスタマージャーニーマップ」「ワイヤーフレーム」「プロトタイプ」と並べても、どの程度自分で担ったのかは読み取れません。

また、担当した画面の多くは守秘の対象で、ポートフォリオに載せられないことがよくあります。画面を見せられない分、**どの工程を、どの深さで担ったか**を文章で伝えることが、シートの中心になります。

読み手が知りたいのは、主に次のことです。

- どんなサービスや業務システムで、誰が使うものだったか
- 調査から評価までのうち、どの工程を担い、どれを自分で計画したか
- 調べた結果を、設計のどこに反映したか
- 作ったものを、どう確かめたか

## プロジェクトの概要は「対象」と「利用者」を先に書く

UI/UXデザイナーの案件は、対象が一般向けのサービスか、社内の業務システムかで求められる経験が大きく変わります。サービス名の代わりに、次の項目を書きます。

| 項目 | 記入例（架空） |
|---|---|
| 対象 | 物流会社の配送管理システム（社内向け）の刷新 |
| 利用者 | 配車担当者と営業所の事務担当者。主にPCで、1日の大半この画面を使う |
| 規模 | 主要な画面が数十、利用者の権限は3種類 |
| 体制 | PdM1名、デザイナー2名（自分を含む）、開発チーム10名程度 |
| 担当 | 配車の画面群の調査から評価までを担当。デザインシステムの整備にも参加 |
| 期間・稼働 | 1年2か月・週4日 |

**利用者**の行は特に大切です。利用者がどんな環境で、どれくらいの頻度で使うかが分かると、読み手は設計の難しさを想像できます。

## 担当工程は「主導」と「参加」を分けて示す

UI/UXデザイナーのシートで差がつくのは、工程ごとの関わりの深さです。表で示すと、面談の前に読み手が把握しやすくなります。

| 工程 | 関わり方（架空） |
|---|---|
| 調査（聞き取り・観察） | 主導：調査の計画、対象者の条件づくり、実施、結果のまとめ |
| 情報設計・画面遷移 | 主導 |
| 画面のデザイン | 主導（もう1名のデザイナーと分担） |
| 試作による評価 | 主導：テストの課題づくりと実施 |
| デザインシステム | 参加：部品の追加と使い方の説明を担当 |
| 実装の確認 | 参加：開発のレビューに同席し、ずれを指摘 |

「主導」は自分で計画して進めたもの、「参加」は他の人の計画の中で担当したもの、と使い分けると、面談での説明と食い違いにくくなります。

## 本文は「課題・調べたこと・変えたこと・確かめた結果」で書く

プロジェクトの本文は、手法の一覧ではなく、判断の流れで書きます。

### 記入例（架空）：手法の一覧から判断の流れへ

> **書き直す前**：ユーザーインタビュー、業務観察、ペルソナ作成、ワイヤーフレーム作成、プロトタイプ作成、ユーザビリティテストを実施

> **書き直した後**
> **課題**：配車の登録に時間がかかり、入力の誤りによる配送のやり直しが起きていた
> **調べたこと**：営業所で配車担当者の作業を観察したところ、画面を行き来しながら紙の一覧と照らし合わせていることが分かった
> **変えたこと**：照らし合わせに使う情報を一つの画面にまとめ、入力の途中で誤りを知らせる設計に変更した
> **確かめた結果**：試作を使って配車担当者にテストを行い、迷う箇所を直したうえで開発に渡した。リリース後、入力の誤りに関する問い合わせが減った

これは書き方を示すための架空の例です。対象や内容は、ご自身の経験に置き換えてください。

書き直した後の例では、画面の外の行動を観察して設計を変えたことが読み取れます。UI/UXデザイナーの面談では、このように**調べた結果で設計を変えた経験**がよく聞かれます。直近の1〜2件は、この形で書いておくことをおすすめします。

:::view
案件をご紹介する立場から見ると、UI/UXデザイナーの経歴で提案が進みやすいのは、利用者と担当工程がはっきり書かれているシートです。一般向けのサービスの改善と業務システムの刷新では、合う方が違うためです。経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。守秘の範囲で書ける内容に置き換えておくと、提案先を広げやすくなります。
:::

## デザインシステムの経験の書き方

デザインシステムに関わった経験は、「デザインシステム構築」と一言で書かず、次の点を分けて書きます。

- 新しく作ったのか、既存のものを引き継いで育てたのか
- 何を担当したか（部品の設計、色や文字の決まり、使い方の説明、開発との対応づけ）
- 何チームくらいで使われていたか、追加や変更をどう決めていたか

作る経験と運用する経験は、案件で求められる場面が違います。どちらを担ったかが分かるように書きましょう。

## 成果の数字を書くときの注意

UI/UXデザインの成果は、利用の数字で語りたくなります。ただ、実数は多くの場合社外に出せません。数字を伏せる場合は、次のように書きます。

- **見ていた指標の名前は書く**：「入力の完了率」「問い合わせの件数」「操作にかかる時間」など
- **値は方向で示す**：「改善した」「減った」など
- **測り方を添える**：テストで確かめたのか、リリース後の数字なのか

数字の変化は、デザインだけでなく、機能の追加や業務の変更、季節の要因でも動きます。自分の設計だけの成果として書くと、面談で切り分け方を聞かれたときに説明が苦しくなります。書いてよい範囲は[スキルシートに書いてよいこと・いけないことの記事](/media/confidentiality-in-skillsheet/)で解説しています。

:::caution
発注先の画面のキャプチャーや、社内資料の図をそのままシートやポートフォリオに貼るのは避けます。公開の了承を得ていない画面は、守秘の対象になっていることが多くあります。見せたい場合は、構造だけを書き直した図や、文章での説明に置き換えましょう。
:::

## スキルの欄に書くこと

スキルの欄には、ツールの名前と年数だけでなく、使い方の深さが分かる情報を添えます。

| 欄 | 記入例（架空） |
|---|---|
| デザインツール | 画面設計と試作に5年。部品と変数を使ったデータの整理、開発への受け渡しまで |
| 調査の手法 | 聞き取りと業務の観察を計画から実施。アンケートの設計は参加の経験のみ |
| 評価の手法 | ユーザビリティテストの計画と実施、専門家としての評価（ヒューリスティック評価） |
| アクセシビリティ | WCAG 2.2の達成基準を参照した設計とチェックの経験 |
| 実装の知識 | HTMLとCSSの基本、フロントエンドの部品の考え方を理解。コードの記述は補助的に |

アクセシビリティの欄は、「対応経験あり」とだけ書かず、参照した基準と、何をどう確かめたかを書くと伝わります。WCAGはW3Cが公開しているウェブコンテンツのアクセシビリティの指針で、2026年10月時点の最新版は2.2です。

## ポートフォリオとシートの役割を分ける

UI/UXデザイナーは、シートとポートフォリオの両方を求められることがあります。両方に同じことを書くより、役割を分けるほうが読み手の負担が減ります。

- **スキルシート**：経歴の全体、担当工程、期間と稼働、使える手法とツール
- **ポートフォリオ**：公開できる範囲の事例を、判断の流れが分かる形で数件

公開できる事例が少ない場合は、自主的に作った事例を加える方法もあります。その場合は、自主制作であることを明記しましょう。考え方は[ポートフォリオの記事](/media/portfolio-github/)にまとめています。

:::view
面談まで進んだUI/UXデザイナーの方を見ていると、評価が安定しやすいのは、うまくいった設計だけでなく、テストで問題が見つかって作り直した経験も話せる方です。シートには成功した事例を並べがちですが、評価の結果を受けて方針を変えた経験は、使いやすさの判断を任せられるかを示す材料になります。参画のたびにシートを更新しておくことをおすすめします。
:::

:::point
- プロジェクトの欄には、サービス名の代わりに「対象」「利用者」「規模」「体制」「担当」を書く
- 担当工程は「主導」と「参加」を分けて表で示す
- 本文は手法の一覧ではなく、「課題・調べたこと・変えたこと・確かめた結果」の流れで書く
- 画面のキャプチャーは了承なく使わず、構造の説明や文章に置き換える
:::

## よくある質問

### 担当した画面をほとんど公開できない場合はどうすればよいですか？

対象、利用者、担当工程、判断の流れを文章で書けば、画面を見せなくても経験は伝わります。画面の構造だけを書き直した簡単な図を添える方法もありますが、元の画面が特定できない形にしましょう。シートの更新の時期は[スキルシートの更新の記事](/media/skillsheet-update/)が参考になります。

### 調査を担当していない案件も書いてよいですか？

書いてかまいません。担当工程の表で、調査は「担当外」または「結果を受け取って設計に反映」と書けば、読み手が関わりの深さを正しく理解できます。担当していない工程まで担ったように書くと、面談で説明がずれて信頼を損ないます。

### Webデザイナーとしての経験はどう書けばよいですか？

見た目の制作の経験は、デザインの基礎として評価されます。UI/UXデザイナーとして応募するときは、その中で利用者の行動を見て直した経験や、画面の構造を決めた経験を前に出すと伝わりやすくなります。独立の進め方は[UI/UXデザイナーがフリーランスになるには](/media/uiux-how-to/)をご覧ください。
