Javaエンジニアのフリーランス案件の仕事は、**設計書とコードを行き来しながら、チームの決まりに沿って機能を作り、テストで確かめ、リリースまで見届けること**が中心です。ただし、業務システムを一から作る案件と、動いているWebサービスに機能を足す案件とでは、1日の時間の使い方も、話す相手も、手元に残る成果物も大きく違います。

この記事では、Javaのフリーランス案件を5つの種類に分け、それぞれの1日と1か月の流れ、関わる相手、成果物を整理します。求められる技術の中身は[Javaエンジニアのスキルの記事](/media/java-skills/)、報酬の決まり方は[Javaの報酬の記事](/media/java-rate/)で扱っているので、ここでは「参画したら毎日何をしているか」に絞ります。

## Javaの案件は「システムの種類」と「局面」で働き方が決まる

Javaは、金融・保険・公共・製造などの業務システムから、自社のWebサービスまで幅広く使われています。同じ「Java／Spring Bootの開発」と書かれた案件でも、働き方を分けるのは次の2つです。

- **システムの種類**：止められない業務システムか、短い周期で改善を重ねるWebサービスか
- **局面**：新しく作っている最中か、動いているものを直しているか、古い環境から新しい環境へ移しているか

この2つを掛け合わせると、Javaのフリーランス案件はおおむね次の5種類に分けられます。

| 案件の種類 | 主な相手 | 時間を多く使う仕事 |
|---|---|---|
| 業務システムの新規開発・刷新 | 設計のリーダー、同じチームの開発者、発注元の業務担当者 | 設計書の作成・レビュー、実装、工程ごとのテスト |
| 既存システムの保守・改修 | 運用担当者、業務部門、前任の開発者 | 影響調査、小さな改修、問い合わせ対応、定期リリース |
| Webサービス・自社サービスの開発 | プロダクトの担当者、フロントエンドの開発者、SRE | 機能の実装、API設計、レビュー、短い周期のリリース |
| バージョン移行・モダナイズ | 基盤のリーダー、各機能の担当者、運用担当者 | 依存の洗い出し、修正、回帰テスト、切り替えの計画 |
| バッチ・基盤・共通部品 | アーキテクト、運用担当者、各チームの開発者 | 処理の設計、性能の確認、共通部品の整備と展開 |

以下では、それぞれの1日と1か月の流れを典型的な例として紹介します。時間の配分は現場によって違うため、目安として読んでください。

## 業務システムの新規開発・刷新の仕事

受託開発の会社が元請けとなり、金融や公共などの発注元のシステムを作る案件です。ウォーターフォール型で工程が区切られていることが多く、参画する工程によって仕事が変わります。

### 1日の流れ（例）

朝はチームの短い打ち合わせで、担当する機能の進み具合と詰まっている点を共有します。設計の工程なら、業務のルールを設計書に落とし、リーダーのレビューを受けて直す作業が午前から午後まで続きます。実装の工程なら、設計書に沿ってコードを書き、単体テストを添えてプルリクエストを出し、レビューの指摘に対応します。夕方は、仕様で分からない点を発注元の業務担当者に確認し、翌日の作業を整理して終わります。

### 1か月の流れ（例）

- **月初**：工程の計画に沿って、担当する機能と期限を確かめる
- **毎週**：進捗の報告と、設計やコードのレビュー会。仕様の確認事項を一覧にして発注元と合わせる
- **月の半ば**：工程の区切りに合わせて、設計書の完成や単体テストの完了を報告する
- **月末**：次の工程に進む判定の材料として、成果物とテストの結果をそろえる。稼働時間を締めて報告する

### 成果物

基本設計書・詳細設計書、テーブルやAPIの定義、ソースコード、単体テストのコードと結果、テスト仕様書と結果の記録、レビューの記録などです。成果物の形式はプロジェクトで決まっていることがほとんどで、自分の流儀より**現場の型に合わせる**ことが求められます。

## 既存システムの保守・改修の仕事

すでに動いている業務システムを、法改正や業務の変更に合わせて直していく案件です。Javaの案件では数が多く、長く続きやすい種類です。

### 1日の流れ（例）

朝は、前日に届いた業務部門からの問い合わせや障害の報告を確かめます。午前中は、改修の依頼に対する影響調査が中心です。該当する画面やバッチのコードを追い、関係するテーブルや他のシステムとの連携を洗い出し、工数の見積もりを出します。午後は、決まった改修の実装とテスト、月次のリリースに向けた資料づくりに使います。古いコードを読み、前任者の意図をくみ取る時間が多いのが特徴です。

### 1か月の流れ（例）

- **月初**：当月のリリース対象を確定し、改修の優先順位を業務部門と合わせる
- **毎週**：改修の進捗と問い合わせの状況を報告する。本番で起きた不具合の原因と対策をまとめる
- **月の半ば**：リリース対象の改修を終え、回帰テストを回す
- **月末**：リリースの手順と切り戻しの手順を整え、リリースに立ち会う。夜間や休日になる現場もある

### 成果物

影響調査の結果、見積もり、改修した設計書とコード、テストの記録、リリース手順書、問い合わせへの回答の記録などです。小さな成果物を毎月積み重ねる仕事で、**変更の履歴を残す丁寧さ**が評価につながります。

:::view
Javaの案件をご紹介していると、同じ「Spring Bootの開発」でも、新規開発と保守・改修で毎日の仕事が大きく違うことに、参画してから気づく方がいます。新しく作る経験が長い方は、保守の案件で古いコードの調査に時間の多くを使うことに戸惑いやすく、反対に保守が長い方は、新規開発の設計レビューの量に驚くことがあります。応募の段階で、担当する工程と、調査と実装の割合を具体的に聞いておくことをおすすめします。
:::

## Webサービス・自社サービスの開発の仕事

事業会社が自社で運営するWebサービスや、SaaSのバックエンドをJavaで作っている案件です。スクラムなどの短い周期で開発を進めるチームが多く、リモートで働ける案件も比較的見つかります。

### 1日の流れ（例）

朝の短い打ち合わせで、担当する機能の状況と困りごとを共有します。日中は、APIの実装、データベースの変更、テストの作成に集中する時間が多くを占めます。プルリクエストを出し、ほかの開発者のレビューも同じ日に返します。フロントエンドの開発者とAPIの形をすり合わせたり、プロダクトの担当者と仕様の細部を決めたりするやり取りは、チャットでこまめに行います。

### 1か月の流れ（例）

- **スプリントの始め**：次の期間で作る機能を決め、作業の大きさを見積もる
- **期間の中**：実装とレビュー、自動テストの整備。小さな単位でリリースを繰り返す
- **スプリントの終わり**：できたものを関係者に見せ、振り返りで進め方を直す
- **月の単位**：性能やエラーの状況を見て、改善の作業を計画に入れる

### 成果物

動くコードと自動テスト、APIの仕様（OpenAPIなど）、設計の判断を残した短い文書、監視やログの設定などです。重い設計書を書く文化は少なく、**コードとテストそのものが成果物**として扱われます。業務システムからWebサービスに移る場合は、レビューの速さと、文書の軽さに慣れる必要があります。

## バージョン移行・モダナイズの仕事

古いJavaやSpringで動いているシステムを、新しい版や新しい基盤に移す案件です。2026年10月時点では、Java 8や11からJava 17以降へ、Spring Boot 2系から3系以降へ移す仕事が一定の数あります。言語の動きは[Javaの将来性の記事](/media/java-future/)で整理しています。

### 1日の流れ（例）

参画直後は、調査が1日の大半を占めます。依存しているライブラリの一覧を作り、新しい版で動かなくなる機能や、名前空間の変更で直す必要がある箇所を洗い出します。方針が決まった後は、修正とビルド、テストの繰り返しです。午後は、各機能の担当者に修正の影響を説明し、回帰テストの協力を依頼します。移行の作業は目に見える機能が増えないため、進み具合を分かりやすく伝える工夫が要ります。

### 1か月の流れ（例）

- **月初**：移行の対象と順番を決め、ビルドが通る状態を作る
- **毎週**：直した箇所と残っている課題を一覧で報告する。性能や動作の違いが出たら原因を記録する
- **月の半ば**：検証環境で回帰テストを回し、差分を潰す
- **月末**：本番への切り替え計画と切り戻し手順を整え、関係者と合意する

### 成果物

依存関係と影響の調査資料、移行の方針書、修正したコード、回帰テストの結果、切り替えと切り戻しの手順書、移行後に残った課題の一覧などです。**「何を変え、何が変わらないか」を説明する資料**の重みが大きい案件です。

## バッチ・基盤・共通部品の仕事

夜間に大量のデータを処理するバッチや、複数のチームが使う共通部品、ログや認証の基盤などを担当する案件です。画面を作る仕事はほとんどなく、処理の正しさと性能が評価の中心になります。

### 1日・1か月の流れ（例）

日中は、処理の設計と実装、データ量に応じた性能の確認に時間を使います。夜間バッチの案件では、朝に前夜の実行結果を確かめ、異常があれば原因の調査から1日が始まります。共通部品の案件では、各チームからの要望や不具合の報告を受け、直して配る仕事が続きます。1か月の単位では、月末や月初の処理量が増える時期に合わせて、性能の確認とリリースの計画を立てます。

### 成果物

処理の設計書、ジョブの依存関係の一覧、実装とテスト、性能の測定結果、運用担当者向けの手順書、共通部品の利用の手引きなどです。運用担当者への引き継ぎが仕事の一部になるため、**異常時に何を見てどう連絡するか**を文書に残す力が求められます。

## どの案件にも共通する仕事

種類が違っても、次の仕事はほぼすべてのJava案件にあります。

1. **レビュー**：自分のコードや設計のレビューを受け、ほかの人のレビューも返す
2. **仕様の確認**：分からない点を放置せず、確認事項として一覧にして相手に渡す
3. **テストの記録**：自動テストか仕様書かにかかわらず、確かめた内容を後から追える形で残す
4. **報告**：進み具合と詰まっている点を、短い言葉で毎日か毎週伝える

フリーランスならではの仕事として、**自分の稼働の記録と報告**もあります。月の稼働時間に幅を決めて精算する契約が多いため、調査や会議に使った時間も日々つけておく必要があります。精算の仕組みは[精算幅の記事](/media/seisan-haba/)をご覧ください。

:::caution
Javaの業務システム案件では、リリースや結合テストの立ち会いが夜間や休日に入ることがあります。また、担当する機能が増えても契約の範囲が変わらないまま、稼働だけが延びていくことも少なくありません。参画前に、夜間・休日の対応の有無と、稼働が精算幅を超えたときの扱いを確かめておきましょう。範囲が広がったときの考え方は[作業範囲が広がったときの契約の扱い](/media/scope-change/)で解説しています。
:::

## 関わる相手と、その相手に出すもの

Javaの案件の1日は、誰に何を渡すかで組み立てられています。相手ごとに整理すると次のようになります。

| 相手 | Javaエンジニアが出すもの | 頻度の目安 |
|---|---|---|
| チームのリーダー・アーキテクト | 進捗、設計の相談、レビュー依頼 | 毎日 |
| 同じチームの開発者 | コードレビュー、共通部品の使い方の共有 | 毎日 |
| 発注元の業務担当者・プロダクト担当者 | 仕様の確認事項、できたものの確認依頼 | 週次、随時 |
| テスト・品質の担当者 | テストの結果、不具合の修正 | 工程の区切り |
| 運用担当者・SRE | リリース手順、異常時の対応方法 | リリース前後 |

働く場所については、Webサービスの案件はリモートで回りやすい一方、金融・公共の業務システムでは閉じたネットワークでの開発や結合テストの立ち会いで出社を求められやすくなります。詳しくは[Javaのリモート案件の記事](/media/java-remote/)と[常駐案件とリモート案件の違い](/media/jochu/)をご覧ください。

:::view
当社では、案件をご案内する前に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。Javaの案件は、システムの種類と局面で毎日の仕事が変わるため、「これまで多く時間を使ってきた仕事」と「避けたい働き方」をあわせてお伝えいただくと、案件を照らし合わせやすくなります。設計書の有無や、調査と実装の割合、夜間対応の有無など、案件票に書かれていない働き方の点は、ご質問いただければ確認します。
:::

:::point
- Javaの案件は、システムの種類と局面で5つに分けると働き方が見える
- 新規開発は設計書とレビュー、保守・改修は調査と月次リリース、Webサービスはコードと自動テストが中心
- バージョン移行は調査と回帰テスト、バッチ・基盤は処理の正しさと性能と運用への引き継ぎが中心
- レビュー・仕様の確認・テストの記録・報告は、どのJava案件にも共通する
:::

## よくある質問

### Javaのフリーランスは、設計から任されることが多いですか？

案件によります。新規開発では詳細設計から入ることが多く、基本設計は社員や長く参画している人が担う傾向があります。保守・改修では、影響調査から実装までを一人で担うことがよくあります。設計の経験を増やしたい場合は、参画前に担当する工程を確かめておきましょう。上流の工程に入る考え方は[上流工程の案件に入るために必要な経験](/media/upper-process/)で解説しています。

### 会議はどのくらいありますか？

Webサービスの案件では、朝の短い打ち合わせとスプリントの会議が中心で、1日の多くは実装に使えます。業務システムの案件では、設計レビューや発注元との確認会が加わり、工程の区切りの前後は会議が増えます。どちらも、PMやリーダーに比べれば会議の割合は少なめです。

### 参画して最初の1か月は何をすることが多いですか？

開発環境の準備、コードの決まりとレビューの流れの確認、担当する機能の小さな修正から始めるのが一般的です。保守の案件では、システムの全体像と業務の流れをつかむ期間になります。初月の進め方は[Javaエンジニアの参画初月にやること](/media/java-first-month/)で詳しく解説します。
