React Nativeエンジニアのフリーランス案件の報酬は、**JavaScriptとTypeScriptの画面の開発に加えて、ネイティブ側の設定・ストアへの公開・版上げまで持てるか、Expoを使う現場か素のReact Nativeの現場か、たまっている版上げの量、設計を任されるか、稼働日数や期間**で決まります。React Nativeの単価について公的な統計はなく、案件ごとに大きく変わります。

React Nativeは、Webの開発で使われるReactの考え方でiOSとAndroidのアプリを作れるため、発注側は「Webのチームの知識を生かして、少ない人数でアプリも回したい」と考えて採用することがよくあります。報酬に差がつくのは、その期待の外側、つまり**JavaScriptの外で起きる問題をどこまで自分で片づけられるか**です。

## 「Reactが書ける」だけでは差がつきにくい理由

React Nativeの案件には、Webのフロントエンドから移ってきた方が多く応募します。コンポーネントの分け方や状態管理、TypeScriptの型の付け方といったReactの知識は、そのまま生かせます。その分、画面の実装だけを担う役割は応募できる人が多く、条件に幅が出にくくなります。

反対に、次のような作業は担える人が限られます。

- Xcodeやビルドの設定、証明書と署名、Androidのビルドの設定で止まったビルドを直す
- React Nativeの版上げで壊れたライブラリを調べ、置き換えるか直すかを判断する
- 公式やコミュニティのライブラリでは足りない機能を、SwiftやKotlinでつなぐ
- App StoreとGoogle Playの審査で受けた指摘に対応する

Reactそのものの報酬の考え方は[Reactエンジニアの報酬の記事](/media/react-rate/)にまとめています。この記事では、React Nativeならではの上下の理由に絞ります。

## 現場の構成で変わる報酬の考え方

React Nativeの公式サイトは、新しくアプリを作るならフレームワークを使うことを勧め、その例としてExpoを挙げています（2026年10月時点）。実際の現場は、Expoで始めたアプリ、Expoを使わずに作られたアプリ、ネイティブのアプリに一部の画面だけReact Nativeを組み込んだアプリなどに分かれます。

| 現場の構成 | よくある仕事 | 報酬に表れやすい点 |
|---|---|---|
| Expoで新しく立ち上げる | 構成と画面遷移の方針決め、ビルドと配布の仕組みづくり、初回の両ストア公開 | 少人数で全体を任されるため、設計とリリースの経験が重く見られる |
| Expoを使わない既存アプリの保守 | 依存ライブラリと版の更新、ネイティブ側の設定の修正 | ネイティブのファイルを直接読める人が少なく、条件に表れやすい |
| ネイティブアプリへの部分導入 | 既存のSwift・Kotlinのアプリに、React Nativeの画面を足す | 両方の世界の橋渡しができる人が限られる |
| 運用中アプリの機能追加 | 既存の設計に沿った画面と機能の追加 | 応募できる人が多く、幅が出にくい |

同じ「React Nativeの開発」でも、どの構成のどの局面かで、求められる責任がまったく違います。募集の文面にExpoの有無や版が書かれていなければ、面談で確かめておくと提示額の理由を読み取りやすくなります。

## 報酬を左右する主な要素

### 1. 版上げの負債をどれだけ抱えたアプリか

React Nativeは2か月ほどの間隔で新しい版が出ています。公式の案内では、保守の対象は最新の3つのマイナー系列とされています（2026年10月時点）。さらに、0.82からはNew Architectureだけで動くようになり、従来のアーキテクチャへ戻す設定は無視されるようになりました。

長く更新されていないアプリでは、版を一つずつ上げながら、New Architectureに対応していないライブラリを洗い出して置き換える作業が発生します。こうした「止まっていたアプリを動く状態に戻す」仕事は、調査の量が読みにくく、経験のある人に任されやすいため、条件にも表れやすくなります。

### 2. ネイティブ側に降りられるか

カメラ、決済、地図、Bluetooth、プッシュ通知などは、ライブラリの設定だけでは要件に届かず、SwiftやKotlinのコードに手を入れることがあります。ネイティブ側を読んで直せる人は、JavaScriptだけの人より任される範囲が広くなります。ネイティブの報酬の考え方は[iOSエンジニアの報酬の記事](/media/ios-rate/)と[Androidエンジニアの報酬の記事](/media/android-rate/)も参考になります。

### 3. リリースと更新の運用を持てるか

ビルドと配布の自動化、署名の情報の管理、両ストアへの申請を一人で進められるかは、少人数のチームで重く見られます。Expoの現場では、EAS Updateでアプリのストア更新を待たずにJavaScriptや画像を配信できますが、Expoの公式ドキュメントでも、ネイティブのコードや権限の変更は配信できず、配信する内容は各ストアのルールに従う必要があると説明されています。どこまでを配信で直し、どこからをストアの審査に回すかを判断できる人は、運用の要として頼られます。

### 4. 稼働日数と期間

立ち上げの案件は公開日までの期間で区切られることが多く、公開の直前は稼働が増えがちです。公開後は版上げと小さな改修に絞り、週2〜3日程度で続く案件もあります。月額だけでなく、精算幅と稼働の変わり方まで見て比べましょう。精算の仕組みは[精算幅の記事](/media/seisan-haba/)で解説しています。

:::view
React Nativeの案件をご紹介していると、面談で評価されやすいのは、画面の実装の量よりも「ビルドが通らなくなったときや、版上げでライブラリが動かなくなったときに、どこまで自分で調べて直したか」を具体的に話せる方です。Webから移ってきた方でも、ネイティブ側の設定ファイルに一度手を入れた経験があれば、短くても伝える価値があります。当社では、先に稼働日数・リモートの希望・ご希望の金額を伺い、その条件に合う案件だけをご案内しています。
:::

## ストアとOSの要件が生む仕事

React Nativeのアプリも、各ストアの要件の変化から逃れられません。たとえばAppleは、2026年4月28日から、App Store Connectにアップロードするアプリは、Xcode 26以降とiOS 26などのSDKでビルドする必要があると案内しています（2026年10月時点）。

こうした要件に合わせるには、React Native本体やライブラリの版上げが前提になることが多く、機能追加とは別の仕事として発生します。版上げを計画的に回せる人は、保守の案件でも継続して声がかかりやすくなります。引き継ぎの案件では、参画前に現状のReact NativeとExpoの版を確かめておくと、稼働の見積もりがずれにくくなります。

## 報酬が伸びにくいパターン

- **JavaScriptの外の問題を他の人に任せている**：ビルドやストア対応の経験が残らない
- **Expoの仕組みを「動いているから」と使っている**：設定がどこで生成されているか説明できないと、壊れたときに頼られない
- **版上げを避けている**：経験年数が増えても、負債のあるアプリを任せられる材料にならない
- **一つのアプリの機能追加だけを続けている**：構成の違いを比べて話す材料が増えない

どれも、今の案件の中で担当を少しずつ広げることで変えられます。

## 単価交渉で示せる材料

契約の更新や担当範囲が変わったときは、条件の見直しを相談しやすい時期です。React Nativeの案件では、次の材料が発注側にも伝わりやすくなります。

| 材料 | 伝え方の例 |
|---|---|
| 担当範囲の広がり | 画面の実装に加え、両ストアへの申請とネイティブ側の設定を担当するようになった |
| 版上げの実績 | 何系から何系へ上げたか、置き換えたライブラリの数（守秘義務の範囲で） |
| リリースの運用 | 配信の手順を整え、ストアの審査に回すものと分ける基準を作った |
| 引き継ぎのしやすさ | 構成と手順を文書にし、他のメンバーが作業できるようにした |

伝える順番や時期は[単価交渉の記事](/media/rate-negotiation/)、報酬の一般的な決まり方は[報酬の決まり方の記事](/media/rate-mechanism/)で整理しています。

:::caution
アプリ1本を「公開したら支払う」請負の形で受けると、ストアの審査を通ることが完成の条件とされ、差し戻しのたびに無償で直す負担が生じることがあります。とくに版上げを含む案件は、調べてみないと作業量が分からないことが多いため、準委任か請負か、何をもって完了とするかを受ける前に確かめましょう。違いは[準委任と請負の違いの記事](/media/junin-vs-ukeoi/)で解説しています。
:::

:::view
アプリの案件では、公開しているアプリの画面や機能が、経歴の説明でそのまま話題になることがあります。当社では、経歴はご本人の了承を得た案件にだけ、氏名・連絡先を伏せて提案しています。どのアプリに関わったかを伝えてよいか迷う場合は、前の契約の秘密保持の範囲を確かめたうえで、早めにご相談ください。
:::

:::point
- React Nativeの報酬は、ネイティブ側とストア公開まで持てるか・現場の構成・版上げの量・稼働条件で決まり、案件ごとに大きく変わる
- Reactの知識だけでは応募できる人が多く、JavaScriptの外の問題を片づけられるかで差がつく
- 公式は最新の3つのマイナー系列を保守するとしており、版上げの経験はそのまま交渉の材料になる
:::

## よくある質問

### React Nativeエンジニアの単価の相場はいくらですか？

React Nativeの単価について公的な統計はなく、現場の構成、担当範囲、ネイティブ側の経験、稼働日数、商流によって大きく変わります。相場の数字を探すより、ご自身の経験が立ち上げ・保守・部分導入・機能追加のどれに合うかを整理し、条件をそろえて比べるほうが判断の材料になります。

### Flutterの案件と比べて、報酬の決まり方は違いますか？

アプリ全体への責任をどこまで負えるかで決まる点は似ています。違いは、React NativeではWebのReactの知識を持つ人が多く応募するため、ネイティブ側と版上げの経験がより差になりやすい点です。Flutterの考え方は[Flutterエンジニアの報酬の記事](/media/flutter-rate/)をご覧ください。

### Expoの経験しかないと単価は上がりませんか？

Expoの現場は増えており、Expoの経験だけで参画している方もいます。ただ、ネイティブの設定がどこで作られ、ビルドがどう組み立てられるかまで説明できるかで、任される範囲が変わります。独立の進め方は[React Nativeエンジニアがフリーランスになるには](/media/react-native-how-to/)をご覧ください。
