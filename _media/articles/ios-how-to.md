iOSエンジニアがフリーランスになるには、**Swiftで画面や機能を作れることに加えて、設計の方針を決め、App Storeへのリリースまでを自分の手で進めた経験**が必要です。業務委託の現場では、仕様を受け取って実装するだけでなく、既存のコードを読み解き、チームの中で判断を任される場面が多いためです。

独立の準備は、経験の棚卸し、実績の見せ方の整理、開発環境とお金の準備、最初の案件選びの順に進めると、無理が少なくなります。この記事では、iOSの案件ならではの事情に絞って説明します。

## iOSのフリーランス案件で多い現場

iOSの業務委託案件は、どのような状態のアプリに入るかで、求められる経験が大きく変わります。

| 現場の型 | 主な仕事 | 特に見られる経験 |
|---|---|---|
| 自社サービスの機能追加 | 運用中のアプリに新機能を足し、改善を続ける | 既存コードの読解、チーム開発、リリース運用 |
| 新規アプリの立ち上げ | ゼロから設計し、初回リリースまで持っていく | アーキテクチャの選定、審査対応、API設計への参加 |
| 古いコードの置き換え | Objective-CからSwiftへ、UIKitからSwiftUIへ移す | 両方の書き方の理解、段階的な移行の計画 |
| 受託開発 | 発注元のアプリを仕様に沿って開発する | 要件の確認、見積もり、納品と保守の範囲 |
| 共通基盤・SDK | 社内の複数アプリで使うライブラリを作る | モジュール分割、API設計、ドキュメント |

運用中のアプリに参画する案件は数が多く、独立して最初に選ばれやすい型です。一方、新規立ち上げは、設計を任せられる人を求めるため、リリースまでを主導した経験が問われます。

## 独立前に積んでおきたい経験

### UIKitとSwiftUIの両方を読める

新しい画面はSwiftUIで作る現場が増えていますが、運用中のアプリの多くにはUIKitのコードが残っています。片方しか書けないと、参画できる案件が限られます。両方のコードを読み、混在した状態でどう保守するかを説明できると、移行案件でも頼りにされます。

### 設計の判断を自分でした経験

MVVMなどの設計パターンの名前を挙げるより、「なぜその分け方にしたか」「画面が増えたときに何が困ったか」を話せることが大切です。Swift Concurrencyによる非同期処理への書き換え、状態管理の見直し、モジュール分割など、設計を変えた経験があれば具体的に整理しておきます。

### リリースと審査の対応

App Storeへの申請と審査の対応は、iOSエンジニアに固有の仕事です。Appleの審査ガイドラインは、安全性・パフォーマンス・ビジネス・デザイン・法的事項の5つの章で構成され、プライバシーポリシーの掲示、データ収集への同意、アカウント作成機能があるアプリでのアカウント削除機能などが求められています（2026年10月時点のAppleの案内）。リジェクト（審査不通過）を受けて修正し、再申請した経験は、面談で話題にしやすい実績です。

### テストと自動化

ユニットテストやUIテストを書いた経験、ビルドや配布を自動化した経験は、チームで開発する案件で評価されます。TestFlightでのテスト配布の運用も、リリースまでを担った経験として伝えられます。

:::view
iOSの案件をご紹介していると、面談で評価されやすいのは、担当した画面の数より「リリースまでに何を判断したか」を話せる方です。たとえば審査で指摘を受けた理由と直し方、古いコードを残すか書き換えるかの判断などです。会社員時代に申請作業を別の担当者がしていた方も、どこまで関わったかを整理すると、伝えられる経験が見つかることがあります。
:::

## 個人開発のアプリは実績になるか

会社の案件は守秘義務があり、具体的なアプリ名を出せないことがよくあります。その点、自分でリリースしたアプリは、コードや画面を見せられる実績になります。

App Storeでアプリを配信するには、有料のApple Developer Programへの登録が必要です。登録は個人と組織のどちらでもでき、年間メンバーシップの費用がかかります。無料のアカウントでもXcodeでの開発や実機でのテストはできますが、App Storeでの配信はできません（2026年10月時点のAppleの案内）。

個人開発のアプリは、規模よりも次の点が伝わるかを意識すると、実務の経験を補う材料になります。

- 設計の方針と、その理由を説明できる
- テストを書き、更新を続けている
- 審査を通し、OSの更新に合わせて保守している

:::caution
受託や業務委託で作るアプリを、自分の個人アカウントからリリースすることは避けましょう。アプリの配信アカウントやストアの権利は、通常は発注元の組織が持ちます。どのアカウントで申請するか、証明書やキーを誰が管理するかは、参画の前に確認してください。成果物の権利の考え方は[フリーランスの著作権の記事](/media/copyright/)で解説しています。
:::

## 会社員とフリーランスで変わること

| 比べる点 | 会社員のiOSエンジニア | フリーランスのiOSエンジニア |
|---|---|---|
| 開発環境 | Macや検証端末は会社が用意する | 貸与されることも、持ち込みを求められることもある |
| 担当範囲 | 部署の役割や上司の指示で決まる | 契約で決めた範囲の中で担う |
| 技術の選び方 | 社内の標準に従う | 現場ごとに違う設計・ライブラリに素早く慣れる |
| 次の仕事 | 異動や昇格で決まる | 契約の更新か、次の案件を自分で探す |

Macや検証用の端末を自分で用意する場合は、OSの更新に合わせて買い替えも必要になります。事業で使う機器の費用は経費として扱える場合があるため、[経費にできるものの記事](/media/keihi-list/)もあわせてご覧ください。参画先の機密を扱う現場では、私物の端末を使えないこともあります。貸与か持ち込みかは、面談の段階で確かめておきましょう。

## 独立までの進め方

### 1. 関わったアプリごとに経験を書き出す

アプリごとに、期間、チームの人数、担当した機能、使った技術、リリースの回数、工夫した点を書き出します。社名やアプリ名は、あとでスキルシートに書くときに伏せて整えます。iOS向けのまとめ方は[iOSエンジニアのスキルシートの書き方](/media/ios-skillsheet/)、基本は[スキルシートの書き方](/media/skillsheet-basics/)で解説しています。

### 2. 希望する条件を決める

稼働日数、リモートか出社か、希望する報酬の下限、得意な領域（EC、決済、動画、ヘルスケアなど）を決めておきます。リモートの傾向は[iOSエンジニアのリモート案件の記事](/media/ios-remote/)、報酬の決まり方は[iOSエンジニアの報酬の記事](/media/ios-rate/)にまとめています。

### 3. 手続きとお金を準備する

退職に合わせて健康保険・年金・住民税の切り替えが必要になり、事業を始めたら開業届を出します。最初の報酬が入るまでの生活費も用意しておきます。流れは[会社員からフリーランスになる手順](/media/quit-company-steps/)と[開業届の出し方](/media/kaigyo-todoke/)をご覧ください。

### 4. 案件を探し、面談を受ける

フリーランスエージェント（案件紹介サービス）、知人の紹介、発注元との直接契約などの方法があります。使い方は[フリーランスエージェントの使い方](/media/agent-how-to-use/)で解説しています。

## 面談で聞かれやすいこと

iOSの案件の面談では、次のような質問がよく出ます。答えを準備しておくと、経験の深さが伝わりやすくなります。

1. **担当したアプリの規模と構成**：画面数、利用者の規模（伏せられる範囲で）、設計パターン
2. **SwiftUIとUIKitの経験**：どちらでどの程度書いたか、混在した環境での保守
3. **非同期処理と状態管理**：通信、キャッシュ、画面の状態をどう扱ったか
4. **リリースの経験**：審査で受けた指摘、リリース後の不具合への対応
5. **チームでの進め方**：コードレビュー、デザイナーやサーバー側の開発者とのやり取り

AndroidやFlutterの経験も問われることがあります。両方を扱う案件については[Androidエンジニアがフリーランスになるには](/media/android-how-to/)、[Flutterエンジニアがフリーランスになるには](/media/flutter-how-to/)も参考になります。

## 契約の前に確認しておくこと

iOSの案件は、月単位で稼働する準委任契約が多い一方、アプリ一式の完成を約束する請負契約もあります。請負の場合、審査で不通過になったときの修正や、OSの更新に伴う対応をどこまで含むかで、負担が大きく変わります。違いは[準委任契約と請負契約の違い](/media/junin-vs-ukeoi/)で解説しています。

2024年11月に施行されたフリーランス法では、発注側は業務を委託したとき、業務の内容・報酬の額・支払期日などを書面やメールなどで直ちに明示することが求められています。担当する範囲、リリース作業を含むか、契約期間と更新の扱いを、条件の明示で確かめておきましょう。

:::view
当社では、経歴をご紹介する前にどの案件に提案するかを伺い、ご了承いただいた案件にだけ、氏名・連絡先を伏せて提案しています。業務の範囲・報酬・支払期日・契約期間は個別契約に書いてお渡ししています。開発環境の貸与やリリース作業の範囲など、iOSの案件で確かめておきたい点は、面談の前に一緒に整理することをおすすめします。
:::

:::point
- iOSで独立するには、Swiftでの実装に加えて、設計の判断とリリースまでを担った経験が必要
- UIKitとSwiftUIの両方を読めると、参画できる案件が広がる
- 個人開発のアプリは、設計の理由と保守の継続を説明できれば実績になる
- 開発環境の貸与、配信アカウントの管理、リリース作業の範囲は参画前に確認する
:::

## よくある質問

### iOSの実務経験は何年あれば独立できますか？

決まった年数はありません。案件側が見るのは、運用中のアプリで機能開発からリリースまでを一通り担ったか、設計の判断に関わったかです。チームの中で自分が何を任されていたかを、具体的に説明できるかを目安にしてください。

### SwiftUIしか書けなくても案件はありますか？

SwiftUIで作る新しいアプリの案件もあります。ただ、運用中のアプリにはUIKitのコードが残っていることが多く、UIKitを読めないと選べる案件が限られます。独立の前に、UIKitのコードを読んで直す経験を少しでも積んでおくと安心です。

### 個人開発のアプリがないと不利になりますか？

個人開発のアプリがなくても、実務の経験を具体的に説明できれば問題ありません。会社の案件で守秘義務があり、見せられる成果物がない場合の補いとして、個人開発のアプリが役立つという位置づけです。
