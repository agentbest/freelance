Azureエンジニアの仕事は、**Microsoftの製品のサポート期限と、IDまわりの方針の変化に合わせて、企業の環境を移し、整え続ける仕事**として続いていくと考えるのが現実的です。Azureの案件は、Windows ServerやActive Directory、Microsoft 365とつながった環境が多く、Microsoftの方針が変わると、現場の作業も変わります。

選択肢を広げるには、Azureの構築経験に、**サポート期限を見据えた移行の判断**、**IDと自動化の作り直し**、**AIの支援を前提にした権限設計**のどれかを重ねるのが近道です。この記事では、公式に示されている期限と方針をもとに、仕事の変化と経験別の広げ方を整理します。

独立までの準備は[Azureエンジニアがフリーランスになるには](/media/azure-how-to/)、案件で問われるスキルと認定資格は[Azureの案件で求められるスキル](/media/azure-skills/)で扱っています。

## 公式の発表から見えるAzureの仕事の節目

2026年10月時点で、Azureの案件に影響する公式の期限と方針は次のとおりです。

| 項目 | Microsoftの公式情報 | 仕事への影響 |
|---|---|---|
| Windows Server 2012/2012 R2 | 延長サポートは2023年10月に終了。拡張セキュリティ更新プログラム（ESU）の3年目は2026年10月13日まで | ESUでつないでいた環境の移行や更新が待ったなしになる |
| Windows Server 2016 | 延長サポートの終了日は2027年1月（ライフサイクルのページでは太平洋時間の1月13日） | 次の移行の計画が動き出す |
| Azureの多要素認証 | ポータルは2024年10月から、CLI・PowerShell・IaCツール・REST APIでの作成・更新・削除は2025年10月1日から順に必須化 | 人のアカウントで動かしていた自動化の作り直しが必要になる |
| Azure Copilot | 利用者が持つ権限の範囲で操作し、操作の前に確認を求める | 権限設計の良し悪しが、AIの使いやすさと安全性を左右する |

Azureでは、**期限や方針の変更が、そのまま案件のきっかけになる**のが特徴です。新しいサービスを覚えることと同じくらい、Microsoftの発表を読み、自分の担当する環境に何が起きるかを先に説明できることが評価されます。

## サポート期限が生む移行の仕事

Microsoftのライフサイクルに関するFAQによると、ESUは、サポートが終わった製品を使い続ける必要がある顧客のための「最後の手段」の有償の仕組みで、長く使い続けるためのものではないとされています。一方で、AzureのVMなどに移した場合は、Windows Server 2012/2012 R2のESUが追加の費用なしで提供されると案内されています。オンプレミスに残す場合は、Azure Arcに対応したサーバーを通じてESUを使う方法も示されています。

つまり、サポートが切れる環境を前にしたとき、企業には次のような選択肢があります。

1. 新しい版のWindows Serverに上げる
2. Azureに移したうえで、時間をかけて更新する
3. オンプレミスに残し、Azure Arcなどで管理しながら移行を進める
4. アプリケーションそのものを作り直す、または廃止する

どれを選ぶかは、アプリの対応状況、ライセンス、費用、止められる時間によって変わります。**この選択肢を並べ、根拠をそろえて発注元に判断してもらう**のが、Azureの移行案件で人が担う中心の仕事です。Windows Server 2016の期限も近づいているため、2012世代の移行で得た経験は、次の移行の計画でも生かせます。

## 多要素認証の必須化で変わる自動化の作り方

Microsoft Learnの案内では、Azureへのサインインに多要素認証（MFA）を必須にする取り組みが2段階で進められています。第2段階では、2025年10月1日から、Azure CLI、Azure PowerShell、IaCツール、REST APIでリソースを作成・更新・削除する操作にMFAが求められるようになりました。準備が必要な顧客には、第2段階の開始を2026年7月1日まで延ばす手段も用意されていました。

ここで影響を受けるのは、**人のユーザーアカウントをサービス用のアカウントとして使い、スクリプトや自動化を動かしていた環境**です。マネージドIDやサービスプリンシパルのようなワークロードIDは対象外とされ、MicrosoftはこうしたアカウントをワークロードIDへ移すよう勧めています。ユーザー名とパスワードでトークンを取る古い認証の流れはMFAと両立しないことも示されています。

ここから生まれる仕事は、次のような地道なものです。

- 自動化に使われているユーザーアカウントを洗い出す
- パイプラインやスクリプトの認証を、マネージドIDやサービスプリンシパルに切り替える
- 切り替えに合わせて、権限の範囲を必要な分だけに絞り直す

IDの設定と、IaCやパイプラインの両方が分かる人は多くありません。**Entra IDの知識と自動化の知識をつなげられること**は、今後のAzureの案件で強みになりやすい組み合わせです。

## AIの支援を前提にした権限設計

Azure Copilotは、Azureポータルなどから自然言語で質問したり、操作を頼んだりできるAIの機能です。公式の概要では、Copilotは利用者がアクセスできるリソースに、利用者が実行できる操作の範囲でアクセスし、操作の前には利用者の確認が必要とされています。エージェントの機能も案内されています。

この仕組みは、**AIが何をできるかは、使う人に与えた権限で決まる**ということでもあります。権限を広く渡したまま運用している環境では、AIを使った操作の影響も広くなります。必要なときだけ権限を上げる仕組みや、役割ごとに権限を分ける設計は、AIの支援が当たり前になるほど重みを増すと考えられます。

AIの支援で、設定の調べ物や定型の操作は速くなる可能性があります。一方で、提案された変更を本番に入れてよいか、どのサブスクリプションに影響するかを判断するのは人です。発注元がAzure Copilotなどの利用を認めているかどうかも、現場ごとに違います。

:::view
Azureの案件をご紹介していると、Windows ServerやActive Directoryの経験が長い方が「クラウドの経験が浅い」と遠慮される場面をよく見ます。ただ、移行やIDの整理の案件では、既存の環境で何が起きやすいかを知っていることが評価されやすい傾向があります。オンプレミスでの経験は隠さず、その経験をAzureの移行や認証の切り替えにどう生かしたかを、あわせて書き出しておくことをおすすめします。
:::

## 選択肢を広げる3つの方向

### IDとセキュリティの側へ

条件付きアクセス、権限の棚卸し、ワークロードIDへの切り替えなど、Entra IDを軸にした仕事は、Azureだけでなく、Microsoft 365や他のSaaSの認証にもつながります。セキュリティを主軸にする場合は[セキュリティエンジニアの将来性](/media/security-engineer-future/)もあわせてご覧ください。

### ハイブリッドと移行の側へ

すべてをすぐにクラウドに移せない企業では、オンプレミスとAzureを並べて管理する期間が長く続きます。Azure Arcによる管理や、閉域の接続、移行の計画を担える人は、移行の始めから終わりまで関われます。拠点やデータセンターとの接続を深めたい場合は、[ネットワークエンジニアの将来性](/media/network-future/)も参考になります。

### 運用の仕組みの側へ

構築した環境を安定して動かすための監視、更新の自動化、障害時の手順づくりは、構築の次に求められやすい役割です。詳しくは[SREの将来性](/media/sre-future/)で扱っています。

## 経験に応じた広げ方

### Windows Server・Active Directoryの経験が中心の人

オンプレミスの経験が長い方は、それを移行の判断材料として示せる立場にあります。まずは、Azureの検証環境で、仮想マシンの移行、Entra IDとの同期、ポータルとIaCでの構築を一通り経験しておくとよいでしょう。40代以降の案件の選び方は[40代のフリーランス](/media/40s/)と[50代のフリーランス](/media/50s/)でも扱っています。

### Azureの構築を任されている人

構築の経験がある方は、IDと自動化の接点に踏み込む時期です。パイプラインの認証を切り替える、権限の範囲を絞り直す、といった仕事を一つやり切ると、設計を任される材料になります。

### 設計やガバナンスを経験している人

この段階では、サポート期限、ライセンス、費用、セキュリティの方針をまとめて、企業全体の移行の順番を描く役割が求められます。AWSやGoogle Cloudとの違いを説明できると、比較検討の段階から呼ばれやすくなります。ほかのクラウドの変化は[AWSエンジニアの将来性](/media/aws-future/)と[GCPエンジニアの将来性](/media/gcp-future/)で扱っています。報酬の考え方は[Azureの報酬の記事](/media/azure-rate/)をご覧ください。

:::caution
サポート期限やMFAの必須化のように日付のある話は、テナントごとの延期の設定や、契約しているライセンスによって、実際の影響が変わります。スキルシートや面談で「MFA必須化に対応」と書くときは、何を洗い出し、何をどの方式に切り替えたのかまで書きましょう。期限そのものは、作業の前にMicrosoftの公式情報で最新の内容をご確認ください。書き方は[Azureのスキルシートの記事](/media/azure-skillsheet/)で解説しています。
:::

:::view
当社では、案件をご案内するときに、先に稼働日数・リモートの可否・ご希望の金額を伺い、合う案件だけをお出ししています。Azureの案件は、移行の期限に合わせて始まるものも多く、参画の時期や、切り替えの夜間・休日の作業があるかで条件が変わります。ご希望を伝える際は、夜間や休日の作業をどこまで受けられるかもあわせて整理しておくことをおすすめします。
:::

- 移行案件の中心は、更新・Azureへの移行・Azure Arcでの管理・作り直しの選択肢を並べ、判断の材料をそろえること
- MFAの必須化で、人のアカウントで動かしていた自動化をワークロードIDへ移す仕事が生まれている

## よくある質問

### Windows Serverの経験は、この先も生かせますか？

生かせる場面はあります。サポート期限を迎える環境の移行では、今の環境で何が動いていて、何が移行の妨げになるかを読み解く力が求められます。そのうえで、Azureでの構築やIaCの経験を少しずつ加えていくと、移行案件で任される範囲が広がります。

### MFAの必須化で、自動化のスクリプトが動かなくなった場合はどうすればよいですか？

Microsoft Learnでは、自動化に使っているユーザーアカウントを、マネージドIDやサービスプリンシパルなどのワークロードIDへ移すことが勧められています。どの方式を使うか、権限をどこまで与えるかは発注元の方針によるため、作業の前に担当者と範囲を決めてから進めましょう。

### Azure Copilotを使えば、Azureの経験が浅くても案件に対応できますか？

調べ物や定型の操作は速くなる可能性がありますが、Copilotは使う人の権限の範囲で動き、操作の前に確認を求める仕組みです。提案された変更が正しいかを判断するには、Azureの仕組みの理解が欠かせません。また、利用が認められているかは現場ごとに違うため、参画前に確かめておきましょう。
