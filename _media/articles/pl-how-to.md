フリーランスのPL（プロジェクトリーダー）になるには、**開発チームの作業を割り振り、進捗と品質をまとめてPMに報告した経験**と、**チームが使う技術を自分で判断できる実務経験**の2つが必要です。案件側が知りたいのは「リーダーの肩書きがあったか」より、「何人のチームで、何をまとめていたか」です。

独立の準備は、リーダーとしての経験の棚卸し、案件の型の見極め、スキルシートと面談の準備、手続きの順に進めると無理がありません。

## PLに求められる経験の目安

PLは、PMの下で一つの開発チームをまとめる実務のリーダーです。プロジェクト全体の計画や予算はPMが持ち、PLはチームの単位で計画を実行に移します。そのため、求められる経験もPMとは違い、**チームの毎日の仕事を回した経験**が中心になります。PMとして独立する場合の考え方は[PMがフリーランスになるには](/media/pm-how-to/)で扱っています。

経験の目安は、年数よりも次のような中身で考えます。

| 経験 | 目安として説明できるとよいこと |
|---|---|
| 作業の割り振り | 機能や画面の単位で作業を分け、メンバーの得意・不得意を見て割り当てた |
| 進捗の把握 | 遅れを早めに見つけ、作業の入れ替えや応援の依頼で手を打った |
| 品質のまとめ | 設計やコードをレビューし、不具合の傾向を見てテストや手順を見直した |
| PMへの報告 | チームの状況を、事実・影響・対応案の順で定期的に伝えた |
| 技術の判断 | メンバーの成果物の良し悪しや、実装方法の選び方を自分で判断できた |
| 一通りの工程 | 設計からテスト、リリースまでを、少なくとも一度はチームとして通した |

すべてそろっていなくても、PLの案件に入れることはあります。ただ、「作業の割り振り」「進捗の把握」「PMへの報告」の3つは、ほとんどの案件で聞かれます。この3つは具体的な場面とあわせて話せるようにしておきましょう。

### 肩書きがなくても経験は数えられる

会社員の時代に「リーダー」の肩書きがなくても、数名の作業をまとめ、進捗を上に報告していたなら、その範囲を正確に書けばPLの経験として伝わります。逆に、肩書きはリーダーでも、実際は自分の担当の実装が中心だった場合は、メンバーとしての経験として整理したほうが、面談での食い違いを防げます。開発の立場からリーダーの役割へ移る段階は[開発者からPM・PMOへ役割を移す進め方](/media/dev-to-pm/)で解説しています。

## フリーランスPLの案件の主な型

PLの案件は、どんなチームを率いるかで求められる動きが変わります。

| 案件の型 | 主な役割 | 見られやすい経験 |
|---|---|---|
| 受託開発のチームリーダー | 開発会社やSIerの体制の中で、機能単位のチームをまとめる | 工程どおりに進める力、レビューと不具合の管理 |
| 事業会社の内製チームのリーダー | 社員のエンジニアとともに、自社サービスの開発チームを回す | 短い周期での計画と見直し、メンバーの立ち上げ |
| 協力会社・海外拠点をまとめるPL | 複数の会社や拠点に分かれた作業を、一つのチームとしてまとめる | 作業の指示の書き方、受け入れの確認、時差や言葉の調整 |
| 開発もするPL | 少人数のチームで、自分も設計や実装を担いながらまとめる | 技術の深さと、自分の作業と管理の時間配分 |

自分の経験がどの型に近いかを把握すると、応募する案件を絞りやすくなります。技術の判断に軸足を置きたい場合は、PLよりテックリードの案件が合うこともあります。違いは[テックリードとして参画する記事](/media/tech-lead/)をご覧ください。

:::view
案件紹介の現場では、PLの面談で「チームで遅れが出たとき、どう気づき、何をしたか」を問われることがよくあります。評価されやすいのは、遅れの兆しを何で見ていたか、メンバーとどう話し、PMに何を相談したかを順に話せる方です。メンバーの話を引き合いに出すときに、個人を責める言い方にならず、仕組みの問題として説明できる方は、任せやすいと受け止められる傾向があります。
:::

## 独立前に積んでおきたい経験

会社員のうちに、次の経験を意識して積んでおくと、独立後に任せてもらえる範囲が広がります。

1. **チームを最初から組んだ経験**：既に回っているチームの引き継ぎだけでなく、メンバーの役割分担や作業の進め方を一から決めた経験
2. **社外のメンバーをまとめた経験**：協力会社や別部署など、自分の会社の上下関係が及ばない相手に作業を依頼した経験
3. **レビューの基準を決めた経験**：自分がレビューするだけでなく、何を見るかをチームでそろえた経験
4. **計画どおりに進まなかったときの経験**：遅れや仕様の変更を受け、作業の順番を組み替えた経験

フリーランスのPLは、参画してすぐに知らないメンバーをまとめることになります。初対面のメンバーと短い期間で仕事の進め方をそろえた経験は、特に話す価値があります。

## 独立までの進め方

### 1. 率いたチームを棚卸しする

関わったプロジェクトごとに、期間、チームの人数と構成、自分の報告先、担当した工程、自分が手を動かした割合を書き出します。そのうえで、上の表の経験のうち、どれを担っていたかを確かめます。

### 2. スキルシートと面談の準備をする

PLのスキルシートでは、技術の一覧より先に、どんなチームをどの範囲でまとめていたかが読まれます。書き方は[PLのスキルシートの記事](/media/pl-skillsheet/)、案件で問われるスキルは[PLのスキルの記事](/media/pl-skills/)で解説しています。

### 3. 条件を決めて案件を探す

稼働日数、出社の頻度、希望する報酬の下限、得意な技術と業務を先に決めておくと、合わない案件に時間を使わずに済みます。報酬の決まり方は[PLの報酬の記事](/media/pl-rate/)、探し方は[フリーランスエージェントの使い方](/media/agent-how-to-use/)をご覧ください。

### 4. 退職と開業の手続きを進める

退職後の健康保険・年金・住民税の切り替え、開業届や青色申告の届け出は、職種にかかわらず共通の手続きです。流れは[会社員からフリーランスになる手順](/media/quit-company-steps/)、届け出の期限や書き方は[開業届の出し方](/media/kaigyo-todoke/)で解説しています。

:::caution
前職の取引先のプロジェクトに、フリーランスとしてPLで戻る話が出ることがあります。退職時の誓約書や就業規則に、取引先との直接取引や競業を制限する定めがないかを確かめてください。判断に迷う場合は、弁護士などの専門家にご相談ください。
:::

## 契約で確かめておきたいPL特有の点

フリーランスのPLは、多くの場合、準委任契約で参画します。準委任では、チームをまとめる業務を専門家として通常求められる注意を払って行うことが約束の中身になり、成果物の完成そのものを約束する請負とは考え方が違います。違いは[準委任契約と請負契約の違い](/media/junin-vs-ukeoi/)で解説しています。

PLならではの確認点は次のとおりです。

- **まとめる範囲**：どのチームの、どの工程を任されるか。品質やリリースの判断まで含むか
- **メンバーへの指示の流れ**：自分が作業を割り振るメンバーは、どの会社に所属し、誰の指示系統にあるか
- **自分への指示の流れ**：発注元から自分への業務の依頼が、契約に沿った形で行われるか
- **手を動かす割合**：実装やテストをどの程度担うか

指示の流れが契約の形と合っていないと、偽装請負の問題につながることがあります。考え方は[偽装請負の記事](/media/gisou-ukeoi/)で解説しています。

フリーランス法では、発注する事業者は業務を委託したとき、給付の内容、報酬の額、支払期日などを書面またはメールなどで直ちに明示する必要があります。6か月以上の業務委託を解除したり更新しなかったりする場合は、原則として少なくとも30日前までに予告することとされています（2026年10月時点、公正取引委員会の案内による）。

:::view
当社では、案件をご案内する前に稼働日数・リモートの希望・ご希望の金額を伺い、条件に合う案件だけをお出ししています。経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。契約では業務範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししていますので、まとめる範囲やメンバーへの指示の流れなど、気になる点はご質問いただければ確認します。
:::

:::point
- PLの独立には、作業の割り振り・進捗の把握・PMへの報告の経験と、チームの技術を判断できる実務経験が必要
- 受託開発・内製チーム・協力会社や海外拠点・開発もするPLなど、案件の型で見られる経験が違う
- 契約では、まとめる範囲、メンバーと自分への指示の流れ、手を動かす割合を確かめる
:::

## よくある質問

### リーダーの経験が1年ほどでもPL案件に応募できますか？

応募できる案件はあります。期間の長さより、何人のチームで何をまとめていたかが見られます。経験が短い場合は、小さなチームのPLや、開発もするPLの案件から入り、まとめる範囲を広げていく進め方が現実的です。最初の案件の選び方は[初めての案件の記事](/media/first-project/)も参考にしてください。

### PLを経ずに、いきなりPMとして独立できますか？

PM案件では、プロジェクト全体の計画や体制を判断した経験が問われます。PLの経験は、その土台になるチーム運営の経験です。PLを経ずにPMになる人もいますが、チームの毎日の仕事を回した経験があると、PMとして入ったときにも現場の状況をつかみやすくなります。

### 技術の経験が古くてもPLになれますか？

管理に専念する形の案件では、技術の深さより運営の経験が重視されることがあります。ただ、多くのPL案件ではメンバーの成果物を見て判断する場面があるため、案件で使われている技術に触れ直しておくと、面談で答えやすくなります。
