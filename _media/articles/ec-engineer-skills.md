ECサイト・Shopifyエンジニアの案件で問われるスキルは、**テーマ開発、アプリとAPI、チェックアウトと割引の仕組み、外部システム連携、ヘッドレス**の5分野に分けると整理しやすくなります。すべてを深く持つ必要はなく、案件ごとにどの分野が中心かが違います。共通して見られるのは、**運用担当が日々触るストアを壊さずに変えられるか**という点です。

この記事のShopifyの仕組みの説明は、2026年10月時点のShopify.devの内容に基づきます。Shopifyは仕様の変更が多いため、参画時には最新のドキュメントを確かめてください。

## ECサイト・Shopifyの案件で見られるスキルの全体像

| 分野 | 主な中身 | 中心になる案件 |
|---|---|---|
| テーマ開発 | Liquid、セクション・ブロック、JSONテンプレート、表示速度 | ストア構築、デザインの刷新、運用中の改善 |
| アプリとAPI | GraphQL Admin API、Webhook、認証と権限、管理画面の拡張 | 自社専用のアプリ、公開アプリの開発 |
| チェックアウトと割引 | チェックアウトの拡張、Shopify Functions | 規模の大きいストアの改修、移行 |
| 外部システム連携 | 受注管理・在庫・基幹・物流との注文と在庫の受け渡し | 業務システムとの連携、移行 |
| ヘッドレス | テーマの外で画面を作り、APIで商品とカートを扱う | 独自の体験を作るストア |

## テーマ開発：運用担当が編集しやすい形で作れるか

Shopify.devのテーマの構成の説明では、テーマはLiquidでHTMLを組み立て、ページの種類ごとのテンプレート、運用担当が画面で編集できる部品であるセクションとブロック、運用担当からは見えない再利用の部品であるスニペットなどで成り立つと説明されています。JSONのテンプレートはセクションを並べる入れ物として働きます。

案件で差がつくのは、Liquidを書けることよりも、**どこを運用担当に任せ、どこをコードで固定するか**の設計です。設定項目を増やしすぎるとテーマが複雑になり、少なすぎると小さな変更のたびに開発者が呼ばれます。また、Shopify.devでは、テーマ内のLiquidとJSONの誤りを見つけるリンターとしてTheme Checkが紹介され、Shopify CLIから手元やCIで実行できると説明されています。こうした道具をチームの開発の流れに組み込めると評価されます。

あわせて、画像の扱いやスクリプトの読み込みによる表示速度の改善、入れたアプリがテーマに足すコードの把握も、運用中のストアでよく求められます。

## アプリとAPI：GraphQLとWebhookを正しく扱えるか

Shopify.devのREST Admin APIのページでは、REST Admin APIは2024年10月1日にレガシーとなり、2025年4月1日以降、新しい公開アプリはGraphQL Admin APIだけで作る必要があると案内されています。これから関わるアプリや連携では、**GraphQL Admin API**を前提に考えるのが基本です。古い連携の処理がRESTのまま残っている案件では、置き換えの経験が問われます。

Webhookの扱いも大切です。Shopify.devのWebhookの説明では、配信は保証されず、同じ通知が重なることも、同じ種類の通知の順番が前後することもあると明記され、署名（HMAC）の検証、重複の除外、定期的にデータを取り直す照合の処理が勧められています。**通知が来なかったら、二重に来たら、順番が逆だったら**を設計に入れられるかは、面談でもよく問われる点です。

アプリの作り方そのものは、Shopify CLIでひな形を作り、管理画面やチェックアウトなどに画面を差し込む拡張や、デザインシステムのPolarisを使う流れがShopify.devで紹介されています。ストアの運用担当がどの画面からアプリを使うかを想像して作れる人が評価されます。

## チェックアウトと割引：Plusの仕組みを理解しているか

チェックアウトの表示や、割引・配送方法の出し分けなどの処理は、売上に直結する部分です。Shopify.devのFunctionsのページでは、Shopify Functionsは、配送の選択肢や新しい割引の種類、カートとチェックアウトの検証など、チェックアウトの過程で独自の処理を動かす仕組みと説明されています。WebAssemblyにコンパイルできる言語で書け、性能の面からRustが強く推奨されています。また、Functionsを含むカスタムアプリを使えるのはShopify Plusのストアに限られます。

このため、チェックアウトや割引の経験は、Plusのストアの案件で特に問われます。処理の時間や入力の大きさに上限がある仕組みなので、**大きなカートでも動くように作れるか**が見られます。

## 外部システム連携：注文の状態をずれなく渡せるか

受注管理、在庫、基幹、倉庫、CRMとの連携の案件では、技術よりも**ECの業務の流れの理解**が問われます。注文のキャンセル、一部の出荷、返品、在庫数の反映の遅れなど、例外のときにどちらのシステムを正とするかを決められる人が求められます。業務の流れは[EC・通販業界の業務知識の記事](/media/ind-ec-chishiki/)で解説しています。

決済に関わる部分では、カード情報を自社のシステムに通さない前提を崩さないことが前提です。カード情報の扱いのルールは[EC・通販業界の規制の記事](/media/ind-ec-kisei/)と[クレジットカード・決済業界の規制の記事](/media/ind-card-kisei/)に譲ります。

## ヘッドレス：テーマを使わない判断ができるか

Shopify.devでは、HydrogenはShopifyのヘッドレス向けの道具で、カートやバリエーションの選択、Storefront APIの呼び出しなどを、Next.jsやReact Router、Nuxt、Astro、SvelteKitなど、サーバー側のコードを動かすフレームワークに足す形で使えると説明されています（2026年10月時点）。

ヘッドレスの案件では、ReactなどのフロントエンドのスキルとSEO、性能の知識に加えて、**テーマで足りることをヘッドレスで作らない判断**も求められます。運用担当がテーマの編集画面で済ませていた作業を、別の仕組みで用意する必要が出るためです。フロントエンドの技術は[Reactエンジニアのスキルの記事](/media/react-skills/)をご覧ください。

:::view
ECやShopifyの案件をご紹介していると、面談で評価が安定しやすいのは、技術の名前よりも「その仕組みを選ばなかった理由」を話せる方です。既製のアプリで済ませた判断、テーマで済ませた判断、自分で作った判断を、それぞれ理由つきで説明できると、ストアを任せられる人として伝わります。
:::

## 経験の段階ごとの目安

| 段階 | 担える仕事の目安 | 次に足したい経験 |
|---|---|---|
| テーマの改修が中心 | 既存テーマのセクション追加、表示の修正、アプリの導入と設定 | 商品の独自項目の設計、表示速度の改善 |
| ストアを一人で任される | 構築から公開、運用担当への引き継ぎ、簡単なアプリや連携 | GraphQL Admin APIとWebhookを使ったアプリ |
| 仕組みを設計する | 移行の計画、外部システム連携の設計、チェックアウトや割引の処理 | 体制づくり、事業側との要件の整理 |

段階が上がるほど、コードを書く量よりも、**何を設定で済ませ、何を作るかを決める比重**が増えます。報酬との関係は[ECサイト・Shopifyエンジニアの報酬の記事](/media/ec-engineer-rate/)で扱っています。

:::caution
Shopifyの仕組みは、APIのバージョンが3か月ごとに更新されるなど、変化が速い分野です。以前の案件で使った書き方が、今は推奨されていないこともあります。スキルとして話すときは、いつ時点の仕組みで経験したかを添えると、面談での食い違いを防げます。
:::

:::view
当社では、経歴はご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。ECの案件は、テーマ中心か、アプリや連携中心かで、合う案件がほとんど重なりません。どの分野が中心かを、スキルシートの冒頭で伝わる形にしておくことをおすすめします。
:::

:::point
- 問われる分野は、テーマ・アプリとAPI・チェックアウトと割引・外部システム連携・ヘッドレスの5つ
- 新しいアプリや連携はGraphQL Admin APIが前提で、Webhookは重複・順不同・欠落を想定して作る
- 段階が上がるほど、設定で済ませるか作るかを決める判断が問われる
:::

## よくある質問

### Liquidが書ければShopifyの案件に入れますか？

テーマの改修の案件には入りやすくなります。ただ、運用担当が編集しやすいセクションの設計や、表示速度の改善、アプリが足すコードの把握まで求められることが多いため、Liquidの文法だけでなく、テーマ全体の構成を説明できるようにしておきましょう。

### Rustを書けないとShopify Functionsの案件は難しいですか？

Shopify.devではRustが強く推奨されていますが、WebAssemblyにコンパイルできる言語で書けるとされ、JavaScriptの例も示されています。案件で使う言語は発注側の方針で決まるため、面談で確かめましょう。

### RESTのAPIしか使ったことがありません。不利になりますか？

古い連携が残る案件では、RESTの経験がそのまま役に立ちます。ただ、新しい公開アプリはGraphQL Admin APIで作る必要があるため、GraphQLでの取得と更新を一度は試し、置き換えの考え方を説明できるようにしておくことをおすすめします。
