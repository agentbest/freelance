クラウドアーキテクトの案件で問われるのは、**要件を整理して数字にする力**、**クラウドを使い分ける判断**、**ネットワークの接続とIDの設計**、**ガバナンス（共通のルールと統制）**、**費用の管理**、**可用性と災害対策**、**移行の計画**、**合意をつくる力**の8分野です。個別のサービスを使いこなす力より、分野どうしのかね合いを判断し、その理由を説明できることが重く見られます。

この記事では、分野ごとに案件で何が問われるかと、経験の段階ごとに求められる水準を整理します。特定のクラウドのサービスや操作の知識は、[AWSのスキルの記事](/media/aws-skills/)、[Azureのスキルの記事](/media/azure-skills/)、[GCPのスキルの記事](/media/gcp-skills/)で扱っています。

## 判断の物差しになる各社の設計フレームワーク

クラウドアーキテクトの判断は、主要な3社が公開している設計の枠組みと重なります。2026年10月時点の公式ページでは、次のように整理されています。

| 枠組み | 柱（観点） |
|---|---|
| AWS Well-Architected Framework | 運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コスト最適化、持続可能性の6つ |
| Azure Well-Architected Framework | 信頼性、セキュリティ、コストの最適化、オペレーショナルエクセレンス、パフォーマンス効率の5つ |
| Google Cloud Well-Architected Framework | 運用の優秀性、セキュリティ・プライバシー・コンプライアンス、信頼性、コスト最適化、パフォーマンス最適化、持続可能性の6つ（AI・機械学習と金融サービスの観点も別に用意） |

名前や数は少しずつ違いますが、観点はほぼ共通です。複数のクラウドをまたぐ案件では、この共通部分を物差しにして、クラウドごとの違いを説明できることが求められます。面談で「何を基準に構成を評価するか」を聞かれたときも、この枠組みに沿って話すと伝わりやすくなります。

## 分野ごとに問われるスキル

### 1. 要件の整理と数字にする力

止まってよい時間、データを戻せる時点、応答の速さ、データを置ける場所、予算の上限など、構成を決める前提を発注側と話し合って数字にする力です。前提があいまいなまま構成を決めると、後から作り直しになります。何を決めずに進むと困るかを先に示せることが見られます。

### 2. クラウドの使い分けの判断

どのシステムをどのクラウドに置くか、既存の契約や社内の技能、データの所在、使いたいサービスなどを比べて決める力です。「複数のクラウドを使うこと」そのものが目的になっていないかを見極め、一つにまとめたほうがよい場面ではそう提案できることも含みます。

### 3. ネットワークの接続とIDの設計

クラウドどうし、クラウドとオンプレミスをどうつなぐか、IPアドレスの割り当てが重ならないか、名前解決をどうするかを決める力です。あわせて、社員や外部の作業者がどのIDで各クラウドに入るか、権限をどの単位で渡すかの設計が問われます。境目の設計は、個別クラウドのエンジニアが手を出しにくい部分で、アーキテクトの出番になりやすい領域です。ネットワークの専門性は[ネットワークエンジニアのスキルの記事](/media/network-skills/)で扱っています。

### 4. ガバナンス

複数のチームが同じクラウドを安全に使えるよう、アカウントやサブスクリプションの分け方、ポリシーによる制限、ログの集約、タグ付けのルールを決める力です。MicrosoftのCloud Adoption Frameworkは、Azureランディングゾーンを、ガバナンスやセキュリティ、共有の機能を一元的に持つ「プラットフォームランディングゾーン」と、各ワークロードのチームがその枠の中で使う「ワークロードランディングゾーン」に分けて説明しています。こうした「共通の土台」と「各チームの領域」の線引きを決める考え方は、他のクラウドでも共通して問われます。

### 5. 費用の管理

クラウドの費用を、チームや製品ごとに分けて見える化し、使い方を見直す仕組みを作る力です。FinOps Foundationが公開しているFinOps Frameworkは、取り組みを「Inform（見える化）」「Optimize（最適化）」「Operate（運用）」の3つの段階で整理し、使用量と費用の理解、ビジネス価値の定量化、使用量と費用の最適化、実践の管理という4つの領域を挙げています（2026年10月時点）。設計の段階で費用の見込みを示し、運用に入ってから見込みとの差を説明できることが見られます。

### 6. 可用性と災害対策

どの障害まで耐えるか（機器、データセンター、地域）を決め、目標の復旧時間と復旧時点に合わせて構成を選ぶ力です。可用性を上げるほど費用と運用の手間が増えるため、システムごとに水準を分けて提案できることが評価されます。運用の信頼性を高める仕組みは[SREのスキルの記事](/media/sre-skills/)が参考になります。

### 7. 移行の計画

現行のシステムを調べ、そのまま載せ替えるか、作り直すか、廃止するかを決め、移行の順番と切り替えの方式を計画する力です。旧環境を止めるまでの段取りと、移行中に二重にかかる費用まで見込めることが求められます。

### 8. 合意をつくる力

選択肢とかね合いを、技術者でない人にも判断できる形で示し、決まったことを文書に残す力です。情報システム部門、セキュリティ担当、経理、各開発チームなど、立場の違う相手の要望を一つの方針にまとめる場面が多くあります。

## セキュリティの位置づけ

セキュリティは8分野すべてにかかわります。クラウドアーキテクトに求められるのは、権限の分け方、ログの集め方、データの暗号化と置き場所などを、ガバナンスや接続の設計の中に組み込むことです。脅威の分析や監査対応を専門に担う役割は、クラウドセキュリティエンジニアの案件として分かれることが多くあります。

:::view
クラウドアーキテクトの案件の面談では、構成図の説明のあとに「その構成で月々の費用はどう決まっていたか」「障害のときに誰がどこまで操作できたか」と、費用と権限の質問が続く場面がよく見られます。8分野のうち、費用とガバナンスは経験を語れる方が比較的少なく、話せると評価されやすい傾向があります。これまでの案件で、費用の内訳と権限の分け方を自分の言葉で説明できるように整理しておくことをおすすめします。
:::

## 経験の段階ごとに求められる水準

| 段階 | 求められる水準 | 合う案件の形 |
|---|---|---|
| 一つのクラウドで設計できる | 1・6の分野を一つのクラウドで判断でき、理由を文書にできる | 特定システムの構成設計、設計レビューの補助 |
| 共通の土台を設計できる | 3・4・5の分野を、複数のチームが使う前提で設計できる | 共通基盤・ガバナンスの設計、ランディングゾーンの整備 |
| 複数の環境をまたいで判断できる | 2・7の分野で、クラウドどうしやオンプレミスとの比較から方針を決められる | 移行計画、クラウドの使い分けの方針づくり |
| 組織の方針を決められる | 8の分野で、経営や複数部署との合意をつくり、方針を運用に落とし込める | 全社のクラウド利用方針、複数ベンダーをまたぐ設計の取りまとめ |

段階は飛び越えにくく、下の段階の経験が上の段階の説得力になります。たとえば、共通の土台を設計した経験がないまま全体方針の案件に入ると、方針を運用に落とす段階で具体策が出せず、評価を落としやすくなります。

## 資格はどう見られるか

設計系の認定資格は、知識の範囲を示す裏付けとして書類の段階で読まれます。ただ、案件で重く見られるのは、上の8分野での判断の実績です。資格が効くのは、実務で深く関わっていないクラウドの案件に広げたいときや、経験年数が短いときです。各資格の範囲と効く場面は、[AWS認定ソリューションアーキテクトの記事](/media/cert-aws-saa/)、[Google Cloud認定 Professional Cloud Architectの記事](/media/cert-gcp-pca/)、[Azureの認定資格の記事](/media/cert-azure/)で扱っています。

:::caution
「マルチクラウドの経験」と書くと、読み手は複数のクラウドをまたいで設計した経験だと受け取ります。実際には、AWSの案件とAzureの案件を別々に経験しただけの場合は、その違いが面談で分かると評価を下げることがあります。クラウドをまたいで何を決めたのか（接続、ID、ルールの共通化など）を具体的に言える範囲で書きましょう。
:::

:::view
当社では、案件をご案内するときは、先に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せて提案しています。クラウドアーキテクトの案件は、上の表のどの段階を求めているかが案件ごとに違うため、ご自身の経験がどの段階に当たるかを整理しておくと、ミスマッチの少ない案件選びにつながります。
:::

## よくある質問

### クラウドアーキテクトに、プログラミングやIaCのスキルは必要ですか？

多くの案件で、IaCのコードを読んで設計どおりかを確かめる力は求められます。自分で書くかどうかは案件によりますが、共通基盤の設計では、ルールをコードで配る前提の現場が増えています。書けなくても、レビューができる水準は持っておくと安心です。

### セキュリティの専門知識はどこまで必要ですか？

権限の分け方、ログの集め方、暗号化とデータの置き場所を、設計の中で判断できる水準は求められます。脅威の分析や監査への対応までを深く担う場合は、セキュリティを専門とする役割と分担することが多くなります。

### 3つのクラウドすべてに詳しくないと案件に入れませんか？

すべてに深い経験がなくても参画できる案件はあります。多くの場合、一つのクラウドの深い経験と、もう一つのクラウドの考え方を比べて説明できる力があれば、使い分けや接続の議論に加われます。3社の設計フレームワークの共通点と違いを押さえておくと、知らないクラウドでも話の糸口をつかみやすくなります。
