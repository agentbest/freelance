React Nativeエンジニアのフリーランス案件の仕事は、**ReactとTypeScriptで画面と機能を作ることを軸に、両OSでの動作確認、ビルドと配信、版上げまでを少人数で回すこと**です。ただし、アプリの段階と、チームにネイティブのエンジニアがいるかどうかで、1日の時間の使い方も成果物も大きく変わります。

この記事では、React Nativeの案件を5つの種類に分け、それぞれの1日と1か月の流れ、関わる相手、成果物を整理します。報酬の決まり方は[React Nativeの報酬の記事](/media/react-native-rate/)、求められるスキルは[React Nativeのスキルの記事](/media/react-native-skills/)で扱っているので、ここでは「参画したら実際に何をしているか」に絞ります。

## 仕事の中身は「アプリの段階」と「JavaScriptの外を誰が持つか」で決まる

React Nativeの案件は、同じ「アプリ開発」の募集でも中身が違います。違いを生むのは、主に次の2つです。

- **アプリの段階**：これから作るのか、運用中なのか、古い版からの移行が必要なのか
- **JavaScriptの外を誰が持つか**：Xcodeやビルドの設定、ネイティブのモジュール、ストアへの公開を、自分が持つのか、ネイティブのエンジニアや別の担当がいるのか

この2つを掛け合わせると、フリーランスのReact Native案件はおおむね次の5種類に分けられます。

| 案件の種類 | 主な相手 | 時間を多く使う仕事 |
|---|---|---|
| 新規アプリの立ち上げ | プロダクトの責任者、デザイナー、API側のエンジニア | 構成の選定、画面と機能の実装、初回のストア公開 |
| 運用中アプリの改善 | 企画の担当者、QA、カスタマーサポート | 機能の追加、不具合の修正、定期的なリリース |
| 版上げ・移行 | テックリード、ネイティブのエンジニア | 依存ライブラリの調査、New Architectureへの対応、回帰の確認 |
| ネイティブアプリへの部分導入 | iOS・Androidのチーム | 一部の画面をReact Nativeで作り、既存アプリに組み込む |
| Webチームでのアプリ担当 | Webのフロントエンドとバックエンドのメンバー | Webと共通の仕組みづくり、アプリ固有の部分の担当 |

以下では、それぞれの流れを典型的な例として紹介します。時間の配分は案件ごとに違うため、目安として読んでください。

## 新規アプリの立ち上げ案件

### 1日の流れ（例）

午前はデザインのデータと仕様を見ながら画面を組み、午後はAPI側のエンジニアとレスポンスの形や認証の流れをすり合わせます。夕方は、iOSとAndroidの実機やシミュレーターで当日の変更を確かめ、確認用のアプリをチームに配ります。立ち上げの初期は、ナビゲーションや状態管理の方式、Expoを使うかどうか、ビルドと配信の仕組みを決める打ち合わせにも時間を使います。

### 1か月の流れ（例）

- **月初**：その月に作る画面と機能を、プロダクトの責任者と優先順位をつけて決める
- **毎週**：確認用のアプリを配り、関係者から画面の動きについて意見をもらう
- **月の半ば**：プッシュ通知、決済、ログインなど、ネイティブの設定が要る機能に取りかかる
- **月末**：初回公開の前なら、ストアに出す情報やプライバシーの記載の準備を進める

### 成果物

画面と機能のコード、プロジェクトの構成と設計の方針をまとめた文書、ビルドと配信の手順、ストア公開の準備の一覧などです。立ち上げでは、**後から入る人が迷わない土台**を残すことも仕事に含まれます。

## 運用中アプリの改善案件

### 1日の流れ（例）

朝は、クラッシュの報告やサポートに届いた問い合わせを確かめ、優先して直すものを決めます。日中は機能の追加や改修を進め、プルリクエストのレビューをやり取りします。不具合が「Androidの特定の機種だけ」「iOSの古い版だけ」のように片方のOSで起きることも多く、再現の条件を絞り込む作業に時間がかかる日もあります。

### 1か月の流れ（例）

- **毎週〜隔週**：決まった周期でリリースし、ストアの審査の結果を確かめる
- **随時**：JavaScriptだけの軽い修正は、Expoの現場ならストアを通さない配信で届ける
- **月末**：クラッシュの件数や評価の変化を見て、翌月の改善の候補を挙げる

ストアを通さない配信は便利ですが、Expoの公式ドキュメントでは、ネイティブのコードや権限、Expo SDKの版を変える変更は新しいビルドが要るとされています。**どの変更をどちらの経路で出すか**の判断も、日々の仕事の一部です。

### 成果物

改修したコード、テスト、リリースノート、不具合の調査の記録、配信の履歴などです。新規開発と保守の違いは[新規開発案件と保守案件の違い](/media/shinki-vs-hoshu/)でも解説しています。

:::view
React Nativeの案件をご紹介していると、「Reactの経験を生かして画面を作る仕事」と思って参画し、実際にはビルドの失敗やストアの審査への対応に多くの時間を使う現場だった、と気づく方がいます。特に運用中のアプリでは、JavaScriptの外の作業の比重が高くなりがちです。応募の段階で、ビルドとストア公開を誰が担っているかを聞いておくことをおすすめします。
:::

## 版上げ・移行の案件

React Nativeは2か月ほどの間隔で新しい版が出ており、公式が保守するのは最新の3つのマイナー系列です（2026年10月時点のReleases Overviewによる）。数年分の版上げが止まっているアプリでは、まとまった移行の仕事が生まれます。

### 1日・1か月の流れ（例）

最初の数週間は、**直すより調べる**期間です。使っているライブラリが新しい版とNew Architectureに対応しているかを一つずつ確かめ、置き換えが要るものを洗い出します。その後、段階を区切って版を上げ、そのたびに両OSでビルドし、主な画面の動作を確かめます。チームの他のメンバーが機能の開発を続けている場合は、版上げの作業と機能の変更がぶつからないよう、取り込みの時期を相談します。

### 成果物

依存ライブラリの調査の一覧、移行の計画と段階の区切り、置き換えたライブラリの記録、回帰の確認の結果、次の版上げのための手順書などです。移行の案件では、**なぜその順番で進めたか**を残しておくと、次の版上げの負担が軽くなります。

## ネイティブアプリへの部分導入の案件

SwiftやKotlinで作られた既存のアプリに、一部の画面だけをReact Nativeで加える案件です。React Nativeの公式ドキュメントには、既存のネイティブアプリにReact Nativeの画面や流れを組み込む手順が用意されています。

### 1日・1か月の流れ（例）

ネイティブのチームと並んで働くため、会議や進め方はネイティブ側に合わせることが多くなります。React Nativeの画面を作るだけでなく、ネイティブ側から渡されるユーザーの情報の受け取り方、画面の行き来、ビルドへの組み込みをネイティブのエンジニアと詰めます。1か月の単位では、どの画面をReact Nativeに移すかの判断材料を、性能や開発の手間の観点でまとめることもあります。

### 成果物

React Nativeの画面のコード、ネイティブ側との受け渡しの取り決め、ビルドに組み込む手順、導入の範囲を広げるかどうかの判断材料などです。

## Webチームでのアプリ担当の案件

Webの画面をReactで作っている会社が、同じチームでアプリも作るためにReact Nativeを選ぶ形です。Webとアプリで型の定義やAPIの呼び出し、業務の処理を共通にすることが多く、**Webとアプリの境目をどこに引くか**が仕事の中心になります。

1日の中では、Webのメンバーとのレビューや設計の相談が多く、アプリ固有の部分（端末の権限、通知、オフラインの扱い、ストアの事情）を説明する役割も担います。Webの側の仕事の中身は[Reactエンジニアの仕事内容](/media/react-shigoto/)をご覧ください。

## どの案件にも共通する仕事

種類が違っても、次の仕事はほぼすべてのReact Native案件にあります。

1. **両OSでの確認**：変更のたびに、iOSとAndroidの両方で動きを確かめる
2. **確認用アプリの配布**：どの版を、誰に、いつ配ったかをそろえる
3. **ストアへの対応**：審査の指摘への対応、ストアに出す情報やプライバシーの記載の更新
4. **依存の管理**：ライブラリの更新と、React NativeやExpoの版との相性の確認
5. **記録**：OSごとの差や、ビルドで詰まった点と解決策を残す

フリーランスならではの仕事として、**自分の稼働の記録と報告**もあります。ビルドの待ち時間や審査への対応は見えにくい作業なので、何に時間を使ったかを日々つけておくと、月末の精算や作業範囲の相談がしやすくなります。

:::caution
少人数の現場では、React Nativeの担当が「アプリのことは何でも」頼まれやすくなります。ストアのアカウントの管理、問い合わせへの回答、Webの画面の改修など、契約した業務の範囲から外れる仕事が少しずつ増えることがあります。引き受ける前に、契約の業務範囲に入るかを確かめましょう。考え方は[作業範囲が広がったときの契約の扱い](/media/scope-change/)で解説しています。
:::

## 関わる相手と、その相手に出すもの

| 相手 | 出すもの | 頻度の目安 |
|---|---|---|
| プロダクトの責任者・企画の担当者 | 進み具合、実装の難しさ、リリースの見通し | 週次 |
| デザイナー | OSごとの見え方の差、実装上の制約 | 随時 |
| API側のエンジニア | 必要なデータの形、エラーの扱い | 随時 |
| ネイティブのエンジニア | ネイティブ側の変更の依頼、受け渡しの取り決め | 随時 |
| QA・サポート | 確認用のアプリ、修正の内容、再現の条件 | リリースごと |

働く場所については、画面の開発や版上げはリモートで進めやすい一方、実機をそろえた通しの確認や機器との連携では対面が求められることがあります。詳しくは[React Nativeのリモート案件の記事](/media/react-native-remote/)をご覧ください。

:::view
当社では、案件をご案内する前に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。React Nativeの案件では、これまで担ってきた範囲が「画面まで」か「ビルドとストア公開まで」かで合う案件が変わるため、その点もあわせてお伝えいただくと照らし合わせやすくなります。案件票に書かれていない体制や作業の分担は、ご質問いただければ確認します。
:::

:::point
- React Nativeの仕事の中身は、アプリの段階と、JavaScriptの外を誰が持つかで大きく変わる
- 新規はビルドと配信の土台づくり、運用中は不具合とリリースの回し方、移行は依存の調査が中心
- 部分導入ではネイティブのチームとの受け渡し、Webチームでは境目の設計が仕事になる
- 両OSでの確認、配布、ストア対応、依存の管理、記録は、どの案件にも共通する
:::

## よくある質問

### React Nativeの案件では、SwiftやKotlinのコードを書くこともありますか？

あります。ネイティブのモジュールの改修や、部分導入の案件でのネイティブ側との受け渡しなどで、少しずつ書く場面が出てきます。どこまで求められるかは案件によって違うため、参画前に確かめておくと安心です。

### ストアへの公開はフリーランスが担当しますか？

現場によります。審査への提出まで任される案件もあれば、アカウントの権限は発注元の社員だけが持ち、フリーランスはビルドまでを担う案件もあります。権限の扱いは[React Native案件の選び方](/media/react-native-anken-erabi/)で解説しています。

### 参画して最初の1か月は何をすることが多いですか？

開発環境を整えて両OSでビルドを通し、アプリの構成と依存ライブラリの状況、リリースの流れを把握するところから始めるのが一般的です。初月の進め方は[React Nativeの参画初月にやること](/media/react-native-first-month/)で詳しく解説します。
