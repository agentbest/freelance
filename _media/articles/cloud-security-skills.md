クラウドセキュリティエンジニアのフリーランス案件では、**権限設計、ログの集約と検知、設定の監査（CSPM）、ゼロトラストの考え方に沿ったアクセスの設計、IaCの段階での予防、そして基準を具体的な設定に落とす力**が中心に見られます。どの分野でも、道具を有効にできることより、「何を防ぐためにその設定にしたか」を説明できるかで任される範囲が変わります。

この記事では、分野ごとに求められるスキルを、経験の段階（入り口・中核・統制を決める側）に分けて整理します。セキュリティ全般の分野（Webアプリの診断やインシデント対応など）は[セキュリティエンジニアのスキルの記事](/media/security-engineer-skills/)で扱っています。

## 分野ごとのスキルの早見表

| 分野 | 入り口の段階 | 中核の段階 | 統制を決める側 |
|---|---|---|---|
| 権限設計 | 役割ごとの権限を最小限で付けられる | 使われていない権限を見つけ、業務を止めずに減らせる | 組織全体の権限の分け方と例外の決まりを作れる |
| ログと検知 | 操作の記録を有効にし、集約先に送れる | 不審な操作の検知ルールを作り、誤検知を減らせる | 何を、どこに、どれだけ残すかの方針を決められる |
| 設定の監査 | 監査ツールの指摘を読み、意味を説明できる | 優先順位をつけ、是正まで進められる | 基準を選び、組織に合わせて調整できる |
| アクセスの設計 | 多要素認証やシングルサインオンを設定できる | 端末や利用者の状態を見てアクセスを制御できる | ゼロトラストの方針を環境全体に落とせる |
| 予防の仕組み | IaCのコードを読める | 危ない設定を本番に出る前に止めるチェックを入れられる | 組織の決まりをコードで管理し、例外の流れを作れる |
| 基準への対応 | 基準の項目を読める | 項目ごとにどの設定で満たすかを対応づけられる | 監査や評価の場で説明する資料を作れる |

## 権限設計：最小限を「保ち続ける」力

権限設計は、クラウドセキュリティの案件で最もよく問われる分野です。最初に最小限の権限を付けることより、**時間がたって増えた権限を見つけて減らし続ける**ことのほうが難しく、そこに経験の差が出ます。

AWSのIAM Access Analyzerを例にとると、外部と共有されているリソースの発見、使われていないロールやアクセスキーの発見、ポリシーの文法とベストプラクティスに照らした確認、操作の記録をもとにしたポリシーの生成といった機能があります（2026年10月時点のAWSの公式ドキュメントによる）。こうした機能の結果を読み、「この権限は本当に要らないのか」を業務の担当者と確かめながら減らした経験が、中核の段階の実績になります。

統制を決める側では、組織全体でどの操作を一律に禁止するか、緊急時に強い権限をどう貸し出して記録するかといった決まりを作ります。権限の考え方はクラウドごとに違うため、AzureやGoogle Cloudの案件では、それぞれの仕組みの違いを説明できることが求められます。クラウドごとの基礎は[Azureエンジニアのスキルの記事](/media/azure-skills/)や[Google Cloudエンジニアのスキルの記事](/media/gcp-skills/)も参考になります。

## ログと検知：後から「追える」状態を作る

クラウドでは、誰がいつどの設定を変えたかを記録できます。ただし、記録を有効にしていなかったり、アカウントごとにばらばらに置かれていたりすると、問題が起きたときに追えません。

- **入り口**：操作の記録とネットワークの記録を有効にし、決められた集約先に送る
- **中核**：権限の変更や記録の停止など、注意すべき操作を検知するルールを作り、誤検知を減らす
- **統制を決める側**：どの記録を、どこに、どれだけの期間残すか、誰が見られるかを方針として決める

政府情報システム向けには、デジタル庁が「脅威の検知・対応のためのログ取得・分析導入ガイドブック」（DS-222、2026年3月31日）を標準ガイドライン群の一つとして公開しています。公共の案件に関わる方は目を通しておくと、求められる水準の目安になります。

## 設定の監査（CSPM）：指摘を「直る順」に並べる

設定の監査の道具は、主要なクラウドにそろっています。AWSのSecurity Hub CSPMは、AWSのベストプラクティスの基準やCIS、PCI DSS、NISTの基準に照らして設定を継続的にチェックし、多くのチェックでAWS Configを使います。Google CloudのSecurity Command Centerは、設定の誤り、外部に公開されたリソース、漏れた認証情報などの問題を見つける仕組みです（いずれも2026年10月時点の公式ドキュメントによる）。

案件で問われるのは、道具の有効化より次の力です。

1. **誤検知を見分ける**：業務の事情で意図的にそうしている設定を、根拠をつけて除外する
2. **優先順位をつける**：外部から届くか、重要なデータに触れるかなど、影響の大きさで並べる
3. **是正の手順を決める**：運用を止めずに直す順番と、直したことの確かめ方を決める
4. **再発を防ぐ**：同じ指摘が新しい環境で出ないよう、予防の仕組みに変える

:::view
クラウドセキュリティの案件をご紹介していると、評価されやすいのは、監査ツールの指摘の件数より「件数の多い指摘をどう束ね、どこから直したか」を話せる方です。たとえば、同じ原因から出ている指摘をまとめて一つの設定の見直しで解消した、といった進め方は、仕事の進め方そのものが伝わります。守秘義務で詳細を話せない場合も、判断の手順を一般化して話せれば十分です。
:::

## ゼロトラストの考え方に沿ったアクセスの設計

ゼロトラストは、ネットワークの内側にいることや会社の資産であることだけを理由に信頼しない、という考え方です。米国のNISTが2020年8月に公表したSP 800-207では、利用者や端末の認証と認可を、リソースへの接続の前にそれぞれ行うことや、ネットワークの区画ではなく資源そのものを守る対象にすることが示されています。日本でも、デジタル庁が「ゼロトラストアーキテクチャ適用方針」（DS-210、2022年6月30日）と、属性に基づくアクセス制御の技術レポート（DS-212）を公開しています。

案件では、この考え方を具体的な設定に落とす力が見られます。

- シングルサインオンと多要素認証を前提に、管理画面への入り口を一本化する
- 端末の状態や利用者の属性を条件にして、アクセスを許すかを決める
- 外部に公開する部分と内部の部分を分け、管理用の経路を絞る

「ゼロトラストを導入した」とだけ書くより、どの入り口に、どの条件を入れたかを説明できるほうが伝わります。

## IaCの段階での予防

本番に出てから直すより、IaCのコードの段階で危ない設定を止めるほうが、手戻りが少なく済みます。中核の段階では、コードの変更のたびに設定を確かめるチェックを開発の流れに組み込んだ経験が見られます。統制を決める側では、組織の決まりをコードで管理し、例外を認めるときの申請と記録の流れまで作ります。コンテナの環境が多い案件では、[Kubernetesエンジニアのスキルの記事](/media/kubernetes-skills/)で扱う基礎も前提になります。

## 基準を設定に落とす力

公共、金融、決済などの案件では、基準の項目ごとに「どの設定で満たしているか」を示す対応表が求められます。公共の案件で土台になる政府統一基準群やISMAPの位置づけは、[公共・官公庁業界の規制とセキュリティのルール](/media/ind-koukyou-kisei/)で解説しています。基準の文章を読み、技術者と監査の担当者の両方に説明できる人は限られるため、この力は統制を決める側に進むほど重みを増します。

:::caution
監査ツールの結果をそのまま報告書に貼り付けるだけでは、発注元にとっての判断材料になりません。誤検知や意図した設定が混ざったままだと、本当に直すべき指摘が埋もれます。報告には、除外した理由と、優先順位の根拠を書き添えることをおすすめします。
:::

:::view
当社では、先に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをご案内しています。クラウドセキュリティの案件は、同じ「権限設計」でも、決められた方針どおりに付ける役割と、方針そのものを決める役割で求められる段階が違います。募集の段階で役割が読み取りにくい点は、ご質問いただければ確認します。上の表で、ご自身がどの分野のどの段階にいるかを整理しておくことをおすすめします。
:::

## 資格との関係

資格は知識の裏付けとして見られます。AWSの範囲を深く示すなら[AWS認定セキュリティ–専門知識](/media/cert-aws-security/)、製品に依らない統制の知識を示すなら[CCSP](/media/cert-ccsp/)が候補です。どちらも、実務で上の表のどの分野をどの段階まで担ったかとあわせて伝えることが大切です。書き方は[クラウドセキュリティエンジニアのスキルシートの記事](/media/cloud-security-skillsheet/)で解説しています。

:::point
- 中心になる分野は、権限設計、ログと検知、設定の監査、アクセスの設計、IaCでの予防、基準への対応
- 権限は「最初に絞る」より「増えたものを減らし続ける」経験に差が出る
- 監査の指摘は、誤検知の除外、優先順位、是正、再発防止までつなげて初めて評価される
- ゼロトラストは、どの入り口にどの条件を入れたかまで説明できるようにする
:::

## よくある質問

### プログラミングはどの程度必要ですか？

大きなアプリを作る力より、IaCのコードを読んで直す力と、監査や検知の結果を集計する小さなスクリプトを書く力がよく求められます。予防の仕組みを作る段階に進むほど、コードで決まりを管理する場面が増えます。

### 複数のクラウドを扱えないと案件はありませんか？

一つのクラウドを深く扱える方向けの案件は多くあります。複数のクラウドの統制を求める案件では、権限やログの考え方の違いを説明できるかが見られるため、主軸のクラウドに加えてもう一つの基礎を押さえておくと選べる案件が広がります。

### 監査ツールの製品名を多く知っていると有利ですか？

製品名の数より、どの製品でも共通する「指摘の読み方」「優先順位のつけ方」「是正の進め方」を説明できるかが評価されます。使った製品は、その判断をどの環境で行ったかを示す補足として書くと伝わりやすくなります。
