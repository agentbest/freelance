データベースエンジニアのフリーランスは、**設計、SQLのレビュー、性能の調査、クラウドのマネージドデータベースの運用**を中心に、リモートで進められる案件があります。一方で、**本番データに直接触れる作業、社内の閉じたネットワークの中にあるデータベース、移行の切り替え当日の作業**は、出社や指定された端末での作業になりやすい傾向です。

リモートで働けるかどうかは、職種より「どのデータに、どこから触れるか」で決まります。この記事では、リモートで進めやすい仕事と進めにくい仕事、本番データに触れずに進める段取り、案件の探し方と確認点を整理します。

## リモートで進めやすい仕事・進めにくい仕事

| 仕事の種類 | 主な中身 | リモートとの相性 |
|---|---|---|
| 設計・レビュー | テーブル設計、インデックスの方針、SQLのレビュー | 進めやすい。資料とオンラインの打ち合わせが中心 |
| 性能の調査 | 実行計画や待機の情報の分析、改善案の作成 | 進めやすい。ただし本番の情報の取り出し方に決まりがあることが多い |
| クラウドのマネージドDBの構築・運用 | インスタンスの設定、パラメータ、版上げの計画 | 進めやすい。管理画面や接続の経路が整っていれば場所を問わない |
| オンプレミスの運用保守 | 監視、定型作業、障害対応 | 体制による。社内のネットワークからしか入れない環境では出社になる |
| 移行の切り替え | 停止、データの移動、確認、戻し | 計画と予行はリモート、当日は現地や指定の部屋になりやすい |
| 個人情報・決済データを扱う作業 | 本番データの調査、データの修正 | 指定された端末や部屋に限られやすい |

同じ案件でも、設計や調査はリモート、本番への反映だけは出社という形はよくあります。「どの作業をどこから行うか」を作業の単位で確かめておきましょう。リモート案件全般の探し方は[フルリモート案件の記事](/media/full-remote/)にまとめています。

## 出社や指定端末が求められやすい理由

データベースの案件で出社が条件になるのは、多くの場合、データの重さとネットワークの都合です。

- **データベースが閉域網の中にある**：社内のネットワークからしか接続できず、外からの経路を作らない方針をとっている
- **本番データに個人情報や決済情報が含まれる**：取引先が委託先の作業環境まで管理する必要があり、作業場所や端末を決めている
- **作業の記録を残す仕組みが社内にある**：本番への接続を、記録が残る専用の端末や踏み台からに限っている
- **切り替えや障害のときに関係者が集まる**：判断を素早く行うため、当日は同じ部屋に集まる体制にしている

取引先が個人データの取り扱いを委託する場合、委託先を監督する立場にもなります。リモートの可否は、こうした取引先側の事情から決まることが多いため、条件の交渉より、**どうすれば決まりの中で作業できるか**を一緒に考える姿勢が伝わりやすくなります。委託で個人情報を扱うときの考え方は[個人情報の取り扱いの委託の記事](/media/kojin-joho-itaku/)で解説しています。

## 本番データに触れずにリモートで進める段取り

### 検証用のデータを先に用意してもらう

性能の調査や設計の検討は、本番と同じ構造で、件数や偏りが近いデータがあれば多くを進められます。個人情報を含む列を置き換えたデータや、件数だけをそろえたデータを用意できるかを、参画の初めに相談しておくと、リモートで進められる範囲が広がります。

### 本番の情報は「中身」ではなく「統計」で受け取る

性能の調査に必要なのは、多くの場合、実行計画、待機の情報、表の件数や容量といった統計の情報です。データそのものを見なくても、原因の多くは絞り込めます。本番から何を取り出してよいかを取引先と決め、決まった経路で受け取りましょう。

### 変更は手順書とスクリプトで渡す

本番への変更は、手順書と実行するスクリプト、戻すためのスクリプトをそろえて渡し、承認を受けてから実行します。実行を取引先の担当者が行う形なら、自分は本番に入らずに済む場合もあります。

### 作業の記録を自分でも残す

離れた場所から本番に関わる作業では、いつ、何を、誰の承認で実行したかを、取引先の決まりに沿って記録しておくことが大切です。何か起きたときに経緯を説明できるだけでなく、次の作業の手順書にもそのまま使えます。記録を手元の端末に保存してよいかは、取引先の決まりで確かめましょう。

### 夜間作業と呼び出しの範囲を決める

マネージドDBのメンテナンスや版上げは、利用者の少ない時間帯に行うことが多くあります。夜間の作業や障害時の呼び出しがあるか、その時間をどう精算するかを、参画前に確かめておきましょう。

:::view
データベースの案件をご紹介していると、リモートの案件で評価されやすいのは、「本番に入らずに原因を絞り込んだ」「手順書とスクリプトで変更を渡した」といった、離れた場所から安全に進めた経験を話せる方です。こうした経験は、リモートの可否を判断する取引先にとって安心材料になります。スキルシートにも、作業の進め方を1行添えることをおすすめします。
:::

## 端末・接続・情報管理で確かめること

| 確かめること | 内容 |
|---|---|
| 端末 | 取引先から貸与されるか、私物を使うか。私物の場合の条件 |
| 接続の経路 | VPN、仮想デスクトップ、踏み台など、どこから何に入るか |
| 本番の権限 | 参照だけか、変更もできるか。変更の承認の流れ |
| データの持ち出し | 調査の結果やログを手元に保存してよいか |
| 作業の時間帯 | 夜間・休日の作業、障害時の呼び出しの有無と扱い |
| 出社の頻度 | 定例や切り替えの日など、出社が必要な場面 |

秘密保持の取り決めは[NDAの記事](/media/nda/)で確かめ方を整理しています。

## リモート案件の探し方

### クラウドのマネージドDBの経験を前に出す

クラウドのマネージドDBの案件は、管理画面と接続の経路が整っていれば場所を問わないため、リモートの割合が高い傾向です。たとえばAmazon RDSでは、標準サポートを過ぎた版は有料のExtended Supportに移るため、版上げの計画を立てる仕事が生まれます（2026年10月時点のAWSの案内）。こうした計画や設計の仕事は、資料と打ち合わせで進められます。クラウド全般のリモート事情は[AWSエンジニアのリモートの記事](/media/aws-remote/)も参考になります。

### 「どこまでリモートで、どこから出社か」で条件を伝える

「フルリモート希望」とだけ伝えるより、「設計と調査はリモート、切り替えの当日は出社可」のように作業の単位で伝えると、合う案件の幅が広がります。

### 隣の職種の案件も見ておく

分析用のデータ基盤の案件は、本番の業務システムから離れているぶん、リモートで進めやすいことがあります。仕事の中身は違うため、[データエンジニアのリモートの記事](/media/data-engineer-remote/)で傾向を確かめておくとよいでしょう。

:::caution
「リモート可」とあっても、本番の作業だけは出社、障害時は駆けつけ、という条件が後から分かることがあります。また、私物の端末から本番のデータベースに接続することは、取引先の決まりに反するおそれがあります。フリーランス法では、発注事業者は給付の内容や役務の提供を受ける場所などを明示することが求められています。作業場所の条件が書面やメールで示されているかを確かめましょう。
:::

:::view
当社では、案件をご案内するときに、先に稼働日数・リモートの可否・ご希望の金額を伺い、合う案件だけをお出ししています。データベースの案件では、リモートの可否が作業の種類ごとに分かれていることが多いため、出社してもよい場面があれば、あわせてお伝えいただくことをおすすめします。契約では業務範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。
:::

:::point
- 設計・SQLのレビュー・性能の調査・マネージドDBの運用はリモートで進めやすい
- 本番データに触れる作業、閉域網の中の環境、切り替え当日は出社や指定端末になりやすい
- 検証用データ、統計の情報、手順書とスクリプトで、本番に入らずに進められる範囲が広がる
- 条件は「どの作業をどこから行うか」の単位で伝える
:::

## よくある質問

### オンプレミスのデータベースの運用でもフルリモートはありますか？

あります。ただ、社内のネットワークからしか接続できない環境では、出社や指定された接続の経路が条件になることが多い傾向です。仮想デスクトップや踏み台を経由して接続できる体制が整っているかを確かめましょう。

### 性能の調査で本番のデータを手元に持ってきてもよいですか？

取引先の許可なく持ち出すことはできません。多くの場合、実行計画や待機の情報など、データの中身を含まない情報で原因を絞り込めます。何を取り出してよいかを取引先と決め、決まった経路で受け取りましょう。

### 移行の切り替えの日だけ出社する条件はよくありますか？

よくあります。計画、予行、手順書づくりはリモートで進め、切り替えの当日は関係者が集まる形です。出社の日程と交通費の扱いを、参画前に確かめておくと安心です。
