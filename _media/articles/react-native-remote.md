React Nativeエンジニアは、**リモートで働ける案件が見つけやすい職種の一つ**です。JavaScriptで書く部分が多く、Expoを使う現場ではクラウドでのビルドや開発ビルドの配布の仕組みが整っているため、離れていても両OSの開発を回しやすいからです。ただし、**iOSの確認に使うMac、両OSの実機、署名の鍵やストアのアカウントの権限**をどう扱うかが、リモートで受けられるかどうかの条件になります。

この記事では、リモートで進めやすい仕事としにくい仕事、リモートで回すときの進め方、案件の探し方と契約前の確認点をまとめます。リモートの働き方そのものの一般論は[フルリモート案件の記事](/media/full-remote/)をご覧ください。

## リモートで進めやすい仕事・進めにくい仕事

| 仕事の種類 | リモートとの相性 | 理由 |
|---|---|---|
| 運用中アプリの画面・機能の追加 | 進めやすい | 既存の構成に沿ってJavaScriptの範囲で完結しやすい |
| 版上げやライブラリの置き換え | 進めやすい | 調査と修正が手元の環境で進み、結果を文書で共有できる |
| Webのチームと共通の仕組みづくり | 進めやすい | Reactの知識を持つメンバーと、コードとレビューでやり取りできる |
| 新規アプリの立ち上げ | 一部で対面がある | 業務の担当者と画面の流れを固める打ち合わせが対面になることがある |
| 機器と連携するアプリ | 進めにくい | Bluetoothでつなぐ機器や店舗の端末など、実物が手元に要る |
| 端末の管理が厳しい業界のアプリ | 進めにくい | 金融や医療などで、貸与の端末と社内の環境に限られることがある |

React Nativeの案件は、Webの開発チームがアプリも担う形で始まることが多く、Webのチームと同じくリモート中心で動いている現場が少なくありません。一方で、ネイティブのチームと並んで部分導入を進める案件は、ネイティブ側の働き方に合わせて出社が求められることがあります。

## 出社や対面が求められやすい場面

- **リリース前の通しの確認**：iOSとAndroidの複数の機種で、関係者がそろって動作を確かめる
- **実物の機器が要る開発**：機器との連携、店舗の端末、決済の端末などを使うアプリ
- **立ち上げの要件の打ち合わせ**：発注側の業務の担当者と画面の流れを決める初期の段階
- **情報管理の決まり**：開発用の端末を社外へ持ち出せない現場

受託の形で参画する場合は、発注元の打ち合わせに同席するかどうかで出社の頻度が変わります。どこまで発注元と直接やり取りするかを、面談で確かめておきましょう。

:::view
React Nativeの案件をご紹介していると、リモートかどうかに加えて「両方のOSを手元で確かめられる環境があるか」がよく確認される傾向があります。Macの有無、手元にあるiOSとAndroidの端末、ストアへの公開まで担った経験を、ご希望の条件とあわせて伝えていただくのがおすすめです。当社では、先に稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをご案内しています。
:::

## React Nativeをリモートで回す進め方

### 確認用のアプリの配り方をそろえる

Expoの公式ドキュメントでは、ストアに出す自分のアプリを作るなら、Expo Goではなく開発ビルドを使うことが勧められています。開発ビルドには、接続する開発サーバーや配信された更新を切り替える画面があり、離れた場所のメンバーも同じアプリで確認しやすくなります。EAS Buildにはチーム内で配布する仕組みもあります。

確認用のアプリを「誰が、いつ、どの版を」配るのかを決めておくと、「手元では直っているのに確認した人の画面では直っていない」というすれ違いを減らせます。

### ストア外の配信は、手順と基準を文書に残す

EAS Updateを使う現場では、JavaScriptや画像などをストアの更新を待たずに配信できます。一方、Expoの公式ドキュメントにあるとおり、ネイティブのコードや権限、Expo SDKの版を変える変更は配信できず、新しいビルドが必要です。リモートのチームでは、配信してよい変更の基準と、配信先（確認用か本番か）の取り違えを防ぐ手順を文書に残しておくと、事故が起きにくくなります。配信の内容は各ストアのルールに従う必要がある点も、チームで共有しておきましょう。

### OSごとの差は報告を分けて書く

不具合の報告では、iOSとAndroidのどちらで起きたか、機種とOSの版、開発ビルドか本番か、配信された更新の版を分けて書きます。離れた場所では画面を指さして確かめられないため、条件を書き分けることが調査の速さに直結します。

## 端末・アカウント・署名の扱いで確かめること

React Nativeのリモート案件では、ソースコードよりも「署名の鍵」と「ストアのアカウント」の扱いが問題になりやすい傾向があります。EAS Buildは、Androidの鍵やiOSのプロビジョニングプロファイル、配布用の証明書を作って管理することもできるため、誰がどこで管理しているかを確かめておく必要があります。

| 確かめること | 理由 |
|---|---|
| 開発に使うMacと端末は貸与か私物か | 私物を使えない現場や、検証用の機種の指定がある |
| 署名の鍵と証明書の管理者 | 紛失や漏えいはアプリの更新に関わる。自分の手元に置くかどうかも確かめる |
| ストアのアカウントの権限 | App Store ConnectやPlay Consoleで、どこまで操作してよいか |
| ビルドと配信のサービスのアカウント | 発注側の契約で使うか、個人のアカウントを使わせてもらうのか |
| ソースコードと検証データの持ち出しの決まり | 実在の利用者の情報を手元の端末に入れてよいか |

EAS Submitはストアへのアップロードまでで、iOSの審査への提出はApp Store Connectで行うと公式に説明されています。審査への提出を自分が担うのか、発注側が行うのかも、権限とあわせて決めておきましょう。

## リモート案件の探し方

### 「JavaScriptの外」まで一人で確かめられることを書く

リモートの案件では、近くに相談できるネイティブのエンジニアがいないことがあります。ビルドの失敗、ネイティブの設定、ストアの審査の指摘を自分で解決した経験を、スキルシートに具体的に書いておくと、リモートでも任せやすい人として見てもらえます。書き方は[React Nativeのスキルシートの書き方](/media/react-native-skillsheet/)をご覧ください。

### Webとアプリの両方を担う案件も視野に入れる

React Nativeを使う会社では、Webの画面とアプリの両方を同じチームが作っていることがあります。Reactの経験を生かして両方に関われると、リモートで長く続く案件につながりやすくなります。Webの側の働き方は[Reactのリモート案件の記事](/media/react-remote/)で解説しています。

### 常駐が前提の案件は条件を分けて比べる

フルリモートにこだわると、選べる案件が限られることがあります。立ち上げの初期だけ出社する、リリース前だけ対面で確かめるといった形も含めて比べると選択肢が広がります。常駐とリモートの選び方は[常駐案件とリモート案件の違いの記事](/media/jochu/)にまとめています。

:::caution
リモートの案件で、確認用の端末を「私物で用意してください」とされることがあります。その場合、端末にインストールした開発中のアプリや検証用のアカウントを、契約が終わったあとにどう消すかまで決めておかないと、情報管理の面で後から問題になることがあります。端末の扱いと契約終了時の対応は、参画前に確かめましょう。
:::

## 契約で確かめておきたいこと

2024年11月に施行されたフリーランス法では、発注する事業者は業務を委託したら直ちに、業務の内容・報酬の額・支払期日などを書面やメールなどで明示することとされています。リモートの案件では、出社の頻度と交通費の扱い、機器の貸与、作業する場所の決まりも、業務の範囲とあわせて書面で確かめておくと安心です。明示される条件の読み方は[フリーランス法で明示される取引条件の記事](/media/freelance-act-terms/)で解説しています。

:::view
当社では、業務の範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。リモートの案件では、出社の頻度や機器の貸与のように、案件ごとに差が出やすい点があります。気になる点は面談の前にご質問いただければ確認します。
:::

- React Nativeは、開発ビルドやクラウドのビルドを使えばリモートで両OSを回しやすい

## よくある質問

### WindowsのパソコンしかなくてもReact Nativeのリモート案件はできますか？

Androidの開発やJavaScriptの部分は進められますが、iOS向けの開発と確認にはMacが要る場面が多くあります。クラウドでのビルドを使う現場もありますが、iOSの実機での確認や不具合の調査まで考えると、Macを用意するか、貸与があるかを確かめてから応募しましょう。

### ストア外の配信の操作まで任されることはありますか？

少人数のチームでは任されることがあります。その場合は、配信してよい変更の基準と、本番へ配信する前の確認の流れを、発注側と合意しておくことが大切です。誤って本番へ配信した場合の戻し方も、あらかじめ決めておきましょう。

### 週2〜3日のリモート案件はありますか？

公開後の保守や版上げを中心にした案件では、稼働日数を抑えた形で続くものもあります。ただし、リリースの前後は対応が増えやすいため、稼働の変わり方と連絡の取り方を面談で確かめておきましょう。
