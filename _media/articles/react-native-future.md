React Nativeは、**0.82でNew Architectureだけで動くようになり、0.84でJavaScriptのエンジンにHermes V1が標準で使われるようになるなど、ここ1年ほどで土台が大きく入れ替わりました**（2026年10月時点の公式ブログ）。版は2か月ほどの間隔で出ており、公式が保守するのは最新の3つのマイナー系列です。この先のフリーランスの仕事は、新しい機能を作ることに加えて、**速く動く土台にアプリを追従させ続けること**が大きな柱になります。

この記事では、React Nativeの公式サイトとExpoの公式ドキュメントで確かめた動きをもとに、仕事の中身の変化と、経験に応じた広げ方を解説します。

## 公式の情報から見えるReact Nativeの現在地

2026年10月時点で、React Nativeの公式ブログでは次のような流れが発表されています。

| 版（公開時期） | 主な変化 |
|---|---|
| 0.82（2025年10月） | New Architectureだけで動く最初の版。従来のアーキテクチャに戻す設定は無視される |
| 0.84（2026年2月） | Hermes V1が標準のJavaScriptエンジンに。従来のアーキテクチャのコードの削除が進み、iOSではあらかじめビルドされたバイナリが標準に |
| 0.87（2026年8月） | 型の厳しいTypeScriptのAPIが標準に。iOSでSwift Package Managerへの対応が実験的に加わる。Node.js 22.13.0以上が必要に |
| 0.88（2026年10月） | 公式のバージョン一覧で最新版として掲載 |

Expoの公式ドキュメントでは、Expo SDKは年に3回出て、それぞれ一つのReact Nativeの版を対象にするとされています。2026年10月時点の最新のSDK 58は、React Native 0.88を対象にしています。

0.82の公式ブログでは、従来のアーキテクチャを使える最後の版は0.81とExpo SDK 54だとされていました。古いアプリをNew Architectureへ移す作業は、この先もしばらく案件として続くと考えられます。

## 「追従し続ける仕事」が厚くなる

React Nativeの公式の案内では、保守の対象は最新の3つのマイナー系列とされています。新しい版が2か月ほどの間隔で出るため、アプリを保守の範囲内に保つには、年に何度も版上げを検討する必要があります。

これにストアの要件が重なります。たとえばGoogle Playでは、2026年8月31日以降、新しいアプリとアプリの更新は、多くの場合Android 16（APIレベル36）以上を対象にする必要があるとされています（2026年10月時点のAndroid Developersの案内）。ストアの要件に合わせるには、React Native本体やライブラリの版上げが前提になることが多くあります。

フリーランスにとっては、この「追従の仕事」を計画的に回せることが、長く続く案件につながる強みになります。具体的には次のような力です。

- 版上げの前に、使っているライブラリの対応状況を確かめ、止まっているものの代わりを探す
- ビルドの道具の要件（Node.jsやKotlinの版など）の変化を読み、開発環境とCIを先に整える
- 版上げの手順を文書にし、次の版上げを他のメンバーでも進められるようにする

## 出す先は、スマートフォンの外にも広がっている

React Nativeの公式サイトでは、iOSとAndroid以外の出し先として、パートナーやコミュニティが保守するプロジェクトが紹介されています。macOSとWindows向け、visionOS向け、テレビ向け、Web向けなどです（2026年10月時点）。また公式ブログでは、2026年2月に「React Native Comes to Meta Quest」という発表もありました。

業務委託の案件はスマートフォンのアプリが中心ですが、社内向けのデスクトップのツールや、Webとアプリで部品を共有する仕組みづくりなど、モバイルの外へ広げる仕事も生まれています。どの出し先も、保守しているのが公式か、パートナーか、コミュニティかで、版上げへの追従の速さが違う点は押さえておきましょう。

:::view
React Nativeの案件をご紹介していると、長く声がかかる方には「新しい版が出たときに、自分のアプリで何が起きるかを先に調べている」という共通点が見られます。版上げを任せられる人は、機能の開発が落ち着いた後も契約が続きやすい傾向があります。今の案件で版上げに関わる機会があれば、手順と判断の記録を残しておくことをおすすめします。
:::

## 選択肢を広げる3つの方向

### ネイティブの側へ深く入る

New Architectureでは、JavaScriptとネイティブの間のやり取りの仕組みが変わりました。ライブラリが追いついていない部分を自分で直したり、小さなネイティブのモジュールを書いたりできる人は、版上げの多い時期に特に頼りにされます。SwiftやKotlinの経験を足す方向です。ネイティブ側の動向は[iOSの将来性の記事](/media/ios-future/)と[Androidの将来性の記事](/media/android-future/)を参考にしてください。

### Webとアプリをまたいで設計する

React Nativeは、Reactを使うWebのチームと考え方を共有できます。0.87で型の厳しいTypeScriptのAPIが標準になったこともあり、Webとアプリで型や部品を共有する設計を担える人の役割は広がっています。Webの側の動向は[Reactの将来性の記事](/media/react-future/)と[TypeScriptの将来性の記事](/media/typescript-future/)にまとめています。

### リリースと品質を担う

両ストアへの申請、ストア外の配信の基準づくり、自動テストとビルドの仕組みづくりは、少人数のチームでは誰かが担わなければならない仕事です。品質と配布の仕組みに軸足を置くと、開発の担当が入れ替わっても必要とされる役割になります。[テスト自動化の案件で求められるスキル](/media/test-automation-skills/)も参考になります。

## 経験に応じた広げ方

### React Nativeの実務が浅い時期

まずは、今の版での開発に慣れることが先です。そのうえで、開発ビルドを自分で作る、ネイティブのライブラリを一つ足す、といった「JavaScriptの外」の作業を一度経験しておきましょう。New Architectureが標準になってから始めた方は、従来のアーキテクチャのアプリを引き継ぐ案件で戸惑うことがあるため、古い構成のコードを読む機会も役に立ちます。

### 機能の開発を任されている時期

版上げを一度、主担当として通しでやるのがおすすめです。ライブラリの対応状況の調べ方、ビルドの道具の要件の変化への対応、問題が起きたときの切り分けを経験すると、引き継ぎの案件に応募できる幅が広がります。

### 設計やリードを経験している人

Webとアプリの共通化、ネイティブのモジュールの設計、版上げとリリースの仕組みづくりなど、チーム全体の進め方に関わる役割が視野に入ります。要件定義や技術選定など、上流の工程へ広げる考え方は[上流工程の記事](/media/upper-process/)で解説しています。Flutterと比べてどちらを伸ばすか迷う場合は、[Flutterの将来性の記事](/media/flutter-future/)もあわせて読むと判断の材料になります。

:::caution
新しい版や実験的な機能を追うことと、案件で使うことは別です。たとえば0.87のSwift Package Managerへの対応は、公式ブログで「本番ではまだ使わないこと」とされています。案件では、公式が実験的としている機能を勝手に取り入れず、発注側と合意したうえで、検証の範囲にとどめましょう。
:::

:::view
当社では、案件をご案内する前に、稼働日数・リモートの希望・ご希望の金額を伺い、合う案件だけをお出ししています。業務の範囲・報酬・支払期日・契約期間は個別契約に書いてお渡ししています。版上げや移行を中心にした案件は、調べてみないと作業量が見えにくいことがあるため、契約の形と範囲を参画前に確かめることをおすすめします。
:::

## よくある質問

### React Nativeはこの先も案件で使われ続けますか？

先のことは断定できませんが、2026年10月時点でも公式から2か月ほどの間隔で新しい版が出ており、Expoも年に3回SDKを出しています。すでに公開されているアプリの保守と版上げも続くため、今ある経験はしばらく生かせると考えられます。

### New Architectureへの移行を経験していないと不利になりますか？

New Architectureが標準になってから始めた方は、移行そのものを経験していなくても問題ありません。一方、従来のアーキテクチャのアプリを引き継ぐ案件では、移行の経験が評価されます。どちらの案件を目指すかで、補うべき経験が変わります。

### Flutterも覚えたほうがよいですか？

両方を同じ深さで身につける必要はありません。React Nativeの経験を軸にしつつ、ネイティブ側の知識を深めるほうが、どちらの技術の案件でも生かしやすい力になります。Flutterの動向は[Flutterの将来性の記事](/media/flutter-future/)で解説しています。
