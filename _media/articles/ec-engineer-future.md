ECサイト・Shopifyエンジニアのフリーランスの仕事は、**ストアを一から作る仕事の比重が下がり、動いているストアを新しい仕組みに追従させ、外の仕組みとつなぐ仕事**を中心に続くと考えられます。Shopifyは決まった周期でAPIの新しい版を出し、古い仕組みの提供を終える流れを続けているため、追従と置き換えの仕事が繰り返し生まれる構造になっています。

一方で、管理画面の設定や既製のテーマ、アプリの組み合わせでできる範囲は広がり、生成AIでコードを書く作業も速くなっています。選択肢を広げるには、**ECの業務を理解して仕組みを選ぶ力**と、**連携・データ・フロントエンドのどれかへの広がり**を持つことが近道です。この記事の公式の動向は、2026年10月時点のShopify.devとヘルプセンターの記載に基づきます。

## 公式の動向から見える3つの流れ

### 1. APIは3か月ごとに新しくなる

Shopify.devのAPIのバージョン管理のページでは、新しいバージョンは3か月ごとに、四半期の初日に出され、各安定版は少なくとも12か月サポートされると説明されています。サポートの切れた版を指定すると、使える最も古い安定版で応答が返る仕組みです。2026年10月時点の最新の安定版は2026-10です。

アプリや連携の処理を持つストアでは、このサイクルに合わせて変更点を読み、影響を調べ、使う版を上げる作業が定期的に発生します。**一度作って終わりではなく、追従し続ける仕事がある**ことが、Shopifyのエンジニアの仕事の前提です。

### 2. 古い仕組みが新しい仕組みに置き換わっている

ここ数年、Shopifyでは大きな仕組みの入れ替えが続いています。

| 対象 | 公式の記載（2026年10月時点） | 置き換え先 |
|---|---|---|
| REST Admin API | 2024年10月1日にレガシー。2025年4月1日以降の新しい公開アプリはGraphQLのみ | GraphQL Admin API |
| サンクスページ・注文状況ページのcheckout.liquidと追加スクリプト | 2025年8月28日に提供終了。Plus以外のストアのスクリプトタグは2026年8月26日に終了 | チェックアウトの拡張 |
| Shopify Scripts | 2026年6月30日に廃止 | Shopify Functions |

提供終了の日を過ぎても、古い作りのまま運用を続けているストアや、置き換えを急いで済ませた後の手直しが必要なストアがあります。**古い仕組みが何をしていたかを読み解き、新しい仕組みで同じことを実現する**仕事は、当面は続くと考えられます。

### 3. 画面とストアの外側への広がり

ストアの画面の作り方も広がっています。Shopify.devでは、ヘッドレス向けのHydrogenが、Next.jsやReact Router、Nuxt、Astro、SvelteKitなど、サーバー側のコードを動かすフレームワークに足して使える形で説明されています。

さらに、Shopify.devには、買い手の代わりにAIエージェントが商品を探し、カートを作り、チェックアウトへ進む仕組み（Universal Commerce Protocol）についての開発者向けの説明が掲載されています。一部は早期提供の段階です。こうした仕組みが実際の案件にどれだけ広がるかはまだ分かりませんが、**商品データや在庫、注文の状態を外の仕組みから正しく扱える形に整える**仕事の重みは増していくと考えられます。

## 残りやすい仕事と、変わりやすい仕事

| 仕事 | 見通し |
|---|---|
| 既製のテーマの軽い調整 | 設定や生成AIの支援で済む範囲が広がり、単独の仕事としては細りやすい |
| 運用担当が編集しやすいテーマの設計 | 運用の仕方を理解した設計が要るため、引き続き求められる |
| 仕組みの置き換え・APIの版の追従 | 公式の周期と提供終了に合わせて繰り返し生まれる |
| 受注・在庫・基幹との連携 | 業務の理解と例外の設計が要り、担える人が限られる |
| 商品データとデータ活用 | 外の仕組みとつなぐ前提として、重みが増す |

テーマの調整の経験が無駄になるわけではありません。ただ、コードを書く作業そのものは速くなっていくため、**何を作るかを決め、作ったものが業務で正しく動くかを確かめる側**に軸足を移していくと、選択肢を保ちやすくなります。

:::view
ECやShopifyの案件をご紹介していると、仕組みの入れ替えの時期には「新しい仕組みで作れる人」と同じくらい、「古い仕組みが何をしていたかを読める人」が求められる傾向があります。割引や表示の処理が、いつの間にか業務の決まりそのものになっていることが多いためです。過去に古い仕組みを扱った経験は、置き換えの案件で話せる材料として整理しておくことをおすすめします。
:::

## 選択肢を広げる方向

ECサイト・Shopifyの経験から広げやすい方向は、主に次の4つです。

1. **連携と業務システム**：受注管理、在庫、物流、基幹とのつなぎ込み。ECの業務の流れの理解が生きる（[EC・通販業界の業務知識の記事](/media/ind-ec-chishiki/)）
2. **フロントエンド・ヘッドレス**：ReactやTypeScriptを深め、テーマの外で画面を作る（[TypeScriptエンジニアの将来性の記事](/media/typescript-future/)）
3. **データ**：注文・会員・アクセスのデータを集めて分析に使う仕組み（[データエンジニアのスキルの記事](/media/data-engineer-skills/)）
4. **決済**：カード決済や後払いなど、決済の仕組みそのものに踏み込む（[クレジットカード・決済業界のIT案件の記事](/media/ind-card-it/)）

どれも、Shopifyの経験を捨てる方向ではなく、ECの経験を土台に隣の領域へ広げる方向です。

## 経験の段階ごとの広げ方

### テーマの改修が中心の段階

既製のテーマの調整が中心なら、まずは運用担当が編集しやすいセクションの設計と、表示速度の改善を、自分の言葉で説明できるようにします。そのうえで、GraphQL Admin APIを使った小さなアプリを開発用のストアで作り、テーマの外に一歩出る経験を作りましょう。

### ストアを一人で任される段階

構築から運用まで任されるようになったら、連携か仕組みの置き換えのどちらかを、計画から担う経験を足します。APIの版の更新を、変更点の確認から反映まで一人で回せるようになると、運用中のストアの案件で頼られやすくなります。

### 仕組みを設計する段階

移行や連携を設計する段階では、技術の選択よりも、事業側と「何を設定で済ませ、何を作るか」を決める役割の比重が増えます。業界のルール（[EC・通販業界の規制の記事](/media/ind-ec-kisei/)）や、運用の体制まで見て判断できると、上流から関わる案件の選択肢が広がります。

## 将来に備えて今からできること

日々の案件の中でも、次のような習慣を持っておくと、仕組みが変わったときに慌てずに済みます。

- **公式の変更履歴を定期的に読む**：APIの版の更新や提供終了の予定は、Shopify.devの変更履歴やドキュメントで先に告知されます。担当するストアに関係するものだけでも追っておきます
- **自分が作った処理の一覧を持つ**：どのストアで、どの版のAPIや、どの仕組みを使った処理を作ったかを控えておくと、提供終了の告知が出たときに影響をすぐ調べられます
- **業務の決まりを処理と結びつけて残す**：割引や配送の処理が、どの業務の決まりから来ているかを書き残しておくと、置き換えのときに同じ動きを再現しやすくなります

:::caution
Shopifyの新しい仕組みは、発表の段階と、実際に使える段階、Plusだけで使える段階が分かれていることがあります。新しい名前を追うだけでなく、自分の案件のストアで使えるかを公式のドキュメントで確かめる習慣をつけておきましょう。
:::

## よくある質問

### Shopifyのエンジニアの仕事はAIで減りますか？

テーマの軽い調整のように、設定や生成AIの支援で済む範囲は広がっています。一方で、仕組みの置き換え、業務システムとの連携、商品データの整備のように、業務の理解と確かめる作業が要る仕事は残りやすいと考えられます。作る作業より、何を作るかを決める側の経験を足していくことをおすすめします。

### Shopify Plusの仕組みを学んでおいたほうがよいですか？

Shopify Functionsを含むカスタムアプリはPlusのストアに限られるなど、Plusでしか使えない仕組みがあります。規模の大きいストアの案件に関わりたい場合は、開発用のストアで仕組みを試し、考え方を説明できるようにしておくと役に立ちます。

### Shopify以外のカートの経験も持っておいたほうがよいですか？

複数のカートを知っていると、移行の案件や、カートの選定から関わる案件で判断材料になります。ただ、浅く広く知るより、一つのプラットフォームで連携や置き換えまでやり切った経験のほうが、面談では伝わりやすい傾向があります。
