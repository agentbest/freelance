Rubyエンジニアがフリーランスになるには、**Ruby on Railsで機能を作れることに加えて、運用中のサービスを改修し、バージョンアップやテストで品質を守ってきた経験**が必要です。Rubyの案件は、自社サービスを持つ企業の少人数チームに入る形が多く、「入ってすぐ、既存のコードを読んで機能を出せるか」が見られます。

独立の準備は、経験の棚卸し、足りない経験の補強、スキルシートの作成、手続きとお金の準備の順に進めます。この記事では、Rails中心の現場ならではの見られ方に絞って整理します。

## Rubyの案件はRailsの自社サービスが中心

Rubyのフリーランス案件は、ほとんどがRailsを使ったWebサービスの開発です。どの段階のサービスに入るかで、求められる経験が変わります。

| 現場の型 | 主な仕事 | 特に見られる経験 |
|---|---|---|
| 新規サービスの立ち上げ | 少人数で機能を素早く作り、リリースを重ねる | 要件があいまいな中での実装、画面からDBまでの一通りの開発 |
| 運用中サービスの機能追加 | 長く続くコードに機能を足し、不具合を直す | 既存コードの読解、影響範囲の見極め、テストの追加 |
| Railsのバージョンアップ | 古いRuby・Railsを新しいものに上げる | 非推奨の置き換え、gemの更新、段階的なリリース |
| フロントとの分離・API化 | 画面をReactやVue.jsに移し、RailsをAPIにする | API設計、認証、フロント側との取り決め |
| 性能の改善 | 遅い画面や重いバッチを直す | SQLの改善、N+1の解消、キャッシュ、非同期ジョブ |

独立して最初に入りやすいのは、運用中サービスの機能追加です。立ち上げ案件は数が限られ、設計を一人で任せられるかを問われやすくなります。

## 独立前に積んでおきたい経験

### バージョンアップを一度は担当する

Rubyにはサポートの期限があります。ruby-lang.orgのメンテナンス状況のページでは、Ruby 3.2はすでにEOL（サポート終了）、3.3はセキュリティ修正のみの段階で、EOLは2027年3月31日の予定とされています（2026年10月時点）。Railsも、公式のメンテナンス方針で、バグ修正は最初のリリースから1年、セキュリティ修正は2年と定められています。たとえばRails 8.0系のセキュリティ修正は2026年11月7日までです。

期限があるため、運用中のサービスでは数年ごとに上げる作業が必要になります。この作業は手間がかかるわりに社内で担い手が少なく、業務委託に任されることがよくあります。次のような作業に自分が関わったかを書き出しておきましょう。

- 非推奨になったメソッドや設定の置き換え
- gemの更新と、更新できないgemの代わりを探す作業
- テストを足して動作を確かめ、段階的にリリースした流れ

### テストを書くことが当たり前になっている

Railsの現場では、RSpecなどでテストを書き、プルリクエストごとに自動で実行する運用が広く行われています。テストを書かずに機能だけ出す進め方は、レビューで止まりやすくなります。既存のテストが少ないコードに、どこから足したかを説明できると評価されます。

### Rails以外の周辺を一つ持つ

Railsだけで完結する案件は多くありません。次のうち一つでも実務で触れておくと、参画できる案件が広がります。

- MySQL・PostgreSQLのインデックス設計と実行計画の読み方
- Sidekiqなどの非同期ジョブと、失敗したときの再実行の設計
- AWSなどのクラウドでの運用（デプロイ、ログ、監視）
- TypeScriptとReact・Vue.jsなど、フロントエンドの基本

求められるスキルの全体像は[Rubyの案件で求められるスキルの記事](/media/ruby-skills/)で詳しく扱っています。

:::view
Rubyの案件をご紹介していると、面談で評価されやすいのは、機能をたくさん作った経験より「既存のコードをどう読み、どこまで直したか」を話せる方です。バージョンアップやN+1の解消など、地味でも自分が判断した作業を具体的に説明できると、少人数のチームでも任せやすい人として見てもらえます。面談の前に、担当した機能と、改修のときの判断を整理しておくことをおすすめします。
:::

## 会社員とフリーランスで求められる動き方の違い

Rubyの現場は少人数のことが多く、フリーランスも社員と同じ開発フローに入ります。そのぶん、会社員のときとは違う動き方が求められます。

| 比べる点 | 会社員 | フリーランス |
|---|---|---|
| 仕事の決まり方 | 上司やリーダーが割り振る | 契約で決めた範囲の中で、自分から課題を拾う |
| コードの慣れ | 長く同じコードに触れて詳しくなる | 短い期間で他人のコードに慣れる |
| 相談の仕方 | 同じ部署の人に気軽に聞ける | チャットで要点をまとめて相談する |
| 技術の選び方 | 社内の方針に従う | 現場の方針を尊重しつつ、改善案を出す |

特に、リモートで働く現場では、詰まったときに早めに相談できるかが重視されます。リモートの傾向は[Rubyのリモート案件の記事](/media/ruby-remote/)で解説しています。

## 独立までの進め方

### 1. サービスごとに担当範囲を書き出す

関わったサービスごとに、期間、チームの人数、担当した機能、Ruby・Railsのバージョン、使ったgemやインフラ、成果を書き出します。「Rails開発」とまとめず、「決済機能の改修」「Rails 6系から7系への更新」のように具体的に書くと、案件との合い具合が伝わります。

### 2. 公開できる成果を一つ用意する

自社サービスの経験は守秘義務で詳しく書けないことがあります。その補いとして、GitHubに置いた小さなRailsアプリや、使っているgemへの修正の提案、技術記事などがあると、コードの書き方を見てもらう材料になります。規模は小さくても、テストとREADMEが整っていることが伝わる形にしておきます。

### 3. スキルシートと希望条件を整える

スキルシートでは、バージョンと担当した工程を表で示すと読み手に伝わりやすくなります。書き方は[Rubyのスキルシートの記事](/media/ruby-skillsheet/)と[スキルシートの基本](/media/skillsheet-basics/)をご覧ください。あわせて、稼働日数、リモートか出社か、報酬の下限を決めておきます。報酬の決まり方は[Rubyの報酬の記事](/media/ruby-rate/)で扱っています。

### 4. 案件を探して面談を受ける

案件の探し方には、フリーランスエージェント（案件紹介サービス）、知人の紹介、発注元との直接契約などがあります。最初の案件は、契約手続きの支援がある経路を選ぶと負担が減ります。流れは[フリーランスエージェントの使い方](/media/agent-how-to-use/)で解説しています。

## 面談でよく問われること

Rubyの案件の面談は、開発チームのリーダーやCTOが同席し、技術の話が中心になることが多くあります。

1. **直近の担当機能**：どんな機能を、画面からDBまでのどこを担当したか
2. **性能の問題への対応**：遅い処理をどう見つけ、どう直したか
3. **テストとレビュー**：どの粒度でテストを書くか、レビューで何を見るか
4. **バージョンアップの経験**：どの版からどの版へ、何に苦労したか
5. **稼働の条件**：開始時期、稼働時間、チャットで連絡が取れる時間帯

PHPやPythonなど、ほかの言語の経験を聞かれることもあります。Rails以外のバックエンドについては[PHPエンジニアがフリーランスになるには](/media/php-how-to/)も参考になります。

:::caution
自社サービスの案件では、「できる人がやる」雰囲気の中で、契約にない作業まで頼まれることがあります。インフラの夜間対応や採用面接への同席などは、契約の範囲に入っているかを確かめてから引き受けましょう。範囲外の作業が続く場合は、契約の見直しを相談します。
:::

## 独立前後の手続きと契約

会社を辞めて独立する場合は、次の手続きが必要です（2026年10月時点の公的な案内による）。

| 手続き | 期限・内容 | 窓口 |
|---|---|---|
| 国民年金への切り替え | 退職日の翌日から14日以内 | 住所地の市区町村 |
| 健康保険の切り替え | 国民健康保険への加入か、任意継続を選ぶ | 市区町村・加入していた健康保険 |
| 開業届 | 事業を始めた年分の確定申告期限まで | 納税地の税務署 |
| 青色申告承認申請書 | 1月16日以後に開業した場合は開業日から2か月以内 | 納税地の税務署 |

最初の報酬が入るまでの生活費も用意しておきます。手順の全体は[会社員からフリーランスになる手順](/media/quit-company-steps/)、開業届は[開業届の出し方](/media/kaigyo-todoke/)で解説しています。税金や保険の判断に迷う場合は、税理士や窓口にご相談ください。

2024年11月に施行されたフリーランス法では、発注する事業者は業務を委託したら直ちに、業務の内容・報酬の額・支払期日などを書面やメールなどで明示することとされています。Rubyの案件では担当範囲が広がりやすいため、明示された業務の内容が面談で聞いた内容と合っているかを確かめましょう。

:::view
当社では、経歴をご紹介する前にどの案件に提案するかを伺い、ご了承いただいた案件にだけ、氏名・連絡先を伏せて提案しています。業務の範囲・報酬・支払期日・契約期間は個別契約に書いてお渡ししています。最初の案件では、稼働日数・リモートの希望・希望金額を先に伺い、条件に合う案件だけをご案内しています。
:::

:::point
- Rubyの独立では、Railsでの機能開発に加え、運用中のコードを改修した経験が大切
- RubyとRailsにはサポートの期限があり、バージョンアップの経験は評価されやすい
- テストを書く習慣と、SQL・非同期ジョブ・クラウドなどの周辺技術を一つ持っておく
- 自社サービスの案件では、契約の範囲を超える作業が増えていないかに気を配る
:::

## よくある質問

### Railsの実務経験は何年あれば独立できますか？

決まった年数はありません。見られるのは年数より、運用中のサービスで機能追加から不具合の対応までを一通り担ったかです。自分が書いたコードがどう本番で動いているかを説明できるかを目安にしてください。

### Ruby以外の言語も学んでおくべきですか？

Rubyだけで続けている方もいますが、フロントエンドのTypeScriptや、インフラの基本に触れておくと参画できる案件が広がります。新しい言語を一から学ぶより、Railsの周辺で使う技術を実務で増やすほうが、面談で説明しやすくなります。

### 受託開発の経験しかなくても大丈夫ですか？

受託開発でRailsを使ってきた経験は十分に伝えられます。ただ、自社サービスの案件では、リリース後の改善や運用の経験を聞かれることが多いため、納品後の保守に関わった経験があれば整理しておきましょう。最初の案件の選び方は[最初の案件の記事](/media/first-project/)も参考にしてください。
