データベースエンジニアのスキルシートは、**扱った製品の名前を並べるより、製品と版・データの規模・可用性の構成を1行で要約し、設計・性能改善・移行・運用のどれを担ったか、何を直し何を戻したかを書く**のが基本です。読み手は、同じ「Oracle、PostgreSQL」という並びからでも、方式を決めた人なのか、決まった環境を運用していた人なのかを知りたいからです。

この記事では、データベースエンジニアならではの書き方の要点と、架空の記入例を紹介します。スキルシート全体の基本の構成は[スキルシートの書き方の基本](/media/skillsheet-basics/)、案件で求められるスキルの中身は[データベースエンジニアの案件で求められるスキル](/media/db-engineer-skills/)で扱っています。

## 製品名の羅列では伝わらないこと

データベースエンジニアのスキルシートでよく見るのが、使用技術の欄に製品名とツール名を長く並べる書き方です。しかし、一覧からは次のことが読み取れません。

- その製品で、設計をしたのか、性能を直したのか、定型の作業をしていたのか
- どれくらいの規模で、どれくらい止められない環境だったのか
- 障害のときに、自分で原因を調べて戻したのか、報告して他の人に任せたのか

データベースの案件の読み手は、インフラや開発の経験がある担当者であることが多く、一覧の長さより、構成と役割の説明を見ています。

## スキル一覧は「製品・版・深さ」をそろえる

スキル一覧では、製品ごとに版と関わりの深さを添えると、読み手は合う案件かどうかを判断できます。

| 製品 | 書き方の例 |
|---|---|
| Oracle Database | 19c（性能改善・バックアップ設計）、11g（移行元の調査） |
| PostgreSQL | 13→16の版上げ（計画と実作業）、レプリケーション構成（構築） |
| SQL Server | 2019（運用・定型作業） |
| MySQL | 8.0（開発支援・SQLレビュー） |
| マネージドDB | Amazon RDS for PostgreSQL（パラメータ設計・版上げ）、Aurora（利用のみ） |
| ツール | 監視ツールでの閾値設計、移行ツールでのデータ移行（検証まで） |

これは書き方を示すための例です。**版を書く理由**は、サポート期限と移行の経験が読み取れるからです。たとえばPostgreSQLは各メジャー版を5年間サポートする方針のため、どの版からどの版へ上げたかを書くと、移行の経験がそのまま伝わります。「利用のみ」「運用」のように、浅い関わりもそのとおりに書いておけば、面談で深く聞かれる範囲を自分で示せます。

## プロジェクト欄の冒頭に「DBの要約」を置く

プロジェクト欄では、案件概要の次に、データベースの構成を1行で要約すると、読み手が全体像をつかみやすくなります。要約に入れたいのは次の4点です。

1. **製品と版**：どの製品の、どの版か
2. **規模の目安**：「数百GB規模」「表の数は数百」など、伏せられる範囲でぼかす
3. **可用性の構成**：単体か、レプリケーションか、クラスタか
4. **止められる時間の厳しさ**：「24時間稼働」「夜間に停止の時間帯あり」など

社名やシステム名は書かず、業種と構成の特徴で書きます。どこまで書いてよいかは[スキルシートに書いてよいこと・いけないこと](/media/confidentiality-in-skillsheet/)をご覧ください。

## 工程ごとに「何をしたか」を書き分ける

| 工程 | 書き方の例 |
|---|---|
| 設計 | 論理設計のレビュー、インデックス方針の策定、バックアップ方式を2案比べて決めた |
| 性能改善 | 夜間バッチの遅延について実行計画を調べ、インデックスとSQLの見直しで業務開始前に終わるようにした |
| 移行 | 版上げの互換性を確認し、切り替えと戻しの手順を作り、当日の作業を担当した |
| 運用 | 監視の閾値を見直し、障害の一次対応と振り返りを担当した |
| 開発支援 | 開発チームのSQLをレビューし、遅くなりやすい書き方を共有した |

性能改善は、改善の数字を書けない場合も多くあります。その場合は「業務開始前に終わるようになった」「画面の待ち時間への問い合わせがなくなった」のように、**業務への影響**で書けば十分です。守秘義務の範囲を超える数字は書かないようにしましょう。

### SQLの経験は「何に使ったか」で書く

「SQL：5年」のような書き方では、データを取り出す程度なのか、遅いSQLを直せるのかが分かりません。SQLの経験は、使い道で分けて書くと深さが伝わります。

- **抽出・集計**：調査や報告のためのデータの取り出し
- **開発**：業務の処理を担うSQLやストアドプロシージャの作成
- **レビュー・改善**：他の人が書いたSQLの見直し、実行計画を見た書き換え

どれか一つでも、自分が主に担った使い道を書いておけば、読み手は開発支援の案件か性能改善の案件かを判断しやすくなります。

### 「戻した経験」は独立した1行にする

バックアップからの復旧や、障害時の切り替えの経験は、データベースの案件でもっとも確かめられる経験の一つです。訓練でも本番でも、実施したことがあれば独立した1行で書きます。「復旧訓練を計画し、見つかった手順書の不足を直した」のように、何を改善したかまで書けると伝わりやすくなります。

:::view
データベースの案件をご紹介していると、運用の経験が中心の方の中には、障害の原因を突き止めた経験や、復旧を担当した経験をスキルシートに書いていない方が少なくありません。「定常運用」とひとまとめにせず、自分が判断した場面を1行ずつ書き出しておくことをおすすめします。面談では、その1行から深く聞かれることが多いためです。
:::

## 架空の記入例

以下は書き方を示すための**架空の例**です。実在の案件・企業とは関係ありません。

**案件概要**：小売業の受発注システムの基盤更改（期間：約1年、体制：基盤チーム5名のうち1名）

**DBの要約**：PostgreSQL（オンプレミス、版上げ前は11）。数百GB規模、レプリケーションで2台構成。夜間に短い停止の時間帯あり。

**担当工程**：移行計画、性能改善、運用設計

**実施したこと**
- サポート期限を過ぎた版からの版上げについて、互換性の確認項目を洗い出し、検証環境で事前に試した
- 切り替え当日の手順と、失敗時に元の環境へ戻す手順・判断の基準を作り、当日の作業を担当した
- 版上げ後に遅くなった検索について、実行計画を比べ、統計情報の取り直しとインデックスの見直しで解消した
- バックアップと復旧の手順を見直し、復旧訓練を実施した

**使用技術**：PostgreSQL、Linux、シェルスクリプト、監視ツール

**工夫したこと**：切り替えの前に、戻す判断をする時刻と確認項目を関係者と決めておき、当日の判断を迷わないようにした

## 認定資格の書き方

資格は、正式名称と取得年月を書きます。ORACLE MASTERのように対応する製品の版がある資格は、どの版に対応した資格かも添えましょう。資格ごとの評価のされ方と書き方は[ORACLE MASTERの記事](/media/cert-oracle-master/)と[データベーススペシャリスト試験の記事](/media/cert-ipa-db/)で詳しく解説しています。

:::caution
古い版の経験を書くこと自体は問題ありません。サポートが終わった版の環境は、移行の案件で調査の対象になるため、むしろ評価されることがあります。ただ、古い版の経験しか書かれていないと、最近の版を触っていないと受け止められることがあります。たとえばSQL Server 2019は2025年2月にメインストリームサポートを終えています（Microsoftのライフサイクルのページ、2026年10月時点）。経験した版と時期を正確に書き、新しい版は検証環境で確かめた範囲を分けて書きましょう。
:::

:::view
当社では、経歴をご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。データベースの経験は、製品と版、担った工程が合っているかで案件との相性が判断されるため、スキルシートの段階でそこが読み取れると、合う案件をご案内しやすくなります。書き方に迷う点はご質問いただければ確認します。
:::

:::point
- 製品名の羅列より、製品・版・規模・可用性・停止の厳しさを1行で要約する
- 工程ごとに何をしたかを書き分け、性能改善は業務への影響で書く
- 復旧や切り替えの「戻した経験」は独立した1行にする
- 記入例は架空のもの。守秘義務の範囲で、社名や数字はぼかす
:::

## よくある質問

### 規模の数字を書けない場合はどうすればよいですか？

「数百GB規模」「表の数は数百」「24時間稼働」のように、幅を持たせた言い方や、止められる時間の厳しさで書けば十分です。取引先との約束で書けない場合は、無理に書かず、面談で話せる範囲を口頭で伝えましょう。

### 運用保守だけの経験はどう書けばよいですか？

監視、バックアップの確認、定型の変更作業を一行にまとめず、障害の一次対応、原因の切り分け、手順書の改善など、自分で判断した場面を分けて書きます。運用の中で改善したことがあれば、それが一番の材料になります。

### データ分析基盤の経験はデータベースエンジニアのスキルシートに書いてよいですか？

書いてかまいません。ただし業務システムのデータベースの運用とは求められることが違うため、項目を分けて書くと読み手が混乱しません。データ基盤の経験の書き方は[データエンジニアのスキルシートの記事](/media/data-engineer-skillsheet/)も参考になります。
