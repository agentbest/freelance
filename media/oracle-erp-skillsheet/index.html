Oracle ERPコンサルのスキルシートの書き方｜面談で評価される実績の見せ方

Oracle ERPコンサルのスキルシートは、プロジェクトごとに製品とリリース・案件の種類・担当領域を1行で示し、担当した内容を業務の流れの言葉で書き、その中で自分がどう関わったか（要件を決めた、設定した、移行した、検証した）を動詞で書き分けるのが基本です。「Oracle ERP担当」とだけ書くと、読み手はEBSの保守を任せる人なのか、Fusionの導入を任せる人なのかを判断できません。

経験の棚卸しの方法はOracle ERPコンサルがフリーランスになるには、案件で問われるスキルの中身はスキルの記事で扱っています。この記事では、棚卸しした経験をシートの上でどう見せるかに絞ります。

プロジェクト欄の冒頭に「環境」を1行で書く

Oracle ERPの読み手が最初に知りたいのは、製品とリリース、案件の種類です。同じ買掛金の設定でも、EBSの保守とFusionの新規導入、EBSからFusionへの移行では、求められる判断が違うためです。

要素書き方の例読み手が判断すること
製品とリリースEBS 12.2.x、Fusion Cloud ERPどちらの製品の経験か、どの時期の環境か
案件の種類新規導入、移行、保守、追加開発、更新対応どの局面で力を出せるか
担当領域総勘定元帳・買掛金・調達など案件の領域と合うか
規模の目安国内の複数法人、海外拠点あり複数の法人や通貨を扱えるか
つながる仕組み周辺システムとの連携あり連携を含むテストを任せられるか

例（架空）：「Fusion Cloud ERP／EBS 12.2からの移行／買掛金・調達／国内の複数法人／周辺システムとの連携あり」

EBSのリリースは、分かる範囲で細かく書くと親切です。Fusionは更新が続くため、版名を書くより、参画した期間と、更新への対応に関わったかどうかを書くほうが伝わります。社名が特定されない書き方はスキルシートと守秘義務の記事をご覧ください。

担当は業務の流れで、深さは動詞で書く

機能の名前だけで終わらせない

「AP担当」「GL担当」のような略称だけでは、担当の中身が伝わりません。「請求書の照合から支払まで」「仕訳の取り込みから月次の締めまで」のように、業務の流れの言葉で書き添えると、読み手は案件の要件と照らし合わせやすくなります。

関わり方の深さを動詞で分ける

動詞意味読み手の受け取り方
要件を決めた利用部門と話し、標準機能での受け方を決めた上流から任せられる
設定した要件をもとに自分で設定した手を動かして作れる
移行したデータを整え、取り込み、照合した移行の工程に入れる
検証した更新やパッチの影響を調べ、テストした運用を任せられる
運用を支えた問い合わせ、締めや支払の時期の対応をした本番環境を任せられる
レビューした他の担当者の設計や設定を確かめたリードを任せられる

書き換えの例（架空）：

  • 書き換え前：Fusion AP担当
  • 書き換え後：Fusion Cloud ERPの買掛金で、請求書の照合と承認の流れの要件を経理部門と決め、設定。旧システムの未払データの移行と照合を担当

EBSとFusionの経験を書き分ける

両方の経験がある方は、プロジェクトの「環境」の行で製品を分けるだけでなく、スキル一覧でも製品ごとに経験年数を分けて書きます。合計の年数だけを書くと、読み手はどちらの経験が長いのか分かりません。

EBSの経験では、次の点を書いておくと、保守や移行の案件で読み手が判断しやすくなります。

  • 扱ったアドオンの種類（帳票、インターフェース、画面など）と、自分の関わり方（仕様を書いた、不具合を切り分けた）
  • SQLで本番データを確かめていたか、PL/SQLの処理を追えたか
  • パッチの適用やバージョンアップに関わったか

Fusionの経験では、導入と運用のどちらの局面か、担当した領域の数、更新対応に関わった期間を書きます。導入だけの経験か、稼働後も続けて関わったかで、読み手が任せたい役割が変わるためです。

スキル一覧は「製品」「領域」「技術」の3つに分ける

スキル一覧の欄は、次の3つに分けると読みやすくなります。

  • 製品：EBS（リリースと経験年数）、Fusion Cloud ERP（経験年数と、更新対応に関わった回数）
  • 領域：総勘定元帳、買掛金、売掛金、固定資産、調達など、担当した領域ごとに工程の範囲を添える
  • 技術：SQL、データ移行のテンプレートの扱い、レポートの作成、連携の仕様の理解など、自分でどこまでできるかを一言で添える

「SQL：本番データの確認と簡単な集計まで」のように範囲を書いておくと、面談で過大にも過小にも受け取られにくくなります。

更新対応と移行の経験の書き方

Fusionの四半期アップデート

運用の経験は「保守・運用」の一言で終わりがちです。更新への対応は、次のように分けて書くと伝わります。

  1. 新機能資料を読み、影響のある変更を洗い出した
  2. 新しい機能を使うかどうかを利用部門と決めた
  3. テスト環境で業務を流すテストの範囲を決め、実施した
  4. 本番の更新後の問い合わせに対応した

何回分の更新に関わったかを書くと、経験の厚みが伝わります。

EBSからFusionへの移行

移行の経験は、「現状調査」「置き換えの方針」「データ移行」「並行稼働・切替」のどこに関わったかを分けて書きます。特に、既存のアドオンをFusionの標準機能で置き換えた、運用を変えてなくした、といった判断は、短くても具体的に書くと評価の材料になります。

エージェントベストの見解

Oracle ERPの案件紹介の現場では、面談でスキルシートの一行を取り上げて「それはEBSとFusionのどちらでしたか」「その設定は誰が決めましたか」と確かめる場面をよく見ます。評価が安定しやすいのは、書いた経験の数が多くなくても、どの行についても製品と自分の役割をすぐ答えられる方です。答えに迷う行があると、他の記載の信頼まで下がることがあります。

記入例（架空）

次は書き方の型を示すための例です。業種と規模はぼかしてあり、実在のプロジェクトではありません。

期間：20XX年4月〜翌年9月（1年6か月）
環境：Fusion Cloud ERP／EBS 12.2からの移行／買掛金・調達／国内の複数法人
業種・概要：卸売業（中堅規模）の基幹システム刷新
立場：財務チーム4名のうち、調達から支払の領域の担当
担当工程：現状調査、要件定義、設定、データ移行、結合テスト、本番切替の支援
担当内容：EBSで使われていた支払関連のアドオンを洗い出し、Fusionの標準機能で受けられるものと運用変更で対応するものに分けて方針を決めた。請求書の照合と承認の流れを設定。未払データの移行と残高の照合を担当
工夫・成果：アドオンごとに「残す・置き換える・なくす」の一覧を作り、利用部門と合意。稼働後最初の支払処理に立ち会った

期間：20XX年10月〜現在
環境：Fusion Cloud ERP／運用・四半期アップデート対応／総勘定元帳・買掛金
立場：運用チームの機能担当
担当内容：更新ごとに新機能資料を読み、影響のある変更を一覧にして利用部門と使うかどうかを決めた。テスト環境での確認の範囲を決めて実施。本番の更新後の問い合わせに対応

実際に書くときは、ご自身の経験に置き換えてください。

注意

画面の名前や設定の項目名を並べるだけの書き方は避けましょう。名前の数が多くても、業務の何を実現したかが伝わらず、操作の経験としか読まれません。また、データベースの構築・運用の経験はERPの経験と別の欄に書くと、読み手の誤解を防げます。

リーダー経験と英語の書き方

領域のリードを担った場合は、チームの人数、管理した課題の範囲、調整した相手（利用部門の責任者、他領域のリード、開発チーム、Oracleのサポートなど）を書きます。英語は、資料を読む、サポートに問い合わせる、海外拠点との会議を進めるなど、使った場面を分けて書くと、任せてよい範囲が伝わります。面談での話し方は、後続の面談の記事で扱います。

エージェントベストの見解

当社では、ご経歴は、ご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。Oracle ERPの案件は、製品・領域・局面の組み合わせが案件ごとに違うため、プロジェクトごとの「環境」の1行と、動詞で書いた担当内容をそろえておくことをおすすめします。案件で求められている製品や領域は、ご質問いただければ確認します。

ポイント

  • プロジェクトの冒頭に、製品とリリース・案件の種類・領域・規模を1行で書く
  • 担当は業務の流れの言葉で書き、深さは「要件を決めた」「移行した」「検証した」などの動詞で分ける
  • EBSとFusionの経験年数は分けて書き、更新対応や移行は関わった段階ごとに書く

よくある質問

EBSとFusionの経験を一つのプロジェクト欄にまとめてもよいですか？

移行のプロジェクトのように両方に触れた場合は一つにまとめてかまいませんが、「環境」の行で移行元と移行先を書き分けます。別々のプロジェクトでの経験なら、欄を分けたほうが読み手は判断しやすくなります。

Oracleの認定資格はどこに書けばよいですか？

資格欄に正式な名称と取得年月を書きます。案件では実務の経験が重視されるため、資格はプロジェクト欄の内容とあわせて読まれます。ORACLE MASTERのようなデータベースの資格は、ERPの資格と区別して書きましょう。

守秘義務でアドオンの中身を書けない場合は？

具体的な処理の中身ではなく、「支払関連の帳票」「外部システムへのインターフェース」のように種類と数の目安、自分の関わり方を書けば十分です。書き方の基本はスキルシートの基本の記事もご覧ください。
