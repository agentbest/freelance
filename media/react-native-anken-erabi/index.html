モバイルアプリ開発

React Nativeエンジニアのフリーランス案件の選び方｜契約前に確かめたいこと

公開 2026-11-04　監修：株式会社エージェントベスト

目次

  2. 契約前に確かめたい7つの点
  3. 確かめた内容を書面と照らし合わせる
  4. よくある質問

React Nativeのフリーランス案件を選ぶときは、報酬や稼働日数に加えて、版とアーキテクチャの状態、Expoの使い方、ネイティブ側を誰が持つか、ストアの権限と公開の担当、チームの中での位置、開発環境と端末、契約の形と権利の扱いの7点を契約前に確かめておくことが大切です。同じ「React Nativeでのアプリ開発」でも、この7点の違いで作業の量と責任が大きく変わります。

特に見落としやすいのは、JavaScriptの外の仕事が誰の担当になっているかです。案件票には画面の開発しか書かれていなくても、参画するとビルドの不具合や審査への対応まで一人で持つことになる現場があります。この記事では、React Native案件に固有の確認点を整理します。契約書全般の確認点は業務委託契約書のチェックポイントで解説しています。

React Native案件の選び方で差が出る理由

React Nativeは、Reactの考え方でiOSとAndroidの両方を作れるため、発注側は少ない人数でアプリを回したいと考えて採用することがよくあります。その分、一人あたりの担当範囲が広くなりやすく、案件票の「React Native経験者募集」という言葉だけでは、仕事の中身が読み取れません。

よくあるずれは次のようなものです。

  • 画面の開発と聞いていたのに、数年止まっていた版上げの対応が中心だった
  • ネイティブのエンジニアがいると思っていたら、すでに退職していて、ネイティブ側の変更も求められた
  • ストアの権限がなく、審査への提出のたびに社員の操作を待つ必要があった
  • 手元のMacと実機での開発が前提で、端末の用意を自分ですることになった

こうしたずれは、面談と条件の確認の段階で聞き方を工夫すれば、多くを防げます。

契約前に確かめたい7つの点

1. 版とアーキテクチャの状態

最初に確かめたいのは、アプリが使っているReact NativeとExpoの版、New Architectureへの対応の状況です。React Nativeは2か月ほどの間隔で新しい版が出ており、公式が保守するのは最新の3つのマイナー系列です（2026年10月時点のReleases Overviewによる）。保守の範囲から外れた古い版のままのアプリでは、機能の開発の前に版上げの作業が必要になることがあります。

古い版のアプリを避ける必要はありません。移行の経験は評価にもつながります。ただ、状態を知ったうえで受けることが大切です。面談では「直近で版を上げたのはいつか」「止まっているライブラリはあるか」を聞くと、負債の量が見えやすくなります。

2. Expoの使い方とビルドの仕組み

Expoを使っているか、使っている場合はネイティブのフォルダをどう扱っているか、ビルドと配信をどの仕組みで回しているかを確かめます。ビルドの仕組みが整っている現場と、特定の社員のMacでしかビルドできない現場とでは、日々の進めやすさがまったく違います。ストアを通さない配信を使っている場合は、本番への配信を誰が判断するかも聞いておきましょう。

3. ネイティブ側を誰が持つか

  • チームにiOSやAndroidのエンジニアがいるか
  • ネイティブのモジュールの改修や、ネイティブのライブラリの更新は誰の担当か
  • 既存のネイティブアプリへの部分導入の場合、ネイティブ側のチームとの分担はどうなっているか

ネイティブ側も自分が持つ場合、SwiftやKotlinをどの程度書く想定かを確かめ、自分の経験と合うかを判断します。合わない部分があれば、参画前に正直に伝えておくほうが、後のずれを防げます。

エージェントベストの見解

React Nativeの案件をご紹介していると、参画後に「聞いていた状況と違った」となりやすいのは、版上げの負債の量と、ネイティブ側の担当の2点です。面談では聞きにくいと感じる方もいますが、作業の見通しを立てるために必要な確認として聞けば、多くの発注元は答えてくれます。案件票だけでは分からない点は、契約の前に確かめることをおすすめします。

4. ストアの権限と、公開の担当

App Store Connectには、アカウント所有者、管理者、アプリの管理、開発者などの役割があり、役割ごとに操作できる範囲が分かれています。Play Consoleでも、アカウント全体に効く権限と、選んだアプリだけに効く権限を分けて付与できます（2026年10月時点の各公式ヘルプによる）。

  • 自分にどの役割や権限が付与されるか
  • 審査への提出と公開の判断は誰が行うか
  • 署名の鍵や証明書は誰が管理しているか
  • 契約が終わったときに、権限をどう外すか

公開の担当が自分になる場合は、審査の指摘への対応や、公開直後の不具合への対応の時間も見込んでおく必要があります。個人の開発者アカウントでの公開を頼まれた場合は、アプリの持ち主が誰になるかに関わるため、引き受ける前に慎重に検討してください。

5. チームの中での位置と、Webとの関わり

React Nativeの担当が何名いるか、自分はその中でどの位置にいるかを確かめます。担当が自分一人の場合は、設計の判断から公開まで任される分、相談相手がいない状態になります。Webのチームがアプリも担う現場では、Webと共通にするコードの範囲や、レビューを誰がするかも聞いておきましょう。

6. 開発環境、端末、リモートの条件

  • 開発に使うMacと、両OSの実機は貸与か、自分で用意するか
  • 検証に使う機種の指定があるか
  • 出社が求められる場面（リリース前の通しの確認、機器との連携など）があるか
  • 私物の端末に入れたアプリや検証用のアカウントを、契約が終わったあとにどう消すか

リモートで受ける場合の確認点はReact Nativeのリモート案件の記事で詳しく解説しています。

7. 契約の形、成果物、権利の扱い

フリーランスのReact Nativeエンジニアは、多くの場合、準委任契約で参画します。新規アプリの開発を請負の形で受ける場合は、完成に対する責任を負うことになるため、役割と契約の形が合っているかを確かめましょう。違いは準委任契約と請負契約の違いで解説しています。

あわせて、作ったコードの著作権がどちらに帰属するか、自分が以前から持っている部品やコードを使う場合の扱いも確かめます。React Nativeのアプリは多くのオープンソースのライブラリに支えられているため、ライセンスの表示を誰が管理するかも確認しておくと安心です。考え方は著作権の扱いの記事とOSSライセンスの記事をご覧ください。

注意

少人数の現場では、参画後に役割が少しずつ広がりやすい傾向があります。Webの画面の改修、APIの修正、ストアに出す説明文の作成、問い合わせへの回答など、契約の業務範囲に入っていない仕事を頼まれたときは、引き受ける前に範囲と条件を確かめましょう。考え方は作業範囲が広がったときの契約の扱いで解説しています。

確かめた内容を書面と照らし合わせる

面談や事前の確認で聞いた内容は、契約の前に書面と照らし合わせます。フリーランス法では、発注する事業者は業務を委託したら直ちに、給付の内容、報酬の額、支払期日などの取引条件を、書面またはメールなどで明示することとされています（2026年10月時点、公正取引委員会の案内による）。明示される事項の内容はフリーランス法で明示される取引条件をご覧ください。

React Nativeの案件では、特に次の点が書面に反映されているかを確かめます。

  1. 業務の内容に、担う範囲（画面の開発、版上げ、ネイティブ側の変更、ストアへの公開など）が書かれているか
  2. 稼働の幅と、超えたときの精算方法
  3. 端末の貸与や、私物の端末を使う場合の扱い
  4. 成果物の権利の帰属と、契約期間・更新の時期

稼働の精算の仕組みは精算幅の記事をご覧ください。面談で聞いておくとよい質問はReact Nativeの面談でよく聞かれる質問と答え方の逆質問の項目でも紹介しています。一般的な逆質問の考え方は面談で聞いておくべき逆質問にまとめています。

エージェントベストの見解

当社では、取引先の会社の実態と支払条件を確かめた案件を扱い、契約では業務範囲・報酬・支払期日・契約期間を個別契約に書いてお渡ししています。React Nativeの案件で気になりやすい版の状況、ネイティブ側の体制、ストアの権限の扱いなど、書面だけでは読み取りにくい点は、ご質問いただければ確認します。条件に迷う点があれば、契約の前に早めにご相談ください。

ポイント

  • React Native案件は、同じ募集でも版の状態、Expoの使い方、ネイティブ側の担当で負担が大きく変わる
  • ストアの権限と公開の担当、チームの中での位置、端末の扱いを面談で確かめる
  • 契約の形と、コードの権利やOSSライセンスの扱いを確かめる
  • 聞いた内容を、業務範囲・精算・端末・権利・期間の観点で書面と照らし合わせる

よくある質問

React Nativeの担当が自分一人の案件は避けたほうがよいですか？

避ける必要はありません。一人で設計から公開まで担った経験は、次の案件で評価されやすい経験です。ただし、相談相手がいない分、ネイティブ側やストアの対応まで自分で持てるかを見極め、稼働の上限と精算の方法を確かめてから受けることをおすすめします。

面談で版上げの状況やコードの状態を聞いても失礼になりませんか？

作業の見通しを立てるための確認として聞けば、失礼にはあたりません。「参画後に最初に取り組むべきことを把握したい」という目的を添えると、相手も答えやすくなります。答えられない場合は無理に聞き出さず、ほかの確認点で判断しましょう。

古い版のままのアプリの案件は、報酬の面で不利になりますか？

一概には言えません。版上げの負債が大きいアプリでは、移行を任せられる人が求められるため、経験があれば評価の材料になります。一方で、作業の量が見込みを超えやすいため、稼働の見込みと報酬を合わせて比べるとよいでしょう。報酬の決まり方はReact Nativeの報酬の記事で解説しています。

業務委託契約の基礎

業務委託契約書のチェックポイント｜署名前に確かめたい10項目

業務委託契約書は、契約形態・業務範囲・報酬と精算・支払期日・契約期間と解除・知的財産・秘密保持・損害賠償などを署名前に確認します。フリーランス新法で発注者が明示すべき事項と照らし合わせると、抜けに気づきやすくなります。

 フリーランス新法・下請法

フリーランス新法の取引条件の明示｜受け取るべき8項目と確認のしかた

フリーランス新法では、発注者は業務委託をしたら直ちに、業務の内容・報酬の額・支払期日など8項目を書面かメール等で明示しなければなりません。口頭だけは不可です。受け取るべき内容と、未定事項や共通事項の扱いを整理します。

 業務委託契約の基礎

準委任契約と請負契約の違い｜フリーランスが知っておくべきこと

準委任は「業務を行うこと」、請負は「仕事を完成させること」に報酬が払われる契約です。責任の範囲・報酬の条件・途中でやめるときの扱いが違うため、契約書で何を約束しているかを確かめることが大切です。

 業務委託契約の基礎

作業範囲が広がったときの契約の扱い｜追加の報酬と変更の残し方

契約で決めた業務範囲を超える作業は、原則として当初の報酬に含まれません。追加するなら、作業内容・報酬・期限を決め直して書面やメールで合意します。フリーランス新法の不当な給付内容の変更の考え方と、変更を合意する手順を整理します。

 業務委託契約の基礎

成果物の著作権は誰のもの？業務委託の知的財産の扱い

業務委託で作ったプログラムや資料の著作権は、契約で決めなければ原則として作ったフリーランスに残ります。発注者に移す場合は、譲渡の範囲・時期・対価と、以前から持っているコードの扱いを契約で確かめます。

 業務委託契約の基礎

納品物にOSSを使うときのライセンスの注意点｜義務の違いと契約での扱い

OSSは条件を守れば使えるソフトウェアで、ライセンスごとに表示やソースコード提供などの義務が違います。納品前に、ライセンスの種類と義務、発注者の利用方針、契約の保証や権利の条項との食い違いを確かめ、一覧で共有します。
