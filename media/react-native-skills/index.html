React Nativeエンジニアのフリーランス案件で求められるスキルと経験

React Nativeのフリーランス案件では、ReactとTypeScriptで画面を組む力に加えて、New Architectureの仕組みの理解、Expoを使ったビルドと配布の仕組み、SwiftやKotlinでのネイティブ連携、両ストアのルールに沿った更新の運用が見られます。画面を作れることは前提で、その外側にどこまで手が届くかで、任される範囲が変わります。

この記事では、案件で問われるスキルを分野ごとに整理し、最後に経験の段階ごとに何を足せばよいかをまとめます。Reactそのものの設計や状態管理の考え方はReactの案件で求められるスキル、TypeScriptはTypeScriptの案件で求められるスキルで扱っているため、ここではモバイルならではの点に絞ります。

React Nativeの仕組み：New Architectureを前提に考える

React Nativeの公式ドキュメントでは、New Architectureは0.76から標準で有効になったと説明されています。さらに0.82の公式ブログでは、0.82はNew Architectureだけで動く最初の版だとされ、従来のアーキテクチャに戻す設定は無視されるようになりました（2026年10月時点）。

公式の説明によると、New ArchitectureではJSIという仕組みで、JavaScriptがC++のオブジェクトを直接参照してメソッドを呼べるようになり、従来の非同期の「ブリッジ」を通したやり取りが置き換えられました。React 18以降の並行描画の機能にも対応しています。

案件で問われるのは、仕組みを細かく暗記していることより、次のような判断です。

  • 入れようとしているライブラリがNew Architectureに対応しているかを、導入の前に確かめられる
  • 対応していないライブラリを、別のものに置き換えるか、自分で直すかを判断できる
  • 公式の説明にあるとおり、有効にしただけで性能がすぐ上がるわけではないことを理解し、効果を確かめてから説明できる

Expoとビルドの仕組み

Expoの現場では、androidとiosのフォルダを手で管理せず、必要なときに設定から生成する「Continuous Native Generation（CNG）」の考え方が使われます。Expoの公式ドキュメントでは、生成されたフォルダに手で入れた変更は作り直すと消えることがあるため、ネイティブの設定は「設定用のプラグイン（config plugins）」で行うことが勧められています。

この仕組みを理解しているかどうかは、トラブルのときに表れます。

  • 権限の文言やビルドの設定を、生成されたファイルではなくプラグインで変えられる
  • ネイティブのフォルダを持つ現場と持たない現場で、ビルドの流れがどう違うか説明できる
  • EAS Buildで、署名に使う鍵や証明書を誰が管理しているかを把握している

ネイティブのフォルダを直接管理している既存のアプリもまだ多いため、両方のやり方を知っていると、引き継ぎの案件にも入りやすくなります。

エージェントベストの見解

React Nativeの案件をご紹介していると、面談で評価されやすいのは、Expoや設定用のプラグインの名前を挙げることより「ビルドが壊れたときに、どのファイルが、何から作られているかを追えた」経験を話せる方です。設定がどこで生成されているかを説明できると、引き継ぎの多い現場でも任せやすい人として見てもらえます。スキルシートには、Expoの有無に加えて、ネイティブのフォルダを手で管理していたかどうかを一言添えることをおすすめします。

ネイティブ連携：SwiftとKotlinに降りる力

カメラ、決済、地図、Bluetooth、端末の暗号化の保存領域などは、既存のライブラリで要件を満たせず、ネイティブのコードに手を入れることがあります。Expoの公式ドキュメントでは、SwiftとKotlinでネイティブのモジュールやビューを作る「Expo Modules API」が用意されており、New Architectureに対応していると説明されています。

案件で頼りにされるのは、次のような経験です。

  • 既存のライブラリの不具合を、ネイティブ側のコードを読んで特定した
  • 小さなネイティブのモジュールを自分で作り、JavaScriptから呼べるようにした
  • 外部のSDKを組み込むために、iOSとAndroidの両方で設定を書いた

ネイティブ側の詳しいスキルはiOSの案件で求められるスキルとAndroidの案件で求められるスキルも参考になります。

ストアのルールと、ストア外の配信の使い分け

React Nativeでは、JavaScriptの部分をストアの審査を経ずに配信する仕組みがよく使われます。この運用には、両ストアのルールの理解が欠かせません（以下は2026年10月時点の各公式ページの記載です）。

  • App Store：審査ガイドライン2.5.2では、アプリの機能を加えたり変えたりするコードをダウンロードして実行してはならないとされています。2.1では、ログインのあるアプリはデモ用のアカウントを用意することなどが求められています
  • Google Play：デバイスとネットワークの不正使用に関するポリシーでは、Google Playの更新の仕組み以外でアプリ自身を変更・更新してはならないとしつつ、仮想マシンやインタプリタで動き、Android APIへの間接的なアクセスにとどまるコードはこの制限の対象外とされています

Expoの公式ドキュメントでも、ストア外の配信は各ストアのルールに従う必要があると明記されています。案件では、どんな変更なら配信で直してよく、どんな変更ならストアの審査に回すかを、チームの決まりとして言葉にできる人が評価されます。判断に迷う変更は、ガイドラインの原文を確かめ、発注側と合意してから進めましょう。

性能とテスト

  • 一覧の描画：長い一覧で表示が引っかかる原因を調べ、描画の回数や画像の扱いを見直した
  • 起動の速さ：最初の画面が出るまでに読み込むものを減らした
  • 調査の道具：React NativeのDevToolsなどで、重い処理や不要な再描画を見つけた
  • テスト：ロジックの単体テスト、画面のテスト、実機での結合テストを、CIで回るようにした

テストの自動化をさらに深めたい方はテスト自動化の案件で求められるスキルも参考になります。

注意

「iOSもAndroidも対応できます」と伝えて参画したものの、実際には証明書の管理やネイティブのビルドの設定を誰も担当しておらず、想定以上の時間を取られることがあります。参画前に、ビルドと署名の管理、ストアへの申請、ストア外の配信の判断がそれぞれ誰の担当かを確かめましょう。契約の形による違いは準委任契約と請負契約の違いで解説しています。

ポイント

  • React Nativeの案件では、ReactとTypeScriptに加え、New Architecture、Expoのビルドの仕組み、ネイティブ連携、ストアのルールが見られる
  • 0.82からはNew Architectureだけで動くため、ライブラリの対応を確かめる力が欠かせない

  • ストア外の配信は、各ストアのルールに沿って「配信で直す変更」と「審査に回す変更」を分ける

よくある質問

SwiftやKotlinが書けないと、React Nativeの案件には入れませんか？

画面の実装が中心の案件なら、ネイティブのコードを書かずに進められることもあります。ただ、ライブラリの不具合やビルドの失敗の原因がネイティブ側にある場面は少なくありません。書けなくても、読んで原因の見当をつけられる程度の理解があると、任される範囲が広がります。

New Architectureの内部まで理解している必要がありますか？

ネイティブのモジュールを作る立場でなければ、内部の仕組みを細かく説明できなくても実務は進められます。案件で問われるのは、ライブラリが対応しているかを確かめ、対応していないものにどう手を打つかを判断できることです。

Webのフロントエンドの経験は、React Nativeの案件でどこまで評価されますか？

コンポーネントの設計、状態管理、TypeScriptの経験は、そのまま評価の材料になります。ただ、モバイルではストアの審査や端末の権限など、Webにはない仕事があります。Webの経験を土台にしつつ、モバイル特有の経験を一つずつ足していくと、説明できる範囲が広がります。
