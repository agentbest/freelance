PHPエンジニアのフリーランス案件の選び方｜契約前に確かめたい8つの点

公開 2026-11-04　監修：株式会社エージェントベスト

目次

  2. 契約前に確かめたい8つの点
  3. 確かめた内容を書面と照らし合わせる
  4. よくある質問

PHPエンジニアのフリーランス案件を選ぶときは、報酬や稼働日数に加えて、PHPとフレームワークの版、コードの状態、担当する範囲、体制と相談相手、契約の形と成果物、障害対応と稼働の振れ幅、環境と端末、契約期間と更新の8点を契約前に確かめておくことが大切です。PHPの案件は、同じ「Laravelでの開発」と書かれていても、この8点の違いで負担と責任が大きく変わります。

特に見落としやすいのは、コードの状態と、障害対応の範囲です。テストも文書もないコードを一人で引き継ぎ、本番の障害の連絡も自分に来る案件は、稼働の見込みが大きくずれます。この記事では、PHPの案件に固有の確認点を整理します。契約書全般の確認点は業務委託契約書のチェックポイントで解説しています。

PHPの案件選びで差が出る理由

PHPは案件の数が多く、新しいサービスから10年以上動いているシステムまで幅があります。案件票には「PHP／Laravel」「ECサイトの開発」のように短く書かれることが多く、参画してから想定との違いに気づくことが少なくありません。

よくあるずれは次のようなものです。

  • 「Laravel」と書いてあったが、実際は古い版で、独自の書き方が多く残っていた
  • 開発の案件と聞いていたが、問い合わせ対応と本番の障害対応が仕事の大半だった
  • 社内にPHPを読める人がおらず、設計の相談も仕様の判断も一人で抱えることになった
  • 準委任の契約なのに、納品物の完成と修正を求められ続けた
  • 週5日の契約なのに、夜間のリリースや休日の障害対応が続いた

こうしたずれは、面談と条件の確認の段階で、聞き方を工夫すれば多くを防げます。案件票の読み方は案件情報の読み方の記事でも解説しています。

契約前に確かめたい8つの点

1. PHPとフレームワークの版、版上げの予定

最初に確かめたいのは、PHP本体とフレームワークの版です。PHPは版ごとにサポートの期限が決まっており、公式サイトの案内では、PHP 8.2のセキュリティサポートは2026年12月31日に終了する予定です（2026年10月時点）。サポートの切れた版で動いているシステムは、脆弱性への対応ができないまま運用されている可能性があり、版上げの仕事が隠れていることがあります。

版上げの予定があるなら、それを自分が担うのか、担う場合はどの範囲（計画、修正、検証、本番への適用）までかを確かめます。版上げは経験として評価される仕事ですが、版上げを含むことを知ったうえで受けることが大切です。

2. コードの状態（テスト、CI、レビュー、文書）

次に、コードの状態を確かめます。

  • テストコードがあるか。あるなら、どの範囲を自動で確かめているか
  • CIで何を動かしているか（テスト、静的解析、コーディング規約の確認など）
  • コードレビューの体制があるか。誰が見るか
  • 環境構築の手順や設計の文書が残っているか

テストも文書もない案件を避ける必要はありません。そうした案件は多く、整えていく仕事は評価にもつながります。ただ、調査と動作確認に時間がかかる前提で、稼働の見込みと報酬を考える必要があります。面談で「直近でテストを足した箇所はありますか」と聞くと、状態が見えやすくなります。

3. 担当する範囲（開発だけか、運用・問い合わせ対応まで含むか）

「開発」と書かれていても、実際の仕事はさまざまです。

  • 機能の実装とレビューだけか、仕様の整理や設計から担うか
  • フロントエンド、インフラ、クラウドの設定まで含むか
  • 本番へのリリース作業を自分が行うか
  • 問い合わせ対応や、データの修正などの運用作業を含むか

範囲が広いほど、一人で完結できる力として評価される一方、稼働の見込みがずれやすくなります。面談では「1週間の作業のうち、新しく作る仕事と直す仕事の割合はどのくらいですか」と聞くと、実態が見えます。型ごとの働き方はPHPエンジニアの仕事内容で解説しています。

エージェントベストの見解

PHPの案件をご紹介していると、参画後に「聞いていた内容と違った」となりやすいのは、コードの状態と、障害対応の範囲の2点です。面談では聞きにくいと感じる方もいますが、任される範囲を判断するために必要な確認として聞けば、多くの発注元は答えてくれます。案件票だけでは分からない点は、契約の前に確かめることをおすすめします。

4. 体制と、相談相手の有無

自分のほかにPHPを読める人がいるかどうかで、仕事の進め方が大きく変わります。

  • 社内や受託会社にPHPのエンジニアがいるか、何名か
  • 設計の判断や仕様の疑問を相談できる相手は誰か
  • 前任者がいる場合、引き継ぎの期間があるか、交代の経緯（答えられる範囲で）
  • 受託の案件なら、発注元と受託会社のどちらの側に立つのか

社内に一人目のエンジニアとして入る案件は、裁量が大きい一方、判断の責任も相談相手もない状態になりやすい案件です。経験が長い方には向いていますが、設計の経験が浅い方は、相談相手がいる案件から選ぶほうが無難です。

5. 契約の形と、成果物・権利の扱い

PHPの仕事は、月単位で稼働する準委任の案件と、サイトや機能を納品する請負の案件が混在しています。確かめたいのは、契約書や発注の書面の書き方が、実際の働き方と合っているかです。

  • 準委任なのに、「完成させて納品する」「不具合は無償で修正する」のような、完成を約束する書き方になっていないか
  • 請負なら、納品物の範囲、検収の方法、修正の回数と期限が決まっているか
  • 書いたコードの著作権が誰に帰属するか。自分が持ち込むライブラリやツールの扱いはどうか

違いは準委任契約と請負契約の違い、権利の扱いは成果物の著作権の記事で解説しています。また、準委任の契約なのに、発注元の社員から細かな作業の指示や勤務時間の管理を受ける働き方は、偽装請負の問題につながるおそれがあります。詳しくは偽装請負の記事をご覧ください。

6. 障害対応と稼働の振れ幅

PHPの案件、特に保守や運用を含む案件では、本番の障害が稼働の振れ幅を生みます。

  • 本番の障害の連絡は誰に来るか。自分に来る場合、稼働日以外や夜間も対応するか
  • リリースの作業は日中に行うか、利用者の少ない夜間や休日に行うか
  • 精算幅を超えたときの扱いと、稼働が少ない月の扱い

障害対応を担う契約なら、連絡の方法、対応する時間帯、時間の扱いを決めておかないと、責任感から無償で対応し続けることになりかねません。精算の仕組みは精算幅の記事、休日の作業の扱いは休日作業の記事をご覧ください。

7. 環境・端末・リモートの条件

PHPの案件はリモートで進めやすいものが多い一方、会員情報や決済の情報を扱う保守では、出社や貸与端末が条件になることがあります。

  • フルリモートか、出社の頻度はどのくらいか
  • 貸与端末か、自分の端末か。自分の端末なら、セキュリティの要件は何か
  • 本番のデータベースや会員情報にアクセスする作業があるか

リモートの条件の確かめ方はPHPのリモート案件の記事で解説しています。

8. 契約期間と更新、終了の予告

契約の期間と、仕事の区切りが合っているかを確かめます。たとえば、版上げの本番適用の直前に契約の更新時期が来ると、更新されなかった場合に最も大事な局面を見届けられません。

フリーランス法では、6か月以上継続して業務を委託している場合に、契約を解除したり更新しなかったりするときは、原則として少なくとも30日前までに予告することが求められています（2026年10月時点、公正取引委員会の案内による）。詳しくは契約解除の予告の記事をご覧ください。契約期間と更新の考え方は、仕事の区切りの見通しと合わせて確かめておきましょう。

注意

PHPの案件では、参画後に役割が少しずつ広がりやすい傾向があります。「ついでに」の改修、別のサイトの相談、インフラの設定、社内の問い合わせ対応など、契約の業務範囲に入っていない仕事を頼まれたときは、引き受ける前に範囲と条件を確かめましょう。考え方は作業範囲が広がったときの契約の扱いで解説しています。

確かめた内容を書面と照らし合わせる

面談や事前の確認で聞いた内容は、契約の前に書面と照らし合わせます。フリーランス法では、業務を委託する事業者は、業務を委託したら直ちに、業務の内容、報酬の額、支払期日などを、書面またはメールなどで明示することとされています（2026年10月時点、公正取引委員会の案内による）。明示される事項の内容はフリーランス法で明示される取引条件をご覧ください。

PHPの案件では、特に次の点が書面に反映されているかを確かめます。

  1. 業務の内容に、担う範囲（開発、版上げ、運用、障害対応など）が書かれているか
  2. 準委任なのに、完成や無償の修正を約束する書き方になっていないか
  3. 稼働の幅と、超えたときの精算方法。障害対応を担う場合はその時間の扱い
  4. 成果物と著作権の扱い
  5. 契約期間と更新の時期

面談で聞いておくとよい質問はPHPの面談でよく聞かれる質問と答え方の逆質問の項目でも紹介しています。一般的な逆質問の考え方は面談で聞いておくべき逆質問をご覧ください。

ポイント

  • PHPの案件は、同じ「Laravelでの開発」でもコードの状態、担当範囲、体制、契約の形で負担と責任が大きく変わる
  • PHPとフレームワークの版、テストとレビューの有無、担当範囲、相談相手の有無を面談で確かめる

よくある質問

テストも文書もない古いシステムの案件は避けたほうがよいですか？

避ける必要はありません。整えていく仕事は評価されやすく、版上げの経験は次の案件でも生きます。ただし、調査と動作確認に時間がかかる前提で稼働の見込みを立て、障害対応の範囲と精算の方法を参画前に確かめてから受けることをおすすめします。

面談でテストの有無や障害対応の範囲を聞くのは失礼ですか？

任される範囲を判断するための確認として聞けば、失礼にはあたりません。「参画後に最初に取り組むべきことを把握したい」という目的を添えると、相手も答えやすくなります。答えられない場合もあるので、その場合は無理に聞き出さず、ほかの確認点で判断しましょう。

報酬の高い案件と、体制の整った案件で迷ったらどうしますか？

一概には言えませんが、PHPの案件では、コードの状態が悪く障害対応も含む案件だと、稼働が増えて時間あたりの報酬が下がることがあります。報酬の額だけでなく、稼働の見込みと担う範囲を合わせて比べるとよいでしょう。報酬の決まり方はPHPの報酬の記事で解説しています。

業務委託契約の基礎

業務委託契約書のチェックポイント｜署名前に確かめたい10項目

業務委託契約書は、契約形態・業務範囲・報酬と精算・支払期日・契約期間と解除・知的財産・秘密保持・損害賠償などを署名前に確認します。フリーランス新法で発注者が明示すべき事項と照らし合わせると、抜けに気づきやすくなります。

 業務委託契約の基礎

準委任契約と請負契約の違い｜フリーランスが知っておくべきこと

準委任は「業務を行うこと」、請負は「仕事を完成させること」に報酬が払われる契約です。責任の範囲・報酬の条件・途中でやめるときの扱いが違うため、契約書で何を約束しているかを確かめることが大切です。

 業務委託契約の基礎

作業範囲が広がったときの契約の扱い｜追加の報酬と変更の残し方

契約で決めた業務範囲を超える作業は、原則として当初の報酬に含まれません。追加するなら、作業内容・報酬・期限を決め直して書面やメールで合意します。フリーランス新法の不当な給付内容の変更の考え方と、変更を合意する手順を整理します。

 業務委託契約の基礎

偽装請負とは｜指揮命令の線引きとフリーランスが注意すること

偽装請負は、請負や準委任の契約なのに、実態として発注者が働き手に直接指揮命令している状態です。判断は契約の名前ではなく実態で行われます。フリーランスは「労働者性」の基準と、参画前に確かめたい点を押さえておきましょう。

 フリーランス新法・下請法

フリーランス新法の取引条件の明示｜受け取るべき8項目と確認のしかた

フリーランス新法では、発注者は業務委託をしたら直ちに、業務の内容・報酬の額・支払期日など8項目を書面かメール等で明示しなければなりません。口頭だけは不可です。受け取るべき内容と、未定事項や共通事項の扱いを整理します。

 フリーランス新法・下請法

中途解除の30日前予告｜フリーランス新法のルールと例外

6か月以上の業務委託を発注者が中途解除・不更新にするときは、原則として30日前までの予告が必要です。予告の方法、予告が不要になる5つの例外、理由開示の請求の仕方を、公正取引委員会・厚生労働省の資料をもとに整理します。
