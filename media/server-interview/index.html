サーバーエンジニアのフリーランス面談でよく聞かれる質問と答え方

フリーランスのサーバーエンジニアの面談でよく聞かれるのは、どのOSをどの規模で扱ったか、どの工程を自分で担ったか、障害が起きたときにどう原因を絞り込んだか、本番環境の作業をどう進めたかの4つです。面談官は、コマンドの知識の量より「この人に本番のサーバーを触らせて大丈夫か」「止まったときに任せられるか」を確かめようとしています。

答えるときは、模範解答を覚えるより、自分の経験から「障害」「構築や更改」「移行」などの場面を3〜4つ選び、どの質問にもそこから答えられるように準備しておくのが近道です。面談全般の答え方の型は業務委託の面談でよく聞かれる質問と答え方で解説しているので、この記事ではサーバーの面談に固有の質問に絞ります。

サーバーの面談で面談官が見ていること

サーバー案件の面談に出てくるのは、発注元の基盤の責任者や、元請けのインフラのリーダーであることが多く、本人もサーバーの構築や運用の経験を持っています。そのため、言葉の上手さより、話の中に出てくる確かめた順番と、その根拠を聞いています。

面談官が知りたいのは、おおむね次の3点です。

  1. 任せられる範囲：どのOS・どの規模・どの工程を、どこまで自分で担ってきたか
  2. 本番での振る舞い：変更の前に何を確かめ、問題が出たときにどう戻すか
  3. 現場との相性：手順書や記録の残し方、報告の仕方が、自社のやり方に合うか

以下の質問は、この3点のどれかを確かめるためのものです。質問の意図が分かれば、答えの中心に何を置くかも決まります。

よく聞かれる質問と答え方の考え方

ここで示す答えの例は、組み立て方を伝えるための架空の例です。そのまま使うのではなく、ご自身の経験に置き換えて準備してください。

1. 「扱ってきたOSと、環境の規模を教えてください」

確かめたいのは、任せられる範囲です。OSは系列とメジャーバージョンで、サーバーは役割（Webサーバー、DBサーバー、ファイルサーバー、ADなど）で、置き場所は物理・仮想・クラウドの別で伝えます。台数は正確な数でなくても、おおよその規模で十分です。

架空の例：「直近はRHEL系のサーバーを中心に、仮想化基盤の上の数十台を見ていました。役割はWebとアプリのサーバーが中心で、Windows ServerのADは運用の範囲で触れています」

2. 「設計・構築・運用のうち、どこを自分で担いましたか」

サーバーの面談で最もずれが出やすい質問です。「構築を担当」と書いてあっても、手順書を自分で書いたのか、渡された手順書どおりに作業したのかで評価は大きく変わります。自分で書いた成果物と、受け取って使った成果物を分けて話すと、誇張していない印象になります。

3. 「障害が起きたとき、どう原因を絞り込みましたか」

最もよく掘り下げられる質問です。答えは次の順番で組み立てると伝わりやすくなります。

  • 何から異常に気づいたか（監視の通知、利用者からの連絡など）
  • 最初に何を確かめたか（影響の範囲、直前の変更の有無）
  • どの順番で原因を絞り込んだか（リソース、プロセス、ログ、ネットワークなど）
  • 暫定の対応と、恒久的な対策をどう分けたか
  • 誰に、いつ、どう報告したか

「再起動で復旧しました」だけで終わると、原因に迫った過程が見えません。再起動を選んだ理由と、その後に原因をどう確かめたかまで話せると、切り分けの力が伝わります。

4. 「本番環境で作業するとき、事前に何をしますか」

本番作業の慎重さを確かめる質問です。変更の申請、検証環境での事前の確認、作業の手順と所要時間の見積もり、切り戻しの手順、作業後の確認項目などを、自分の型として話します。ダブルチェックの体制や、作業の記録の残し方にも触れると具体性が増します。

5. 「OSの更改や移行で、苦労した点は何ですか」

移行の経験の深さを確かめる質問です。既存のサーバーで何が動いているかをどう調べたか、版の違いで動きが変わった点にどう対処したか、切り替えの時間をどう見積もったかを話します。事前の調査で見つけた依存関係の話ができると、移行を任せられる印象につながります。

6. 「手作業を減らしたり、自動化したりした経験はありますか」

構成管理の道具やスクリプトの経験を確かめる質問です。大きな仕組みでなくても、繰り返していた作業をスクリプトにした、手順のばらつきを減らした、といった小さな改善で構いません。何を自動化し、どれくらい手間や誤りが減ったかを、言える範囲で話します。

7. 「夜間作業や障害時の待機には対応できますか」

働き方の条件を確かめる質問です。応じられる頻度や時間帯、連絡を受けてから作業を始めるまでの目安などを、正直に伝えます。無理に「何でも対応できます」と答えると、参画後に負担が積み上がりやすくなります。条件の扱いは契約前に書面で確かめることになるので、面談では応じられる範囲を具体的に示しておくと話が早く進みます。

8. 「なぜフリーランスで働いているのですか」

長く続けられるか、契約の働き方を理解しているかを確かめる質問でもあります。働き方の希望だけでなく、どの工程やどの基盤で力を出したいかを添えると、案件との合い方が伝わります。

エージェントベストの見解

サーバーの案件をご紹介していると、面談で評価されやすいのは、障害や移行の場面を「何を見て、どの順番で確かめたか」で話せる方です。反対に、扱ったOSや製品の名前を並べるだけで、自分が判断した場面が出てこないと、経験の深さが伝わらず見送られやすい傾向があります。うまくいかなかった作業でも、原因と次に変えたことを話せれば、経験として受け止められることが多くあります。

技術的な確認を求められたとき

サーバーの面談では、口頭で技術的な確認を受けることがあります。たとえば、ディスクの容量が急に増えたときに何を見るか、サービスが起動しないときにどこから調べるか、権限の設定をどう考えるか、といった問いです。

こうした問いでは、正確なコマンドの名前より、確かめる順番と、その理由が見られています。思い出せないコマンドがあれば、無理に答えず「普段は手順書で確認しています。確かめる観点は〜です」と、考え方を中心に話すほうが信頼されます。実技の課題が出る場合の考え方は技術テストの記事で整理しています。

準備は「場面」を3〜4つに絞る

上の質問は数が多く見えますが、答えの材料は共通しています。準備は次の手順で進めると効率的です。

  1. 場面を選ぶ：障害の対応、構築や更改、移行、自動化など、性質の違う場面を3〜4つ選ぶ
  2. 場面ごとにメモをつくる：状況、気づいたきっかけ、確かめた順番、選んだ対応、報告の仕方、結果、次に変えたことを書き出す
  3. 環境の情報をそろえる：OSの系列と版、サーバーの役割、置き場所、おおよその規模を、どの場面でも同じ言い方で話せるようにする
  4. 2分版と5分版をつくる：最初は2分で話し、掘り下げられたら詳しく話せるようにする
  5. スキルシートと照らし合わせる：シートの担当工程の欄と、話の内容が一致しているかを確かめる

スキルシートとの一致は特に大切です。面談官はシートを見ながら質問するため、話とシートがずれると、どちらも信用されにくくなります。シートの書き方はサーバーエンジニアのスキルシートの記事、冒頭の自己紹介の組み立て方は面談の自己紹介の記事で解説しています。

注意

サーバーの面談では、前の現場のホスト名、IPアドレスの体系、セキュリティの設定の中身、障害で止まったサービスの名前などを、具体的に話してしまいがちです。サーバーエンジニアは基盤の内部に触れる立場だった分、話の具体性と守秘のバランスが問われます。社名や固有の名前は伏せ、規模は台数の目安や構成の特徴で示しましょう。考え方はスキルシートに書いてよいこと・いけないことが参考になります。

面談の相手によって重心が変わる

面談の相手重く見られやすい点
発注元の基盤の責任者本番作業の進め方、報告の仕方、運用まで見据えた判断
元請けのインフラのリーダー担当工程の深さ、手順書や試験の品質、チームでの動き方
運用の現場の担当者障害の切り分け、定型作業の正確さ、当番への対応

元請けと発注元の両方と面談する場合は、元請けの面談では工程の深さ、発注元の面談では本番での振る舞いや報告に重心を置くと、限られた時間を有効に使えます。

サーバーエンジニアならではの逆質問

面談の終わりの逆質問は、印象づくりより参画後のずれを防ぐ確認に使います。サーバーの案件では、次の点を聞いておくと判断がしやすくなります。

  • 担う工程と、手順書や設計書を誰が作り、誰がレビューするか
  • 扱うOSの版と、物理・仮想・クラウドの割合
  • 本番環境への作業の申請と承認の流れ
  • 夜間作業や障害時の待機の有無と頻度
  • 作業をする場所（リモート、常駐、データセンター）

一般的な逆質問の考え方は業務委託の面談で聞いておくべき逆質問にまとめています。逆質問で聞いた内容は、契約前の確認にもそのまま使えます。案件を選ぶときの確認点はサーバーエンジニアの案件の選び方で整理しています。

エージェントベストの見解

当社では、経歴をご本人の了承を得た案件にだけ、氏名・連絡先を伏せてご提案しています。サーバーの面談では、案件票だけでは分からない工程の分担や当番の有無について、面談の前に確認しておきたい点があれば、ご質問いただければ確認します。面談後に参画を迷う点が出てきた場合も、早めにご相談ください。

ポイント

  • サーバーの面談では、OSと規模、担当工程、障害の切り分け、本番作業の進め方がよく聞かれる
  • 答えは「気づいたきっかけ→確かめた順番→選んだ対応→報告→次に変えたこと」の順で組み立てる

  • 逆質問では、工程の分担、OSと置き場所、承認の流れ、当番、作業の場所を確かめる

よくある質問

古いOSの経験が中心ですが、面談で不利になりますか？

不利とは限りません。古いOSからの更改や移行の案件では、既存の設定を読み解ける経験が評価されることがあります。新しい版との違いをどう調べ、どう対処したかを話せるように準備しておくと、経験が生きます。

コマンドを思い出せなかったら、どうすればよいですか？

正直に思い出せないと伝え、確かめる観点や順番を説明すれば問題ありません。面談官は暗記より、本番で慎重に確かめながら進められるかを見ています。知らないことを知っているように話すほうが、掘り下げられたときに信頼を損ないます。

運用の経験しかありませんが、構築の案件の面談ではどう話せばよいですか？

運用の中で手順書を自分で書いた、設定の変更を計画した、障害の恒久対策を入れた、といった場面を中心に話します。肩書き以上の役割を語ると掘り下げられたときに答えに詰まるため、自分が担った範囲を正確に伝えることが大切です。見送られやすい理由は面談で見送られる理由の記事で解説しています。
