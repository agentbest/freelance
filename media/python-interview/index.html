Pythonエンジニアのフリーランス面談でよく聞かれる質問と答え方｜面談官が確かめたいこと

Pythonエンジニアのフリーランス面談でよく聞かれるのは、どの分野でPythonを使ってきたか、作ったものは本番で動き続けたか、ほかの人が保守できるコードを書いているか、性能や障害の場面で何を判断したかの4つです。Pythonは使われる分野が広いため、面談官は「Pythonが書けるか」より「うちの案件の分野で、同じ水準の仕事ができるか」を確かめようとしています。

答えるときは、模範解答を覚えるより、自分の経験から「設計や判断をした場面」を3〜4つ選び、どの質問にもそこから答えられるように準備しておくのが近道です。面談全般の答え方の型は業務委託の面談でよく聞かれる質問と答え方で解説しているので、この記事ではPythonの面談に固有の質問に絞ります。

Pythonの面談で面談官が見ていること

Python案件の面談に出てくるのは、開発チームのリーダーやテックリード、データ基盤や機械学習の責任者であることが多く、本人もPythonでコードを書いています。そのため、用語を知っているかより、話の中に出てくる判断の順番と、コードの扱い方の癖を聞いています。

面談官が知りたいのは、おおむね次の4点です。

  1. 分野の合い方：Web・データ基盤・機械学習・自動化のうち、自社の案件と同じ分野の経験があるか
  2. 本番運用の経験：試作や分析で終わったものと、本番で動かし続けたものを分けて話せるか
  3. コードの質：型ヒント、テスト、依存関係の管理、レビューの進め方を、自分の習慣として持っているか
  4. 困ったときの動き方：性能の問題や障害が起きたとき、何を見て、何を決めたか

以下の質問は、この4点のどれかを確かめるためのものです。質問の意図が分かれば、答えの中心に何を置くかも決まります。

よく聞かれる質問と答え方の考え方

ここで示す答えの例は、組み立て方を伝えるための架空の例です。そのまま使うのではなく、ご自身の経験に置き換えて準備してください。

1. 「Pythonをどの分野で、どのくらい使ってきましたか」

確かめたいのは、分野の合い方です。「Pythonは5年」とだけ答えると、面談官は分野を聞き直すことになります。分野、主なフレームワークやライブラリ、担当した工程を最初にまとめて伝えます。

架空の例：「Web・API開発が中心で、DjangoとFastAPIを合わせて4年です。設計から運用まで担当しました。直近の1年は、同じサービスのデータの集計基盤も担当しています」

分野が複数ある場合は、軸になる分野を先に言い、ほかは「補助的に」と添えると、誇張していない印象になります。

2. 「直近のプロジェクトで、あなたが担当した範囲を教えてください」

設計、実装、テスト、リリース、運用のどこまでを自分で担ったかを聞いています。チームで作ったものを「自分が作った」と話すと、掘り下げられたときに答えに詰まります。自分が決めたことと、ほかの人が決めたことの線を示すと信用されます。

3. 「そのフレームワークやライブラリを選んだ理由は何ですか」

選定の判断を聞く質問です。自分が選んだのでなければ「既存の構成を引き継いだ」と正直に言ったうえで、引き継いでから変えた点や、変えなかった理由を話します。「流行っているから」ではなく、チームの習熟、既存のコードとの相性、性能や保守のしやすさなど、比べた観点を示すことが大切です。

4. 「試作で終わったものと、本番で動かしたものを分けて教えてください」

Pythonの面談に特有の質問です。分析や機械学習の経験が長い方ほど、試作と本番の区別があいまいになりがちです。本番で動かしたものについては、どのくらいの期間動き続けたか、障害が起きたときにどう直したか、引き継ぎをどうしたかまで話せると、運用の経験が伝わります。試作で終わったものは、終わった理由（精度が届かなかった、事業の判断が変わった）も添えると、経験として受け止められます。

5. 「型ヒントやテストはどのくらい書いていますか」

コードの質を確かめる質問です。面談官は「書いている」という答えより、どう決めて、どう続けているかを聞きたがります。型ヒントをどこまで付けるか、テストは何を対象にしているか、CIで何を自動で確かめているか、レビューで何を見ているかを、具体的な習慣として話します。前の現場で徹底されていなかった場合は、自分の範囲で何をしていたかを話せば十分です。

6. 「Pythonのバージョンや依存関係は、どう管理していましたか」

環境の再現性を確かめる質問です。仮想環境の使い方、依存ライブラリの固定の仕方、バージョンを上げたときの確かめ方を話します。Pythonのバージョンの上げ方で困った経験や、ライブラリの更新で壊れた経験があれば、それをどう解決したかも判断の材料になります。

7. 「性能の問題や障害が起きたとき、どう調べて、何をしましたか」

最もよく掘り下げられる質問です。答えは次の順番で組み立てると伝わりやすくなります。

  • 何の情報から問題に気づいたか（監視、ログ、利用者からの連絡）
  • どこに原因があると見立て、どう確かめたか（計測、再現）
  • どんな選択肢を並べ、なぜそれを選んだか（処理の見直し、キャッシュ、並列化、クエリの改善）
  • 直した後、再発を防ぐために何を残したか

「処理を速くしました」だけで終わると、計測せずに勘で直した印象になります。計測して確かめたことと、ほかの選択肢を捨てた理由まで話せると、判断の質が伝わります。

8. 「扱ったデータの規模と、規模による工夫を教えてください」

データ基盤や機械学習の案件で聞かれます。行数や容量の目安、処理にかかった時間、メモリに載らないデータをどう扱ったかなどです。規模の数字は守秘に触れない範囲で、桁の目安で伝えれば十分です。

9. 「Python以外の言語やクラウドの経験はありますか」

分野の隣への対応力を見る質問です。SQL、シェル、クラウドのサービス、コンテナなど、Pythonの周辺で使ったものを、どの場面で使ったかとあわせて話します。使ったことのないものを「できる」と言わないことが大切です。

10. 「なぜフリーランスで、なぜこの案件なのですか」

長く続けられるかと、案件との合い方を確かめる質問です。働き方の希望だけでなく、どの分野でどんな仕事に力を出したいかを添えると、案件との合い方が伝わります。希望の金額を聞かれたときの答え方は面談で希望単価を聞かれたときの答え方で解説しています。

エージェントベストの見解

Pythonの案件をご紹介していると、面談で評価されやすいのは、分野を最初に宣言し、本番で動かしたものと試作で終わったものを自分から分けて話せる方です。反対に、分析や機械学習の試作の経験が多い方が、Web・API開発の案件でも同じ話を繰り返すと、「本番で動かす仕事ができるか」が見えず、見送られやすい傾向があります。案件の分野に合わせて、話す場面を選び直すことをおすすめします。

技術面談・コーディングテストがある場合

Pythonの案件では、会話の面談に加えて、コードを書く課題や、書いたコードを見せながら説明する技術面談が入ることがあります。見られているのは、難しい問題が解けるかより、読みやすいコードを書き、自分の判断を説明できるかです。

  • 関数や変数の名前、処理の分け方、例外の扱いなど、普段の書き方がそのまま出る
  • 「なぜこう書いたか」「別の書き方との違いは」と聞かれたときに、理由を話せるか
  • 標準ライブラリで済むことに、外部のライブラリを持ち込んでいないか

準備の仕方は技術面談・コーディングテストへの備え方で解説しています。課題の量が多すぎる場合や、実際の業務に使えそうな成果物を無償で求められる場合は、受ける前に範囲を確かめましょう。線引きの考え方は面談で課題の提出を求められたときをご覧ください。

準備は「判断の場面」を3〜4つに絞る

上の質問は数が多く見えますが、答えの材料は共通しています。準備は次の手順で進めると効率的です。

  1. 場面を選ぶ：設計の判断、性能や障害の対応、試作から本番への移行、依存関係の更新など、性質の違う場面を3〜4つ選ぶ
  2. 場面ごとにメモをつくる：状況、気づいたきっかけ、選択肢、選んだ理由、結果、残したものを書き出す
  3. 分野と数字をそろえる：分野、年数、フレームワーク、データの規模の目安を、どの場面でも同じ言い方で言えるようにする
  4. 2分版と5分版をつくる：最初は2分で話し、掘り下げられたら詳しく話せるようにする
  5. スキルシートと照らし合わせる：シートの分野の宣言やライブラリ欄と、話の内容が一致しているかを確かめる

スキルシートとの一致は特に大切です。面談官はシートを見ながら質問するため、話とシートがずれると、どちらも信用されにくくなります。シートの書き方はPythonのスキルシートの記事、冒頭の自己紹介の組み立て方は面談の自己紹介の記事で解説しています。

注意

面談では、前の案件の社名、データの中身、取引先の名前、具体的な売上の数字などを話してしまいがちです。データを扱うPythonエンジニアは機密に触れる立場だった分、話の具体性と守秘のバランスが問われます。データの規模は桁の目安で、処理の内容は一般化して話しましょう。前の現場のコードの質や前任者の批判も、「自分たちも同じように言われるのでは」と受け取られやすいので避けたほうが無難です。

面談の相手によって重心が変わる

Pythonの面談は、相手によって聞かれる内容の重心が変わります。

面談の相手重く見られやすい点
開発チームのリーダー・テックリードコードの質、レビューの進め方、設計の判断
データ基盤や分析の責任者データの規模の経験、SQLとの組み合わせ、運用の経験
機械学習や生成AIの責任者試作と本番の区別、評価の仕方、費用と精度の見極め
業務部門や情報システム部門（自動化の案件）聞き取りの力、説明の分かりやすさ、引き継ぎの経験

エンジニアではない相手が出てくる面談では、専門用語を減らし、「何ができるようになったか」を先に話すと伝わりやすくなります。オンラインで行う場合の注意はオンライン面談で気をつけることにまとめています。

Pythonならではの逆質問

面談の終わりには、こちらから質問できる時間があります。逆質問は、印象づくりより参画後のずれを防ぐ確認に使います。Pythonの案件では、次の点を聞いておくと判断がしやすくなります。

  • 使っているPythonのバージョンと、上げる予定の有無
  • テスト、CI、コードレビューがどの程度回っているか
  • 試作で終わる案件か、本番で動かすところまで担うか
  • 本番の障害対応や問い合わせの窓口に、自分が入るか
  • 分析の担当者や業務部門など、エンジニア以外の相手とのやり取りの頻度
  • 開発環境（手元の端末で動かせるか、指定の環境に入るか）

一般的な逆質問の考え方は業務委託の面談で聞いておくべき逆質問にまとめています。逆質問で聞いた内容は、契約前の確認にもそのまま使えます。案件を選ぶときの確認点はPython案件の選び方で整理しています。

ポイント

  • Pythonの面談では、分野、本番運用の経験、コードの質、性能や障害での判断がよく聞かれる

よくある質問

試作や分析の経験しかなく、本番運用の経験が少ない場合はどう話せばよいですか？

試作の中で、テストを書いた、再現できる手順を残した、ほかの人に引き継いだ、といった本番に近い動きをした場面を中心に話します。本番運用の経験がないことを隠すより、「本番で動かすために何が必要かを理解している」ことを示すほうが、面談官は判断しやすくなります。

コーディングテストで解けない問題が出たらどうすればよいですか？

解けないこと自体より、どう考えたかを話すことが大切です。分かる範囲まで書き、「ここから先はこう調べる」「本番ならこの点を確かめる」と説明すれば、考え方は伝わります。黙り込むより、考えを声に出すほうが評価されやすい傾向があります。

面談で前の案件のデータの規模を聞かれたら、どこまで答えてよいですか？

社名や売上などの数字は伏せ、行数や容量の桁の目安、処理の頻度で規模を伝えれば十分です。どこまで話してよいかの考え方はスキルシートに書いてよいこと・いけないことが参考になります。面談で見送られやすい理由は面談で見送られる理由の記事で解説しています。
